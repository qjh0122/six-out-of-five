| # | 原则 | 含义 |

## P1 · 决策可见性（这是「够不够优秀」的分水岭）

### P1-1 结算页显示「理论最高分 vs 实际得分」 · ✅ 已完成（v110）

| 项 | 内容 |
|---|---|
| **目标** | 让玩家在每把结束后看到：按当时的手牌，**理论上最多能拿多少分**，**自己实际拿了多少** |
| **为什么是它** | 设计域判定：这个游戏把玩家当「规则执行者」而不是「决策者」。`ai.js` 能在 1ms 内枚举 60 种分法并打分，这份能力只用来决定机器人出牌，从没让玩家看过。而对手的分法永远不可见，玩家失去了同类游戏都有的自学通道 |
| **口径（关键）** | 这是**事后视角**——结算后才知道所有人手牌，所以叫「理论最高分」，不叫「你应该这么打」。文案必须点明这一点，否则等于放马后炮 |
| **技术基础** | 结算后客户端已有完整 history（每个人的手牌 `c` + 每组赢家牌型 `t`），用 `engine.settleGroup` 对 60 种分法重算即可，估算 <10ms |
| **做什么** | ① 抽一个纯函数 `bestSplit(hands, myId)` 返回理论最高净胜 ② 结算页加一行对比 ③ 开关控制，关掉与现状完全一致 |
| **不做什么** | 不展示「最优分法长什么样」——那是给答案，会毁掉重玩价值；只给**分数差** |
| **验收判据** | ① 同一手牌跑两次结果相同（纯函数、无随机） ② 关掉开关后界面与现状一致 ③ 60 秒分牌不因此变慢 ④ 人工核对 3 个极端手牌，与手算一致 |
| **成本** | 1~2 天 |
| **状态** | ✅ 已完成。口径按负责人确认的写成「**理论最高 X · 你拿了 Y**」，负数也照常显示（不换「少输了多少」的说法 —— 那在赢的时候无法表达）。实现在 `pwa/js/bestLine.js`（纯逻辑，直接复用 `Engine.settleGroup`，不另写比较器），结算页只挂在「我」那张卡里，别人没有 |
| **实测** | 整把枚举 60 + 6 = 66 种分法、192 次 `settleGroup`，平均 **6ms**（上限定的 500ms）。交叉验证：拿实际用过的分法跑一遍，得到的净分必须等于结算净分 —— 这条把「口径漂移」挡在合入前 |
| **抓到的两个真问题** | ① 第一版按 `room.handId` 过滤 history，而结算页读到 handId=2、history 的 hid 全是 1 → 复盘行整块消失且**不报错**（4589 条单测全绿）。改成取 history 末条所属的那一把，并抽成 `lastHandRounds` 单独测 ② 测试里我自己预设「弱牌对强牌一定输」，实际 +1 —— 因为**单张组里 A 算 1 点、是最小的**，2♦ 能赢 A♠。这条反直觉规则现在单独立了一条断言 |
