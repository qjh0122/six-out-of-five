> **这份文件回答一个问题：接下来做什么、按什么顺序做、怎么算做完。**
>

> - [`docs/BACKLOG.md`](./BACKLOG.md) —— 已知问题与「为什么当时不修」
> - [`docs/review/`](./review/) 下三份 v109 专项分析（代码 / 设计 / 质量）

## 0. 排序原则

计划不是愿望清单，所以先定排序依据。四条，按优先级：

| # | 原则 | 含义 |
|---|---|---|
| 1 | **先堵不可逆的洞** | 密钥泄露、玩家数据入库、规则写错导致玩家算错分——这些「已经错出去了」，越晚成本越高 |
| 2 | **再补「玩家感觉得到」的缺口** | 玩家看不见的东西做得再好也不产生价值；这是当前最大的一块欠账 |
| 3 | **然后才是结构债** | 代码形态的问题不改变行为，但会让每次改动更贵；规模到了才动手 |
| 4 | **不做「加了也不会更好」的** | 内容量已经够（五档时长 5~45 分钟），加牌型/加档位不在计划内 |

## P1 · 决策可见性（这是「够不够优秀」的那口气）

> 设计侧的判定原话：**这个游戏把玩家当成规则执行者，而不是决策者。**
> 系统已经知道答案（`ai.js` 能在 1ms 内给 60 种分法打分），但从来没让玩家看过一眼。

### P1-1 结算页给一句「这把的最优与你的差距」

| 项 | 内容 |
|---|---|
| **目标** | 让玩家在每把结束时知道「我这一把自己的分法值几分」，而不是只知道输赢 |
| **依据** | `design-maturity-v109.md` §5 结论 2 / §7。这是同类游戏不需要做、而本项目规则逼出来的必需品：**对手分法永远不可见，玩家失去了唯一的自学通道** |
| **做什么** | 复用 `ai.js` 已有的枚举打分（`ai.js:147-196`，已能 1ms 内评 60 种），在结算页加一行：`最优能拿 X 分，你拿了 Y 分`。不新增玩法、不改结算逻辑 |
| **不做什么** | 不做「逐张点评」、不做「最优分法展示」（会变成看答案，反而毁掉重玩价值） |
| **验收判据** | ① 结算页出现该行且数值与 AI 的打分表一致（同一条断言跑两次结果相同） ② 关掉开关后与现状完全一致 ③ 60 秒分牌不因此变慢（实测 <10ms） |
| **成本** | 1~2 天（含测试） |

### P1-2 把爆点拦截的手伸到斗牛

| 项 | 内容 |
|---|---|
| **问题** | 现在唯一被系统主动纠正的是十点半爆点——单组最多 2 分/人；而斗牛没牛撞五花牛是 **9 分/人**，系统一句话不说 |
| **依据** | `design-maturity-v109.md` §3.2「系统的手伸到了 2 分/人 的小额失误上，没伸到 9 分/人 的大额失误上」 |
| **做什么** | 把 `tenHalfAdvice` 的判定模式扩展到斗牛：提交前若「本组没牛且存在有牛的打法」给出一次提示（**可坚持提交**，不是硬拦） |
| **不做什么** | 不做成硬拦。十点半爆点是**确定的负收益**，斗牛没牛只是**期望更低**，两者不该同一强度 |
| **验收判据** | ① 提示出现时不阻挡提交 ② 玩家点「就这样交」后结果与现状一致 ③ 有牛的打法存在时才提示（负向断言：无解时不弹） |
| **成本** | 1 天 |

### P1-3 把「怎么分才不亏」写进引导

| 项 | 内容 |
|---|---|
| **问题** | 4 屏引导教的 100% 是「规则是什么」，0 条「怎么分才不亏」。而新手最直觉的打法（大牌给单张）单轮胜率 **41.2%，低于随机分牌的 45.9%** |
| **依据** | `design-maturity-v109.md` §3（§3.1 未教的 7 件事） |
| **做什么** | 引导加 1 屏：「第二轮把大牌留在斗牛，单张那 1 分不值得抢」——一句话 + 一组对照牌例。**总屏数不变**（合并现有 4 屏里重复的一屏） |
| **验收判据** | 新玩家前 3 把的斗牛有牛率，对比改动前的基线有提升（L1 模拟 + L2 真实数据各一份） |
| **成本** | 1 天 |

## P2 · 结构债（不改变行为，但让每次改动更贵）

### P2-1 平台存储收口（`SaveStore`）

| 项 | 内容 |
|---|---|
| **问题** | `localStorage/sessionStorage` 直连散落 **9 个文件、32 处、16 个物理键、3 套命名**（`lxw_*_v1` / `weile_*` / `weile_touch`），无单一实现、无版本迁移、无统一清理 |

| **验收判据** | `pwa/js` 里 `grep 'localStorage\.'` 无输出；v1→v2 迁移实测不丢数据；换内存桩可跑通上层 |
| **成本** | 1~2 天 |

## P3 · 观望（有明确理由不做，写下来防止反复讨论）

| 项 | 为什么不做 | 什么条件下重估 |
|---|---|---|
| **加好友 / 常客名单** | 修的是留存结构（社交全在对局内），但修不好「玩家不知道自己错在哪」——错在局内，不在局间 | 有稳定日活后 |
| **AI 多档难度** | 现在只有一档，且稳定强于新手。加难度不解决「不知道为什么输」 | P1-1 上线后 |
| **`DOUNIU_NONE_PENALTY` 5→2** | 只有 L1 证据，属于把症状调轻；P1-1 做完后玩家能自己看见差距，再谈数值 | P1-1 上线并收集一轮真实数据后 |
| **微信内置浏览器适配（D1）** | 内置浏览器不能装桌面、没有离线，是平台限制 | 有明确的微信内分享场景 |
| **忘记密码找回（D2）** | 需要短信/邮箱通道 = 成本与合规负担，与「无手机号注册」的取舍冲突 | 用户量到需要客服介入的规模 |
| **排行榜分页（D6）** | 现在 8 人规模完全够用 | 人数超过 50 |
| **平板竖屏圆桌（N17/N19）** | 已裁定不支持：放不下就不放，而不是「桌子有了、牌变小一圈」 | 不改「竖屏设计宽 750」这条全站前提就永远不做 |

## 附：本轮 review 的元结论

三个专业域独立得出的判断，指向同一件事：

| 域 | 判断 | 出处 |
|---|---|---|
| 设计 | 「能玩」，底子扎实，但**不是优秀**；差的不是功能，是**决策可见性** | `design-maturity-v109.md` §7 |
| 工程 | 工程质量实际水位高于代码形态给人的第一印象；真正的欠账只有三笔（存储未收口 / 708 行事件容器 / 房间态无持久化） | `code-analysis-v109.md` §7 |
| 架构 | 可公开性 3 分（10 分制），做完治理后 9 分；安全 4 → 8 | `repo-public-plan.md` §6 |

**一句话**：这个项目在「别让规则出错」上投入了 100%，在「让玩家看见自己的决策质量」上投入了 0%。
补后者不需要新增玩法，只需要把已经算出来的答案显示出来。
