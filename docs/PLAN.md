> **这份文件回答一个问题：接下来做什么、按什么顺序做、怎么算做完。**
>
> 输入来自 [`REVIEW.md`](./REVIEW.md)（成熟度与缺口）、[`BACKLOG.md`](./BACKLOG.md)（已知问题）、
> [`review/`](./review/) 下的三份 v109 专项分析。
>
> **本版变更**：2026-11-01 由项目所有者逐项裁定，已剔除不予实施的方向。
> 表里出现的每一条都是**确定要做**或**确定排期在后面**的。

## 0. 排序原则

| # | 原则 | 含义 |
|---|---|---|
| 1 | **先确认功能没坏，再加新功能** | 有 10 个探针是红的、跨 9 个版本没人看。在「功能可能坏了」的前提下加东西，等于在沙子上盖楼 |
| 2 | **先补「玩家感觉得到」的缺口** | 玩家看不见的东西做得再好也不产生价值 |
| 3 | **然后才是结构债** | 不改变行为，但会让每次改动更贵 |
| 4 | **内容量不再增加** | 五档时长（5~45 分钟）+ 五种玩法已经够，不加牌型、不加档位 |

## P1 · 决策可见性（这是「够不够优秀」的分水岭）

### P1-1 结算页显示「理论最高分 vs 实际得分」

| 项 | 内容 |
|---|---|
| **目标** | 让玩家在每把结束后看到：按当时的手牌，**理论上最多能拿多少分**，**自己实际拿了多少** |
| **为什么是它** | 设计域判定：这个游戏把玩家当「规则执行者」而不是「决策者」。`ai.js` 能在 1ms 内枚举 60 种分法并打分，这份能力只用来决定机器人出牌，从没让玩家看过。而对手的分法永远不可见，玩家失去了同类游戏都有的自学通道 |
| **口径（关键）** | 这是**事后视角**——结算后才知道所有人手牌，所以叫「理论最高分」，不叫「你应该这么打」。文案必须点明这一点，否则等于放马后炮 |
| **技术基础** | 结算后客户端已有完整 history（每个人的手牌 `c` + 每组赢家牌型 `t`），用 `engine.settleGroup` 对 60 种分法重算即可，估算 <10ms |
| **做什么** | ① 抽一个纯函数 `bestSplit(hands, myId)` 返回理论最高净胜 ② 结算页加一行对比 ③ 开关控制，关掉与现状完全一致 |
| **不做什么** | 不展示「最优分法长什么样」——那是给答案，会毁掉重玩价值；只给**分数差** |
| **验收判据** | ① 同一手牌跑两次结果相同（纯函数、无随机） ② 关掉开关后界面与现状一致 ③ 60 秒分牌不因此变慢 ④ 人工核对 3 个极端手牌，与手算一致 |
| **成本** | 1~2 天 |

### P1-2 记住上次选的局数

| 项 | 内容 |
|---|---|
| **问题** | 每次开房都要重选局数，默认回 10。原口径是「不选就是 10」，但对固定牌搭子来说这是每次多一次点击 |
| **做什么** | 建房弹窗打开时回填上次选择（localStorage），首次仍回 10 |
| **验收判据** | 选 15 关掉 → 重开弹窗仍是 15；首次访问仍是 10；清缓存后回 10 |
| **成本** | 0.5 天 |

## P2 · 结构债（不改变行为，但决定下次改动有多贵）

### P2-1 平台存储收口

| 项 | 内容 |
|---|---|
| **问题** | `localStorage/sessionStorage` 直连散落 **9 个文件 / 32 处 / 16 个物理键 / 3 套命名**（`lxw_*_v1`、`weile_*`、`weile_version_reloaded`），无单一实现、无版本迁移、无统一清理 |
| **依据** | `code-analysis-v109.md` H1（主程序给出的第一优先） |
| **做什么** | 按四方法契约收口：`read` / `write` / `list` / `migrate`；唯一实现 `LocalStorageSaveStore` 承载全部物理键；组合根注入，上层只依赖接口 |
| **验收判据** | `pwa/js` 里 `grep 'localStorage\.'` 无输出；v1→v2 迁移实测不丢数据；换内存桩上层照常工作 |
| **成本** | 1~2 天 |

### P2-2 `bindEvents` 拆容器

| 项 | 内容 |
|---|---|
| **问题** | `game.js:3911-4618` 单函数 **708 行**，内含 12 个嵌套 binder；注释还写着「570 行」 |
| **硬前置** | **先给 12 个 binder 补「handler 真被调用」的计数断言**。现在事件绑定层几乎没有行为断言，拆之前没有网 |
| **手法** | 沿用 v108 已验证的做法：只搬定义、不动调用点 |
| **验收判据** | 12 个 binder 各有 ≥1 条调用计数断言；拆分后断言数不减；`test/helpers/gameSource.js` 不出现集体假失败 |
| **成本** | 3~5 天 |

### P2-3 房间态持久化

| 项 | 内容 |
|---|---|
| **问题** | 房间只在内存（`hub.rooms`），进程重启 = 所有进行中对局消失，这一把的分数还不落库 |
| **现状兜底** | 靠「发布挑无人时段」这个流程约束。个人项目可接受，但这属于「靠人守」 |
| **做什么** | 落盘房间快照（同一套原子写 + 去抖），启动时恢复未结束的房间 |
| **验收判据** | 打一半杀进程重启，重启后能继续且分数不丢 |
| **成本** | 2~4 天 |

### P2-4 重复实现收口

| 项 | 内容 |
|---|---|
| **双份统计** | 场次 / 胜负 / 胜率 / 连胜在 `profile.js`（服务端权威）与 `records.js`（本机兜底）各有一套。现在口径一致（有测试对齐），但改规则要改两处 |
| **工具函数** | `el()` / `esc()` / `colorFor()` / `short()` 在 `game.js` 与 `records.js` 各有一份；`avatar.js` 的 `esc()` 与 `gameUtils.js` 也重复 |
| **做什么** | 工具函数并入 `js/ui-common.js`（v108 拆分后已具备条件）；统计口径抽成一份共享纯函数，双端引用 |
| **验收判据** | 改一处统计规则，另一处自动跟随（对拍测试能证明） |
| **成本** | 1 天 |

### P2-5 `state` 字段分组

| 项 | 内容 |
|---|---|
| **问题** | `state` 上堆了 17 个字段、生命周期各不相同（本次打开 / 当前房间 / 当前分牌），跨屏污染难查。其中 `justDealt` / `absorbSig` / `dissolveWasActive` 三个还靠首次赋值动态挂上，没在字面量声明 |
| **做什么** | 分三组 `state.session` / `state.room` / `state.split`，在进房、退房、开局三个时机整体重置；三个隐式字段补进声明 |
| **验收判据** | 从战绩页回首页再进房，不出现上一局的残留状态 |
| **成本** | 1~2 天 |

### P2-6 CI 偶发失败（待抓现场）

| 项 | 内容 |
|---|---|
| **现象** | 公开仓库 CI 在同一份功能代码上出现过一次 failure、两次 success（`c74b4d4` 成功 → `0a11d7e` 失败 → `6bc48d5` 成功 → `12a4c23` 成功），失败点在「全量测试」 |
| **推测** | 时间敏感测试在慢机器上超时：`ws-heartbeat`、`login-ip-limit`（10 分钟窗口）、`dissolve-timeout` / `forfeit-timeout` |
| **做什么** | 下次失败时抓日志定位；确认是超时后放宽阈值或注入可控时钟 |
| **不要做** | 不要为了让 CI 变绿去放宽全局超时 —— 那会把真超时一起盖掉 |
| **成本** | 半天（前提是抓到现场） |
