# 探针排查：10 个红探针到底是什么（2026-11-01）

> **这份文件回答一个问题：v108 那轮体检里 10 个红探针，是「脚本跟不上」还是「功能真坏了」。**
>
> 背景：`review/2026-11-01-v108.md` 记下「36 个探针 25 绿 / 10 红，跨 9 个版本无人处理」。
> 两组 REVIEW 都提到了它，但没人去跑 —— 因为跑一个探针要起一个真浏览器，37 个串起来 20 分钟。
> 结果是这 10 个红点变成了一个说不清的悬案：**在「功能可能是坏的」前提下加新功能，等于在沙子上盖楼。**

---

## 一、结论

**10 个红探针，已查清 8 个，全部是脚本过期，没有一个功能是坏的。**

而且根因高度集中：**v103 把「创建房间」改成了两步**（先弹「本局打几把」，点确认才真的开房），
探针还按一步点 —— 于是房间根本没建，后面所有断言都在「没有牌桌」的前提下执行，
报出来的是一堆看起来像功能问题的假象，比如：

- `probe-tenhalf` 报「**找不到一对会爆的牌**」——听起来像发牌出了问题，
  实际是它连牌桌都没进去，`enterSplit()` 返回 null，重开 4 次全空。
- `probe-emoji` 报「**顶栏没有对手座位**」——听起来像座位环坏了，
  实际是房间压根没建。
- `probe-result-seq` 报 `{registered:true, bots:0, gameVisible:false}` ——
  「补 AI 补了 0 个」，因为它没见过房间页，`btn-add-bot` 是隐藏的。

这类假象最难查：**它把「测试自己坏了」说成「产品坏了」，而且症状描述得很具体、很像真的。**

| 探针 | 修前 | 修后 | 根因 |
|---|---|---|---|
| `probe-emoji` | 0/2（后续全挂） | **44 / 0** | 建房两步 |
| `probe-tenhalf` | 0/2 | **39 / 0** | 建房两步 |
| `probe-leave` | 5/14 | **19 / 0** | 建房两步 |
| `probe-ready-button` | 8/4 | **12 / 0** | 建房两步 |
| `probe-table-ready` | 16/17 | **34 / 0** | 建房两步 + 2 条断言停在 v103/v106 之前 |
| `probe-result-seq` | 崩（无汇总） | **57 / 0** | 建房两步 |
| `probe-slot-type` | 崩（无汇总） | **29 / 0** | 建房两步 + 死分支里的未定义变量 |
| `probe-rollback` | 8/14 | **22 / 0** | 建房两步（且在「单参 evaluate」的文件里照抄了双参写法） |

`probe-tenhalf` 修完的 39 项里包括它自己的核心断言，都是真跑的：

```
PASS ★ 槽位进入爆点态（.is-bust）
PASS ★ 拦截框只有一个按钮（没有「就这样提交」这种后路）
PASS ★ 改成不爆的组合后再提交：正常放行（10.5）
PASS ★ 那件事已经在门口解决了（确认框里不再有爆点警告）
```

这说明「十点半爆点拦截」这条 v103 的核心交互**一直是好的**，只是没人验证过。

## 二、修的过程中暴露的第二层问题

修「建房两步」只是把门打开；门开了之后才看见里面还堆着三样东西。这三样都是**以前从没执行过的代码**：

### 1. 死分支里的未定义变量（`probe-slot-type`）

```js
const th = (sampled || {}).tenhalf || {};      // sampled 在全文根本不存在
```

采样结果一直存在 `placed.seen` 里（同文件第 420 行就在用 `placed.seen.piaosanye.slotFresh`）。
这条分支只在「十点半正好凑到 10.5」时才走 —— 探针进不了牌桌时永远走不到，
进了牌桌第一次抽到 10.5 就 `ReferenceError`。

**这类 bug 的特征：它不在「经常跑的路径」上，所以从来不会红，也从来不会绿。**

### 2. 断言停在两条已删的规则上（`probe-table-ready`）

| 旧断言 | 现实 | 处理 |
|---|---|---|
| 「中央卡写了**起始 20 分**」 | v106 把基准分改成 0，卡片显示「第 1 / 1 · 0 分」 | 改成断言「有分数读数 + 有把次进度」 |
| 「中央卡写了**见底规则**」 | v103 已删掉「见底出局」 | 改成**反向断言**：不该再出现「见底」 |

第二条尤其值得记：把一条**已删的规则**正着钉在测试里，等于让测试站在产品的对立面 ——
它红了不是产品退步，是产品前进了而测试没跟。改成反向断言之后，它才重新变成守卫
（有人把删掉的规则写回去，它会立刻红）。

### 3. 「页面里跑的代码」和「Node 里跑的代码」混写

`probe-leave` 里那段登录+建房是一整块**字符串**（传给 CDP 在页面里执行），
里面只有页面环境。第一版修改时我在里面写了 `await sleep(500)` 和 `evaluate(cdp, …)` ——
那是 Node 侧的函数，页面里不存在，报 `"… is not a function"`。

同一类错误在 `probe-rollback` 上换了个样子：那个文件的 `evaluate` 是**单参数**的
（`evaluate(expr)`），照抄别的探针写成 `evaluate(cdp, expr)` 之后，`cdp` 对象被当成表达式
传给 CDP，报 `Failed to deserialize params.expression`。

**教训**：探针是 37 个独立脚本，各写各的辅助函数，签名不统一。
批量改探针时不能按「一个文件的写法」推全部。

## 三、为什么这一年没人发现

| 原因 | 具体 |
|---|---|
| **不在 CI 里** | 37 个探针一个都没接 CI（`grep -c "probe" .github/workflows/test.yml` = 0）。红不红全靠有人想起来跑 |
| **跑了也不看** | 探针输出几百行，`5/14` 这种数字混在中间，不主动找看不出来 |
| **症状描述得像产品 bug** | 「找不到一对会爆的牌」不会让人想到「房间没建」 |
| **一次改动的连锁反应没人算** | v103 改建房流程时，受影响的探针有 11 个。改的人不可能同时想到 11 个脚本 |

这正是 `docs/PLAN.md` P0-2 要解决的问题：**把一部分探针接进 CI，并且第一次上线必须先证红**
（删掉一个导出 → CI 必须失败）。没有这一步，下一轮改动还会重演同一件事。

## 四、本轮新增的工具

`scripts/run-probes.js` —— 探针跑批器。

```bash
node scripts/run-probes.js                # 全跑（约 20 分钟）
node scripts/run-probes.js leave tenhalf  # 只跑名字匹配的
node scripts/run-probes.js --list         # 列清单
```

输出三态：`✓ 全绿` / `✗ 有失败` / `‼ 崩溃（连汇总都没打出来）`。
第三态单独标出来是有意的 —— 崩溃的探针最可疑，它多半是脚本自己被改坏了，
而不是产品坏了（本轮 8 个里有 3 个属于这一类）。

**为什么不并行**：每个探针起一个独立 Edge + HTTP 服务 + WS 端口，CDP 端口挤在 93xx 区间，
两个撞上就开始互相串消息。串行 20 分钟是值得的。
**为什么不传视口**：各探针参数格式不统一（`390x844` / `390 844` / 不认参数三种都有），
传错会让宽高变成 `NaN`、断言全乱。一律不传，用各自默认值。

### 5.1 我自己引入的两个回归（如实记录）

给成就系统加了个入口之后，两个既有探针立刻变红 —— 这是**它们起作用了**：

| 探针 | 报什么 | 实际情况 |
|---|---|---|
| `probe-safearea` | `#ach-entry-num` 字号 9.9 CSS px < 11px | 我按 24 设计px 写的，横屏 `stageScale ≈ 0.41` 之后只剩 9.9。改成 30 → 12.3px |
| `probe-seat-info` | 信息档 `scrollH=569 > clientH=538` | 成就行 75px 把底部顶出去 31px。压缩行高 + 隐藏那句「只读查看」的说明 |

**这两条如果没接探针，会原样发到线上** —— 一条是横屏下小字看不清，一条是面板最后一行被推到滚动区外。
它们是 P0-2（探针接 CI）最直接的论据。

### 5.2 一个被这次排查顺手抓住的泄露

`scripts/probe-records-cloud.js` 里有 3 处真实玩家昵称（`爱吃肉的棒国`）。

**为什么脱敏时漏了**：脱敏脚本替换的是完整昵称「爱吃肉的棒国**华**」，而探针里写的是截断版
（少一个字）。**截断变体是脱敏最容易漏的一种**，它不在任何词表里，肉眼扫代码也看不出来。

已经补了两层：① 改成「玩家A」；② 复查脚本改成「对每个昵称额外检查去掉末字的变体」，
扫出 6 个命中，逐一确认全是误伤（`qjh0122` 是 GitHub 用户名、`sam`/`will` 是 `same-origin`/`will-change` 的子串）。

## 六、两条「待查」的结论（v110 查清）

上次留了两条「不知道是真 bug 还是探针过期」的，这一轮都查完了 —— **两条都不是产品 bug**。

### 6.1 `probe-records-cloud`：`reset-stats` 其实调了

| | |
|---|---|
| **症状** | 界面确实变空了（本地清干净了），但探针的 mock 服务器 `resetCalls` 是 0 |
| **真因** | **断言比请求先执行**。原顺序是「点确定 → 等页面出现空态 → 立刻断言 `resetCalls === 1`」。而空态是 `finish()` 里 `Records.clear()` 之后同步渲染的，请求那时候可能还在路上。读到的 0 既可能是「真没发」，也可能只是「读早了」—— 两种含义完全不同的故障混成一个数字，等于没有诊断力 |
| **现在** | 加了 `waitForFlag(() => resetCalls, 6000)`：真没发就超时失败，发慢了就多等 80ms 后通过。同时把断言的期望值从「共 25 局」改成「共 25 场」（单位统一了） |
| **结果** | **52 项全绿**。前端 `AuthStore.resetMyStats()` → `/api/me/reset-stats` 这条链路是通的，「删除是真的删了」 |

> 顺带收获一条通用教训：**「等 UI 变化」不等于「等副作用完成」**。UI 变化可能来自乐观更新，
> 而副作用（网络请求、落盘）是另一条时间线。这两者混用时，断言就变成了掷骰子。

### 6.2 `probe-result-seq`：两个「3」是合法的并列

| | |
|---|---|
| **症状** | 4 人局（冠军 + 3 个 AI）的名次角标是 `["","2","3","3"]`，探针期望 `["","2","3","4"]` |
| **真因** | **并列**。第 3 和第 4 同分 → 竞赛式排名两人都是第 3，第 4 名被跳过。页面本身是对的，而且已经给这两行加了 `is-tie` 标记（视觉上有区分） |
| **探针的问题** | 断言写死 `[2,3,4].slice(0, BOTS)`，等于假设「这局没有同分」。可**同分在真人局里很常见**，一撞上就红，而且红得让人以为名次算错了 |
| **现在** | 改成**独立复算**：探针自己读每行的分数、按从高到低算出期望角标，再和页面读数比。同时新增一条「并列的行才带 `is-tie`，不并列的不能带」。这样既能放过合法并列，也能抓住真正的算错 |
| **结果** | **62 项全绿**。实测这一局 `scores: [21,-4,-4,-13]` → `pos: ["","2","2","4"]`（第 2、第 3 同分并列）|

> 这条值得单独记一句：**「写死期望值」在有个体差异的地方一定会假红。**
> 名次、时间、随机牌都是这类。判据应该是「按规则复算」，不是「上次跑出来的样子」。

### 6.3 仍然没做的

| 项 | 说明 |
|---|---|
| **`probe-handlimit-settle.js` 的重试分支注释** | 注释写着「任一玩家分数 ≤0 会提前结束」—— 那是 v103 之前的规则。分支留着无害（能兜其他异常），但注释是错的。记为 `BACKLOG N18` 的一部分 |
| **其余探针的断言时效性** | 全量 37 个里，绿的只说明当前代码能过，不说明断言还反映当前规则。§二.2 那类问题可能还有 —— 这是 `N18` 仍开放的唯一原因 |
| **UI 巡检接 CI** | ✅ 已在 v110 完成，见 `PLAN.md` P0-2 |
