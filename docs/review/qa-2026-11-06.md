## ① 结论先说

**判断是「仍有大洞」，不是「已经过密」。**

不是"多测了没用的"，而是**测的全部集中在不需要动的那一层**：状态机与协议字段名被反复钉死，而「跑起来会不会对」这一层系统性缺失。

三条硬数字支撑（均为静态可复算，非推断）：

1. **`pwa/js/game.js` 5239 行，0 个测试 `require` 过它**。占前端 JS 总量（18385 行）的 **28.5%**，且是 100% 的 DOM / 渲染 / 交互 / 结算页 / 房间页层。零依赖（无 `node_modules`）→ 无 jsdom / playwright，「用一个测试真正跑到它」这条路现在不存在。
2. **`server/hub.js` 三个到期回调体从未被执行过**：`_startGrace` 的 90 秒宽限、`_armHoldTimer` 的 3 分钟等待、`_armRoomRecycle` 的 30 分钟回收。它们的时长是**硬编码常量**（`GRACE_MS = 90000` / `stateMachine.js:1209 HOLD_TTL_MS = 3*60*1000` / `ROOM_IDLE_MS = 30*60*1000`），全仓**没有任何假时钟**（`grep useFakeTimers|fakeTimers|clock.tick|sinon` → 0），也没有任何测试等过 ≥60 秒。
3. **全仓 0 处并发发送**：135 个文件里 `Promise.all` 出现 **0** 次。所以「两人同时 wantNext / hold 到期与 wantNext 撞一起」这一类，连"两个人一起发"这个前置动作都不存在于测试里。

配套的反对意见我也写清楚：**不要在这个基础上继续加状态机单测**。`stateMachine.js` 已被 31 个文件 `require`，server 侧守卫占比只有 5.7%，那部分深度是够的。新投入必须全部落在"第一次真正执行某段代码"上。

**我补的那条分支（比 `outNext` 更容易触发）**：
因为 `MIN_PLAYERS = 2`，在 2 人房里 `dropFromNext` 掉任何一个人，`list` 必 ≤ 1 → `canStartNext` **恒为 false**。也就是说：

> **2 人房里「不等他」这颗按钮在数学上永远无效**，无论被跳的是 `outNext` 还是「结算期掉线、且永远不会回来的人」（`:1782` 保证他不会变成 `left`，所以他会一直挂在 `pendingNextPlayers` 里）。按钮点了必然开不了局，而 `dropFromNext` 返回的是 `{ok:true}` —— **用户得到的反馈是「操作成功」**。

唯一出路是 `addBot`（房主专属）。这与 §3.1-B3（holdNext timer 漂移）合起来是同一类故障：**"所有人都在等，界面显示得很正常，就是不开，而且没有任何东西告诉你会一直不开"**。

**对验证方式的要求（判据 4：系数要用极值跑一遍证明可达）**：这条必须以**表驱动**覆盖 `N = 2,3,4,5` 全档，断言「`dropFromNext` 之后 `canStartNext` 的期望值」随 N 变化的**变点恰好落在 N=2 与 N=3 之间**。只测 3 人房（现有 `next-round-gate.test.js` 的覆盖范围）永远看不到这个边界。

### 3.3 结算页「等待说明」的空态：事实成立，但**归因不成立**

> 技术架构师新增 6/7/8 的复核见 §⑥.2。这里只收结论，因为其中一条会直接影响是否该动 `settleView.js`。

**事实（已复核）**：`settleView.js:945-963` 里 `joined = nextRoundPlayers(room).length`；`waitTxt` 初值 `''`；只有 `holdNow` 或 `joined > 0` 两支会写文案。于是 **`joined === 0 && !holdNow` → `waitTxt` 保持空串**。`renderWaitRow(:977-1000)` 里那句 `else if (!line) line = '还有朋友要来？点「等人」先别开牌'` **嵌在 `if (iAmOwner)` 内**（`:981`）→ 非房主拿到 `box.textContent = ''`。

**但我不认为这是 bug（判据 2：误伤评估）**：
`joined === 0` 的语义是「**包括我自己在内，没有任何人点过「开始下一局」**」。此时非房主看到的就是一颗可用的按钮 —— **没有任何"点了没反应"需要解释**。空态是"无可奉告"，不是"漏了文案"。
反过来硬填一句话的代价已经写在代码里：`settleView.js:969-974` 记录了这个位置试过三处、全部撞墙（390×844 下 cover 重叠 4177px²、要往下滑才看得见、与把数块重叠）。**为填一个正确的空态去重复一次已经失败过三次的排版实验，是负收益。**

**真正的缺陷在同一支的房主侧**，而不是非房主侧：
`:996-998` 那句「还有朋友要来？点「等人」先别开牌」在**「房间已不可能开局」**时是**误导**——用户照做会挂起 3 分钟，到期后仍然开不了（§3.2）。这与 `:940-944` 注释里 v121 修过的那个 bug 是同一个形状：**给了方向，但方向指错了**。

**所以这条要测的不是文案，是「出口存在性」**（把文案断言翻译成可判定的不变量）：

> 对任意「`canStartNext(room) === false`」的房间状态，必须满足 `pendingNextPlayers(room).length > 0 || holdNextOf(room)` —— 否则这个房间**既有否决理由、又没有任何可点出口**，界面说什么都是在骗人。

这条在**纯 SM 层**就能跑，不需要 DOM、不引用任何文案，而且它同时覆盖 §3.2 的死锁分支。断言消息里再报出「当前 `joined` / `pending` / `holdNow` / 剩余真人数」四个数，红了就能直接定位。
