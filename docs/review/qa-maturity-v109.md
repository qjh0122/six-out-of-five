### 3.1 独立复算：期望值是否引用被测常量 / 被测函数

**正面（1）** `pwa/test/engine.test.js` 头部把这条纪律写成了设计原则 —— 这在本仓是**自觉**而非偶然：

> 「能用『独立实现』算期望值的地方，绝不拿引擎自己验自己（例如十点半总点数用 rank 直接算、斗牛牛几用总点数取模算）」

配套的正例：`pwa/test/double-bust.test.js:31`

```js
ok(E.tenHalfTotal(a99) === 180 && E.tenHalfTotal(b88) === 160, '点数分别是 18 / 16（×10 存）');
```

`180`/`160` 是**手算常量**（存的是 ×10 的内部表示），不是拿 `tenHalfTotal` 反推的。同类正面：`scripts/e2e-score.js` 用 engine 独立复算 DOM 上渲染出的分数并做三方一致性比对 —— 它验的是**「页面画出来的数字对不对」**，不是「函数自己等于自己」。

**正面（2）** `pwa/test/config-sync.test.js:47-55` 是**变异式**自检：先人为把 `Engine.CONFIG.INITIAL_SCORE` 改成 `999999`，再重新加载 config，断言被纠正回原值。这不是「跑一遍通过」，而是**先造一个坏状态，证明守卫真会红**。全仓最稀缺的一个动作。

**反面（1）** `pwa/test/double-bust.test.js:55`

```js
ok(E.tenHalfTotal(p1) === E.tenHalfTotal(p2), '两手点数相同');
```

期望值来自**被测函数本身**。它只能证明「两个输入被映射成同一个数」—— 如果 `tenHalfTotal` 整体算错（例如把 A 一律当 10），这条**照样全绿**。这是本仓最典型的一类「自证式」断言。

**反面（2）** `pwa/test/handkey.test.js:147`

```js
ok(SM.handKey(room3) === SM.handKey(room3), '重复计算得到同一个键（无副作用）');
```

作为「幂等/无副作用」的断言它是**正当**的（它有独立的语义目标），但作为「键的取值对不对」它**零判别力**。读的人容易把它当成后者。

### 3.2 误伤评估：按这条判据改实现会不会引入新问题

**正面** `pwa/test/room-actions-fit.test.js`（12 项）钉的是「CSS 约束」而不是像素值；`pwa/test/sw-precache.test.js` 面对「`flex-gap-fallback.css` 不该进预缓存」这个决定，用的是**显式豁免 + 一条「豁免项没有被加回清单」的反向断言**，而不是把断言放宽或删掉。这两处的共同点是：**改实现不会误伤，因为判据站的是意图层。**

**反面（实测误伤，有数字）** 28 个文件用 `helpers/gameSource.js` 对源码做正则。v108 把 `game.js` 拆成 1+8 个文件后，这批守卫**全部假失败**：

- 规模：**275 项 / 17 个文件**（来源 `REVIEW-v108-2026-11-01.md` §四）；
- 处置是正确的（`gameSource.js` 让读取跟上布局，**断言一个字不改**，并显式拒绝「删断言/放宽断言」这条捷径 —— 它头部把这条写成 `✗` 项）；
- 但结论要留住：**这类判据对「实现搬家」零容忍，对「实现接错」零发现**。v108 挖出的 5 处致命失效全在「两边接得上吗」这个层级：`modalKit` 导出块丢失、`cardView` 8 个尺寸常量没导出、9 个依赖按值传引用后被 `var` 赋值覆盖成 `undefined`、`settleView` 用了裸 `BIG_TYPES`、三个模块用了裸 `state`。**旧守卫一条都没红。**

`pwa/test/module-contract.test.js`（v108 新增 39 项）就是为这个层级补的，并且它自己写了「都用已知坏样本证过会红」。**这是全仓判据质量的最高点，建议作为模板推广。**

### 3.3 负向断言：不该触发的事件是否计数为 0

**密度（实测）** `=== 0` **146** 处、`!==` **195** 处、`=== false` **87** 处、`=== null` **34** 处、`length === 0` **40** 处、`.length, 0`（`eq` 形式）**67** 处。粗估负向断言占比 **18.8%**（口径：`ok`/`eq` 实参里出现上述形态，行级 —— 见 §3.0 的工具告警）。

**正面** 三条分别代表三个不同层：

- 实现层：「不许再用旧写法」—— `pwa/test/render-guards.test.js`
  `eq(/state\.myId\.slice\(-4\)/.test(gameJs), false, '没有裸露的 state.myId.slice(-4)')`

### 3.4 一致性与可达性

**正面（一致性）** `pwa/test/offline.test.js:120-121` 用正则从 `server/hub.js` 与 `pwa/js/roomStore.js` 里**分别取出** `GRACE_MS`，断言两侧都是 `'90000'`。同一事实两处陈述、跨两个文件比对 —— 这正是「同一对象的两个陈述不得互相否定」的落地写法。同文件 `:43/:47` 又真跑状态机证明「宽限到期 → `left = true`」**可达**，两条一起构成「一致性 + 可达性」的完整闭环。

**正面（可达性自检）** `pwa/test/module-contract.test.js`「用已知坏样本证过会红」+ `config-sync.test.js` 的破坏-恢复。

**反面（上限/系数没用极值跑过 → 恒真门）** `BACKLOG.md` **N26** 记的正是这件事：「起始分归零之后，两条守卫**退化成恒真门**」。这类失效最阴险的地方是 —— **测试仍然全绿、CI 仍然绿灯、报告仍然可以写「守卫在守」**。同一族的另一个实证是 **N23**：把 `INITIAL_SCORE` 从 20 改成 0 时，**15 项硬编码 20 的断言全挂**，而它们守的是「零和」「分数不被凭空改动」这些真规则 —— 判据没错，**是判据把数值写死了**。修法（改成读 `CONFIG.INITIAL_SCORE`）也是正确的。

### 5.2 「读旧 review 时的坑」—— 四条，按踩中概率排序

1. **版本号有三套编号在打架，认「版本」不认「R 编号」。**
   `app-version`（`20261101a`）/ `sw CACHE_NAME`（`v108`）/ `release-progress` 的 `R7–R17` / 章节号的 `v44–v108` —— 四套并存。**N2 就是被这套编号坑过的实例**：它记的是「v86 已修（版本 `20261031f` / sw `v90`）」，一个修复横跨三个编号。**引用时永远写「app-version + sw 版本」两个数，只写 `vXX` 会在两套编号间失配。**
2. **「已修」≠「已验证」。** N5 写「v81 已修，**待真机复验**」；N2 的教训更狠 —— `probe-online-smoke` 当时把 403 算作**不算失败**，于是「线上 manifest 全 403」在输出里**挂了一个月**都没人发现。**读旧 review 时必须区分「代码改了」与「线上验过」。**
3. **「平台限制 / 不做 / 接受」这三个词必须重审。** N2 是「平台限制」被推翻；N19/N17 是「裁定不做」（有明确几何理由，可信）；B-L1–B-L4 是「接受」（每次复核都重写了理由，可信）。**三类混在一起时，只有 N2 这类是错的** —— 判断标准：看它有没有写「将来怎么验」，没写的那条就是没想清楚。
4. **旧 review 的汇总数字一律不可复用。** 42/23/19 → 46/29/17；108 文件/4463 断言 → 109/4502。**汇总层是全文最不可信的一层**，因为它靠 grep，而 BACKLOG 有五种关闭写法（`已完成/已修/已清/已改/归零`）。在新文档里，**要么逐条实读后重算，要么明确标「引用自 X，未复核」。**
