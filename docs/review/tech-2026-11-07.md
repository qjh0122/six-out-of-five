## ② 定时器与重启的正确性缺口（指到函数与行号）

### 2.1 三类场景现在各自靠什么保证

**(A) 进程重启**

| 环节 | 靠什么 | 位置 |
|---|---|---|
| 写 | 400ms 去抖 + **同步**原子写（`writeFileSync` → `renameSync`） | `hub.js:273 _scheduleStateSave` / `roomsState.js:41-42` |
| 读 | 坏文件 / 版本不符一律 `null`，**不挡启动** | `roomsState.js:52-76`，`:68` 是版本闸 |
| 谁被恢复 | 房间对象 + 座位令牌；连接一律置 `connected=false` | `hub.js:186-217`，`:193` |

**(B) 时间跳变**

先说结论：**运行期是安全的，跨进程是不安全的。**

- 运行期：`setTimeout` 用的是单调时钟，已经把时长定死了，`Date.now()` 之后不再参与 → 系统时钟跳变**不影响已挂的计时器**。
- 跨进程 / 每次重算：全部依赖 `Date.now()` 减一个落盘的墙钟时刻 —— 共 **5 处**：`hub.js:252`（grace）、`:959`（dissolve）、`:728`（hold）、`:1494`（split 补时限）、`:1230`+`:1250`（下发给客户端的 `splitEndsAt` / `holdNextEndsAt`）。
- **缺口**：这 5 处里只有 3 处会真正设置 timer，而设置点 `hub.js:1546`（grace）、`:959`（dissolve）、`:734`（hold）**全部只写了 `Math.max(0, …)`**。
  → 时钟**回拨** T 秒，就把 grace 延长到 `GRACE_MS + T`，dissolve 延长到 `DISSOLVE_TIMEOUT_MS + T`，hold 同理。
  → 时钟**前跳** T 秒，`Math.max(0, 负数)` 归零 = **立刻判全桌断线者离开**（这条方向是"快"，比"永不判"好，但同样没有上界保护）。
- **修法（三行，不是重构）**：把上界钳制放**进设置点**而不是调用点 ——
  `_startGrace`（`hub.js:1546`）改成 `Math.min(GRACE_MS, Math.max(0, Math.round(delayMs)))`；`_syncDissolveTimer`（`:959`）与 `_armHoldTimer`（`:734`）同样加 `Math.min(自身 TTL, …)`。
  为什么放进设置点：这样「任何调用点都不能传超上限」变成**被测行为**，而不是一个只写在恢复路径里的约定。

**(C) 并发重连**

现有防线**是够的**，我逐条核过，不成立的地方我也写出来：

| 场景 | 现状 | 判定 |
|---|---|---|
| 同一 playerId 两条活连接，关掉其中一条 | `onClose`（`hub.js:399-415`）先 `_hasLiveConn(ctx.playerId, ctx.roomId)`（`:1651-1657`，**同时比对 playerId 与 roomId**）→ 还有活连接就**不判掉线** | ✅ 正确 |
| 重复 `reconnect` | `_clearGrace`（`hub.js:1071`）+ `_refreshSplitDeadline`（`:1073`）都是幂等的；`graceTimers` 键是 `roomId#playerId`，与连接无关 | ✅ 正确 |
| 断线 → 宽限内回来 | `reconnect` 里 `_clearGrace`；`markDisconnected` 写下的 `disconnectedAt` 由 `hub.js:599` 置 `null` | ✅ 正确 |
| 「宽限到期回调」与「此刻正好回来」抢同一个 tick | 单线程 + `clearTimeout` 对未执行回调有效 + 回调里还有 `if (!p \|\| p.connected \|\| p.left) return`（`hub.js:1552`）三重保险 | ✅ **我原本怀疑这里有竞态，核过源代码后撤回** |

→ **结论：并发重连不是缺陷，是盲区。** 全仓没有一条测试是"同一 playerId 两条连接交错"或"close 与 resume 同 tick"。要指到函数的话，盲区就是 `hub.js:399 onClose` + `hub.js:1049 reconnect` + `hub.js:1651 _hasLiveConn` 这三者的组合 —— 它们**互相依赖正确**，而**没有任何断言钉住这个组合**。

### 2.2 还缺的那一条断言（最关键的一条）

> **「重启前后，同一张桌上『谁在什么时候被判离开』必须可复算」**

具体形态（写进 `server/test/rooms-state.test.js`，它就是该文件应有的第 24 项）：

```
构造快照：5 人局，p1.connected=false，p1.disconnectedAt = now - 30000
new Hub({ statePath })
断言 (a) graceTimers 有键 `roomId#p1`
断言 (b) 其触发时刻 ∈ now + (GRACE_MS - 30000) ± 200ms      ← 钉住"按剩余"，不是满额
断言 (c) _view(room, null).splitEndsAt - Date.now() <= SPLIT_TIMEOUT_MS   ← 上界，钉住 N-1 / N-2
```

- (b) 已经能被 v125 的实现满足 —— **但它现在没有被断言**，任何人把 `_startGrace(…, left)` 写成 `_startGrace(…)`，145 个文件 5630 条断言**没有一条会红**。

### 4.1 明确**不进表**的一项：100 人在线的服务端开销

**未实测。** 而且它**今天没有观测点**，所以进不了预算表 —— 按预算准入规则，绑定不到可执行处置的条目不得进表。

能给的是**上界推算**（基于 v123 评审实测的单房间快照 3,348 字节，非本轮实测）：

- 100 人 ≈ 20 桌（5 人局）→ 快照 ≈ **67 KB 序列化**、房间对象 heap **< 2 MB**。
- `_saveStateNow` 每次**全量**序列化所有房间（`hub.js:285-291`），400 ms 去抖 → 稳态 **2.5 次/秒 JSON.stringify + 一次同步 fs 写**。

- 连接数**无上限**（`server.maxConnections` 零设置；`_checkCapacity` 只管房间数 5000，`hub.js:1665-1667`）→ 真正的过载形态是 **fd / 内存被空连接吃满**，而非房间数。

补完之后才能挂阈值（建议 `rss < 200 MB`、`eventLoopDelay p99 < 50 ms`、save 频率 `< 3/s`）。

## ⑤ 三条优先级（按「不做的代价 × 成本」排）

### 1️⃣ 把「跨进程的时间」这条债收口 —— 0.5 天

**做什么**（三件事，一处口径）：
1. `splitStartedAt` 的语义落盘：**不要动 `roomsState.VERSION`**（`roomsState.js:68` 是 `Number(obj.v) !== VERSION → null`，bump 一次等于**上线那一刻把在飞的房间全丢一次**，比它想修的问题更严重）。做法：在 `room` 对象上加一个增量字段（如 `splitEndsAtByPlayer`），老快照没有就按"满额"处理并可断言。
2. 三个设置点加上界钳制：`hub.js:1546` / `:959` / `:734`。
3. `hub.js:248` 循环开头补 `if (!this.rooms.has(roomId)) return;`（N-3）。
4. 补一条断言（2.2 那条 (b)+(c)）。

**判据**（改完能回答）：问「重启后分牌倒计时是剩余还是满额」→ 有一个**断言**能回答，而不是靠读 `hub.js:1474` 的注释。

**为什么排第一**：成本 0.5 天，收益是「把最后一类静默规则变化变成断言」，而且**不需要产品决策**。

### 2️⃣ 把 17 条 `manual` 探针接进发版门禁 —— 0.5 天

**做什么**：
