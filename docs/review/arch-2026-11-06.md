### 为什么 `game.js` 判「不拆」（判据，不是感觉）

判据：**看「一次典型改动」要跨几个文件、跨多少行**，不看总行数。

- 实测一次功能改动（v122「等个人」）的切面：`stateMachine.js`（12 处）+ `hub.js`（4 处）+ `roomStore.js`（1 处）+ `pwa/js/game.js`（1 处）+ `settleView.js`（1 处）+ `pwa/test/hold-next.test.js`（21 处）+ `server/test/hold-next.test.js` —— **7 个文件**。这是**双端同源 + 协议 + 视图分层**的结构性代价，删掉 `game.js` 里那 1 处也不会变成 6 个文件以下。
- 也就是说：`game.js` 已经不是新功能的主战场，它是「29 个 RPC 调用点 + 各自的 busy/flash/render 样板」。再拆一次的收益是导航，成本是**每一处调用点都可能接错**——而接错的表现恰恰是本文件第 3、4 条风险（静默 / 文案误导）。
- 什么时候该重启拆分（任一成立）：① 同一类改动需要在 `game.js` 的 **≥3 个互不相邻区域**改代码（用 `grep -n` 看行号分布，跨 >1500 行）；② 新增一种「屏幕形态」（如旁观页/复盘页）需要往裸 `game.js` 加 >150 行；③ 一次定位需要连续读 >800 行上下文。
- 在此之前，把 `game.js` 的增长成本压到最低的**唯一**动作是：把第 3 条那 11 处 `catch` 收敛掉（它们是这个文件里唯一会自动把 bug 藏起来的东西）。

**第 10 条的解法（已按 QA 复核改正）**：
- **先撤回一个错误归因**：我上一轮说「`holdNextLeftMs` 会踩设备时钟偏差」——**不成立**。它唯一调用方是服务端（`hub.js:637`），服务端算服务端时间，当前不存在设备偏差；偏差只会在「前端拿它做倒计时」之后才出现，而前端现在是零调用点。
- **同时撤回一条无效断言**：我提议的「构造 `at`、看返回值随 `at` 单调递减」抓不到那个偏差——测试里构造 `at`、函数内部读本机 `Date.now()`，两边同源，永远同偏差，断言必然绿。
- **改成契约对称化（消除缺陷类别，而不是事后加守卫）**：`split` 阶段已经下发 `splitEndsAt + now`（`hub.js:1126-1139`），`hold` 阶段只给相对值 `leftMs` —— 两个阶段的时间协议**现在就不一致，这本身是债**。给 hold 补 `holdNextEndsAt`（并在视图里带 `now`），前端就永远不必自己算，也顺手把第 10 条的渲染变成「照抄分牌倒计时的写法」。0.2h。
- 渲染层用绝对时刻文案（「到 HH:MM 自动开牌」）+ 广播驱动重绘；**不要**为它加 `setInterval` 做秒级跳字（每桌一个定时器、还要管销毁，属于过度工程）。

**#11 的裁定（self 与 target 必须区别对待，`pendingNextPlayers` 不许动）**：
1. **`target ≠ self`（房主「不等他」）**：在 `dropFromNext` 里加一条下限守卫——若 `nextRoundPlayers(room).length <= MIN_PLAYERS` 且被 drop 的**不在**名单里，直接拒绝（`{ok:false, error:'这样就不够 2 人了 · 点「补 AI 队友」或拉个人进来'}`）。理由：这一下**不会让房间更接近开局**，只会把一个「等一个可能回来的人」换成「结构性卡死」，而它返回 `ok:true` 会让用户以为成功了。
2. **`target === self`（「这一把先不打」）**：**必须继续允许**。它是 v121 的必需出口（`:1394-1397` 注释写明「否则只能靠别人替他按按钮」），拒绝它等于把人锁在房间里。允许之后房间进入 `ALL_OUT_NEXT`，靠 gate 的 code + 文案 + 补 AI 借位给出路。
3. **不要给 `pendingNextPlayers` 加 `connected` 过滤**。加了就等于「他掉线所以静默落下他」，正好是 v121 立意的反面；而且 v113 A-1 特意让结算期掉线不置 `left`，就是为了让他回来时结果不被改写。正确做法是**把「他掉线了」变成可见状态**（座位卡已有离线标记，文案要跟上），而不是从名单里删掉他。

**第 9 条的补充（design review 第二轮交叉验证，两条都已读码复核成立）**：

- **9-a：房主自己请假时也零出口**，我说的「房主有出口」只对「房主点了开始下一局」成立。`canAddBot` 要求 `SETTLED && !!nextWait`（`game.js:694-696`），而 `nextWait` 只在就位态为真（唯一入口 `game.js:480` `me.wantNext`）；`#btn-add-bot` 又只长在 `#screen-room` 的 `room-actions` 里（`index.html:447`）。房主说了「这把不打」→ 落在结算页 → 那颗按钮既不在他的屏幕上、也过不了 `nextWait` 判定。
- **9-b：`joined === 0` 时结算页对非房主是一片空白**。`settleView.js:945-963`：`holdNow` 为空 + `joined === 0` → `waitTxt` 保持 `''`；`renderWaitRow` 只有房主会被 `:996-998` 补一句（而且补的是「还有朋友要来？点『等人』先别开牌」——在一个人都没上场时方向是反的）。非房主拿到空串 → `#settle-wait`（`index.html:506`）是空的 `<p>`。这条可以直接当断言：`ALL_OUT_NEXT && joined === 0` 时该节点 `textContent` 必须非空。
- **一个能省掉一半分支的事实**：`joined === 0` ⇒ 没有任何人处于就位态（就位态唯一入口是 `me.wantNext`，`game.js:480`），所以 `NEED_PLAYERS` / `ALL_OUT_NEXT` 在 `joined === 0` 时**只需要结算页那一句**，`#room-hint` 不必为它们加分支。
- **借位方案的一个硬约束（本轮新发现，属于实施风险不是文案问题）**：把 `#btn-hold`（`index.html:517`，与 `#btn-next` 同排、`.next-row`）在 `ALL_OUT_NEXT` 里改成「补 AI」，必须同时满足两点，否则会引入新缺陷：
  1. `onAddBot` 现在写死 `pressBusy($('#btn-add-bot'), …)`（`game.js:3083` `pressBusy` 按**元素**做 `dataset.busy` 去重）。借位后可见的那颗是 `#btn-hold`，如果不把元素传进去，busy 守卫会落在**看不见的** `#btn-add-bot` 上；而 `hub.addBot` **不幂等**（每次 `botSeq++` + `joinRoom`，`hub.js:907-912`）→ **连点两下就多两只 AI**。改法：`onAddBot(el)` 接受元素，默认回退 `$('#btn-add-bot')`（+0.5h）。
  2. `renderHoldBtn`（`settleView.js:1004-1014`）现在靠 `data-hold-next` 做委托。借位时必须 `removeAttribute('data-hold-next')` 与 `data-add-bot` **互斥**，否则一次点击会同时命中两个委托。
- **槽位内容应当由 gate code 决定，而不是由「哪个屏幕」决定**：这正是 9-a 的病根——权限判断被写成了「按钮长在哪个 screen 的 DOM 里」。统一成 `renderSlot(code)` 之后，`HOLD`→「等人/开牌」、`ALL_OUT_NEXT`+房主→「补 AI」、其余→「等人」；屏幕位置只是渲染结果。
- **一个必须写进文案的数值事实**：`joined === 0` 时补 1 只 AI **不够**（`nextRoundPlayers` 只认 `wantNext && !left`，`stateMachine.js:1176`，AI 计 1 人，`MIN_PLAYERS=2`），要补 2 只——所以 `joined === 0` 那支文案**不能**说「补个 AI 就能开」（design 给的那支文案正好没提补 AI，是对的，别在实施时手滑补上）。顺带：补 2 只之后房间会以「0 真人 + 2 AI」开局（读码推断，未实测），属于既有行为，不在本次修范围内。
- **收窄（design 第二轮）：借用只发生在 `code === ALL_OUT_NEXT && joined === 1`**。因为 `MIN_PLAYERS = 2` 且该 code 要求 `pending === 0`，所以 `joined ∈ {0,1}`；`joined === 0` 时这一格**藏掉且不提供补 AI**（`joined===0` 时补 1 只不够、补 2 只等于「0 真人 + 2 AI 空转」；房主要打就自己按「开始下一局」→ joined 变 1 → 这一格变「补 AI」，一步一个可解释的结果）。**据此删掉了原「`joined===0` + 补 2 只 AI」待实测项**——那条路径不再存在。另：`joined===0` 只是 `joined` 的一个取值，不新增 code。
- **第三条硬约束（design 加、我背书）：这一格的存在与文案只能由 `code` + `joined` 两个服务端事实决定**，任何本地「刚点过 / 补过一次」的记忆都是回归（v121 缺陷 2 的形态：界面一套、服务端一套）。**也不许用 `canAddBot` 的 `activePlayers < cap` 决定显隐**——容量够 ≠ 缺的人数够，那正是 9-a 的原始病根。
- **命名一致**：借用后按钮写「补 AI」（120 设计 px 放不下「补 AI 队友」），提示语里也必须写「补 AI」，否则玩家会去找一颗屏幕上不存在的按钮。
- **结算页空态裁定（已按 QA 复核改写）**：`joined === 0` 时非房主看到空串**是正确设计**（"无可奉告"，此时他面前就有一颗可用按钮，没有「点了没反应」需要解释）；而且 `settleView.js:969-974` 记着这个位置试过三处、全部撞墙，为填一个正确的空态重做排版的收益为负。**真正的缺陷在房主侧 `:996-998`「还有朋友要来？点『等人』先别开牌」——在「房间已不可能开局」时它指错方向**（照做挂起 3 分钟，到期还是开不了）。这类不能用文案断言测，改用上面那条「出口存在性不变量」。
- **`addBot` 不要加幂等键**（QA 复核，我采纳）：「连补 3 只 AI」是正当操作（`MAX_PLAYERS=5`，`hub.js:905` 只在满员拒），加幂等键会打断它。防连点只能在前端/协议层：① 借位后 `pressBusy` 必须指向**当前那颗**按钮（现在写死 `#btn-add-bot`）；② 真要防重就用**客户端生成的请求 id**（现有 `reqId` 通道），不按房间维度去重。断言写成「连调两次 → bot 数 +2 且 `botId` 不同」，**不要**断言「第二次被拒」。
- **「0 真人 + 2 AI 开局」是已知设计，不是缺陷**：`hub.js:929-936` 注释原文写明是 C-3b 之后的一条合法路径（房主不报名、只补 AI，自己在旁观）。据此我上一轮反推的「文案不能说补个 AI 就能开」**也撤回**——那句讲的是「等人」，与 AI 无关。
- 成本修正：第 9 条 3h → **3.5h**（gate + 视图分支 3h、`onAddBot(el)` 与委托互斥 0.5h；原 1h 的 `joined===0` 测试垫片因路径收窄而取消）。

## ③ 第 1 条（重启丢 grace）到底要动几处

结论：**3 处必改，2 处可选，不加新文件**。关键是**不要**因此 bump `roomsState.VERSION` —— `roomsState.js:68` 是 `if (Number(obj.v) !== VERSION) return null;`，bump 一次等于**上线那一刻把在飞的房间全丢一次**，比它想修的问题更严重（新增字段是纯增量，老读到新、新读到老都不该判废）。

| 改动点 | 具体动作 | 为什么必须 |
|---|---|---|
| `hub.js:_startGrace(roomId, playerId)` → `(roomId, playerId, delayMs)` | 加一个可传时长的参数，默认 `GRACE_MS` | 恢复时只能给**剩余**时间，给满 90 秒等于「重启一次白送 90 秒宽限」 |
| `hub.js:_restoreRooms()` | `room.players` 里 `connected === false && !p.left && p.disconnectedAt` 的人：`remain = GRACE_MS - (Date.now() - p.disconnectedAt)`；`remain <= 0` 时**立刻**走 `SM.finalizeLeave`（并处理 `deleted`），否则 `_startGrace(roomId, p.id, remain)` | 这是整个缺口的本体。`disconnectedAt` 已经在落盘的房间对象里，不需要新字段 |
| `hub.js:_restoreRooms()` | `rooms.set` 之后补一句 `this._syncDissolveTimer(room.roomId)` | 第 2 条风险的全部修复；`_syncDissolveTimer` 已按 `d.startedAt` 算剩余（`hub.js:868`），补挂天然正确 |
| （可选）`holdTimers` | 恢复时 `if (SM.holdNextOf(room)) this._armHoldTimer(room.roomId)` | **不修也能接受**：`holdNextOf` 是按 `h.at + HOLD_TTL_MS` 时间戳判定的（`stateMachine.js:1218`），过期逻辑自愈；丢的只是「到点时那一次自动开局 + 广播」，会等到下一次有人动作才推进 |
| （可选）`splitStartedAt` | 想让重启后分牌倒计时**接着算**而不是重新给满 60 秒 | 现在重启等于给所有人一次满额 60 秒（偏宽松，不害人）。要改就得把 `splitStartedAt` 落盘进房间对象（增量字段，**不要** bump VERSION） |
