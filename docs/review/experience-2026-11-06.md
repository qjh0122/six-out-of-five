# 体验 Review：一局打完 → 再开一局（v123）

- 视角：**一个不看文档的普通玩家**（不是工程师、没读过 README 的「一场对局会怎么走」）
- 范围：结算页（`settleView.js`）→ 就位态（`game.js` `renderRoom` / `renderReadyCard`）→ 开局门槛（`stateMachine.js` `canStartNext`）→ 旁听（`game.js` `renderGame` 的 `me.benched` 分支）
- 方法：只读代码与文档，不改动 `pwa/` `server/` `scripts/`；结论逐条指到函数
- 一句话结论：**这条链路现在是一条"补丁链"，不是一个"设计"**。v121 修分母、v122 补窗口、v123 补入口与文案，三次都在给同一颗主按钮加旁路。它能跑通，但对普通玩家不可解释 —— 因为**一个动作（点不点「开始下一局」）同时承担了三个语义：报名、开局、以及"不做也有代价"的默认值**。

---

## ① 三问：

### A. 对一个不看文档的普通玩家，这条链路可解释吗？

**不可解释。** 界面文案本身是够的（`settleView.js` `renderSettle` 的 `waitTxt`、`game.js` `renderRoom` 的 `hint` 都会点名"在等谁"），但玩家要操作对，**必须先理解三条内部规则**，而这三条没有任何一条在界面上说清：

1. **「按了不等于开始」**：`#btn-next` 写的是「开始下一局」，实际做的是 `wantNext()` → 置 `wantNext` + `ready`（`stateMachine.js:1293`），只是**报名**。开不开由 `canStartNext` 的四条判据（`stateMachine.js:1277`）决定。所以按完什么都不发生是"正确"的，但玩家第一反应是"按钮坏了"。
2. **「不做也有代价」**：`pendingNextPlayers`（`stateMachine.js:1185`）把所有没表态的真人算成"在等他"，`canStartNext` 第 ④ 条（`:1283`）因此不成立 → 整桌停住。**"我什么都不做"从 v121 起等于"我要求全桌等我"**。这是反直觉的默认值，全仓只有 `game.js` 一处 hint 在想解释它。
3. **「局 ≠ 把」**：结算页标题写「本局结束」、主按钮写「开始下一局」、等待文案写「已经有 N 人进入下一把」（`settleView.js:952`、`:954`）、把数块写「打几把」（`handLimitBlock`）。两个词对应两种重置：**把**分数延续、**局**分数归 0（`renderSettle` 里 `endReason === 'handLimit'` 才显示「下一把分数从 0 分重新开始」，`:914`）。玩家点完发现自己从 0 开始，只会以为分丢了。

一句判断：**v121/v122/v123 都在修"玩家没做错事却被判旁听"，但真正让玩家难受的不是被落下，而是他从来不知道自己按下的那一颗按钮是"报名"还是"开局"。** 同一屏上两套名词（把/局）、一个按钮两种语义、一个默认值反直觉 —— 这三样任意缺一个都还能活，三个叠在一起就必须读文档。

### B. 现在有几种"让某一局少一个人 / 多一个人"的机制？是否过载？

**八种，其中五种共用同一批内部字段，玩家分不清是必然的。** 清点如下（全在 `stateMachine.js`）：

| 玩家看到的 | 真实动作 | 落到哪个字段 |
|---|---|---|
| 什么都不点 | 被算进 `pendingNextPlayers` → 全桌等 | `!wantNext` |
| 「不等他」（别人按） | `dropFromNext(room, actor, target)` `:1402` | `target.outNext = true` |
| 「这把不打」（自己按） | `dropFromNext(room, actor, actor)` | `actor.outNext = true` |
| 「等人」（房主） | `setHoldNext` `:1228` | `room.holdNext`（3 分钟 TTL） |
| 「补 AI 队友」 | 填一个空位（`game.js:691`） | `players.push` |
| 打牌中才进房 | `joinRoom` 放行但 `benched = true`（v122） | `benched` |
| 结算期才进房 | `joinRoom` 直接置 `wantNext + ready`（`stateMachine.js:357`） | `wantNext`（直接进下一把） |
| 离开房间 / 弃局 | `left = true`，分数冻结 | `left` |

**已经过载了，但不是数量过载，是"名词过载"**：

- **三颗按钮做同一件事**（不点 / 不等他 / 这把不打 → 同一个 "这一把没你"），却有三个完全不像的名字，分散在两屏（结算页 vs 就位态）。玩家要理解"我被别人不等了"和"我自己说不打"后果完全一样，只能靠踩过一遍。
- **"旁听"是一个状态，却被四种原因共用**：没表态被跳过、自己请假、打牌中才进来、结算期才进来。`renderGame` 的 `me.benched` 分支（`game.js:980`）只有一句「你不在这一局」，**不写原因** —— 而这四种原因下玩家该做的事完全不同（前两种等这一把打完就行，后两种是正常的加入路径）。
- **房主手里同时有「等人」和「不等他」**，两个词只差一个字、位置隔了两屏、语义相反（一个是"多留一个人"、一个是"少一个人"）。`renderHoldBtn`（`settleView.js:1004`）把「等人 / 开牌」做成同一颗按钮切换，`skipWaitHtml`（`game.js:916`）把「不等 X」做成信息卡里的一颗按钮 —— 玩家在结算页看到「等人」，在就位态看到「不等 X」，很难相信这是两件不同的事。

结论：**机制不是太多，是缺一个统一的名词。** 桌上真实只有两件事：「这一把谁上场」和「什么时候开」。现在这两件事被做成了八个动作。

见 ②。共同特征：**都能跑通、都不是 bug，但都让玩家多按一次、多猜一次、或者事后才明白。**

## ② 体验断点表

| 现象 | 谁会撞上 | 代价 | 建议方向 |
|---|---|---|---|
| **① 有人按「这把不打」把在场人数压到 1 人，整桌静默卡死，而且界面在"等一个已经表过态的人"。** 链路：`onSitOut`（`game.js:3448`）→ `dropFromNext` 置 `outNext`（`stateMachine.js:1414`）→ `pendingNextPlayers` 排除 `outNext`（`:1188`）→ ④ 通过，但 `canStartNext` 第 ② 条 `list.length < MIN_PLAYERS` 不通过（`:1281`）→ `renderRoom` 落进 `act.length < MIN_PLAYERS` 分支，写「还差 1 人才能开下一局，**等其他人点「开始下一局」**」（`game.js:680`）→ 而那个人已经明确说不打了。同屏 `staleNextPlayers` 返回空（`:909`），所以连「不等他」都没有。唯一出口是房主的「补 AI 队友」（`game.js:691`），非房主没有任何出口 | 2 人好友局（最常见的形态）里，一个人想歇一把就够了。没有房主身份的玩家直接无解 | 整桌以为在等一个不存在的人，等到有人退房为止；这是**纯静默**的，全程没有任何错误提示 | 人数不足时把它当成一个显式的"这一把开不了"状态给出（谁请假了 / 剩下几个人 / 唯一能做的两件事），别复用"等某人"的文案 |

| **④ 「这把不打」按下去，界面没有任何持续反馈。** `onSitOut` 只 `flash` 一句（`game.js:3455`），`settleView.js` 全文**不读 `outNext`**（grep 无命中），`settleListEl` 只标 `benched` / `left`（`:759`） | 第一次按这颗按钮的人，以及在误触之后想确认的人 | 屏幕毫无变化 → 怀疑没生效 → 再按一次（`dropFromNext` 幂等，`stateMachine.js:1411`，什么都不会发生）→ 更怀疑。而这是一个**锁定状态**：这一把只能看着 | 表态要留下痕迹（按钮变成"这一把不打 ✓／点这里回来"），幂等的静默对玩家来说是"没反应" |
| **⑤ 「等人」和「开牌」是同一颗按钮的两个语义，而且挂起 3 分钟会**自己**到期开牌，界面没有倒计时。** `renderHoldBtn`（`settleView.js:1004`）按 `holdNow` 把同一颗按钮的文字和 `data-hold-next` 在 `1/0` 之间反转；`HOLD_TTL_MS = 3 分钟`（`stateMachine.js:1209`）到点由 `hub._armHoldTimer` 自动放行；剩余时间**服务端已经下发了**（`server/hub.js:637` 返回 `leftMs`，`stateMachine.js:1222` `holdNextLeftMs`），但**前端零调用点**（grep 确认） | 房主（尤其手机上手忙脚乱的那位），以及所有被挂起挡住的人 | ① 想延长时间的人再点一下 = 直接放行开牌（语义反转，无二次确认，而它是全场唯一能让桌子停下的动作）；② 挂了 3 分钟后牌自己发了，房主会坚称"我明明点了等人" | 一个"让全桌停住"的动作必须和"放行"分开，并且要把剩余时间显示出来（数据已经在手上了） |

| **⑦ 旁听卡不说原因，而三种原因的出路完全不同；其中一种的承诺是做不到的。** `renderGame` 的 `me.benched` 分支（`game.js:996-1029`）只有「旁听中 / 你不在这一局 / 打完会回到结算页」，不区分"被不等""自己请假""打牌中才进房"；而 `onSitOut` 的 toast 明确承诺「**随时**点「开始下一局」回来」（`game.js:3455`）—— 但旁听期间这一屏只有一颗「离开房间」（`:1021`），「开始下一局」要等这一把打完 | 自己请假的人（他信了那句"随时"） | 他一次次找那颗按钮，找不到；或者以为被踢了。旁听是这条链路上**唯一**的"少一个人"的后果，而它现在长得像一个惩罚界面 | 旁听卡要说清"你怎么进来的 + 什么时候能回去"，并且不要承诺界面上不存在的按钮 |
| **⑧ 术语混用：同一件事三个词。** 「本局结束」（`index.html:504`）/「开始下一局」（`:516`）/「已经有 N 人进入下一把」（`settleView.js:952`、`:954`）/「打几把」（`handLimitBlock` `:679`）/「准备下一局」（`renderReadyCard` `game.js:877`） | 所有玩家，尤其第一次打满把数的那一局 | 「把」和「局」在 README 里是两个层级（一把 = 两轮，打满把数 = 本局结束），而分数**只在一个层级归零**。玩家要理解"为什么点完分数从 0 开始"，必须先猜到这两个词不是同一件事 | 名词收敛到一个层级；如果两个层级都必须在界面上出现，就让它们各自带上"分数会/不会归零" |

## ③ 如果只改一处

**改结算页的主按钮区：把「开始下一局」+「这把不打」做成并排、同级、二选一的"表态"，而不是"一颗报名按钮 + 一颗藏在第三排的灰色小按钮"。**

理由：上面八条里有五条（①②④⑤⑦）的根都是同一件事 —— 玩家不知道自己此刻在做"表态"，以及"不表态"会锁住全桌。把它变成显式的二选一，普通玩家不需要理解 `canStartNext`、不需要读文档、也不需要分辨「不等他 / 这把不打 / 不点」这三颗做同一件事的按钮。这是文案 + 布局层面的改动，**不动任何规则**（`canStartNext` 四条判据一条都不用改）。

## ④ 三态文案（与 tech-architect 交叉验证后补，供 `nextRoundGate` 1:1 落地）

tech-architect 的结论我认同：断点 ① 的真正病根不是文案，而是**`canStartNext` 只回答"能不能开"、不回答"为什么不能开"**，`renderRoom`（`game.js:670-689`）只能从三个派生数组里反推原因，第 ④ 个否决条件（`outNext`）加进来就漏了。所以下面是**按 reason code 给的文案**，不是按现有分支打的补丁。

### 先补两个新发现（都是同一个病：视图渲染的状态少于规则允许的状态）

- **新发现 A：房主自己说了「这把不打」时，「补 AI 队友」根本不在他眼前。** `canAddBot` 要求 `SETTLED && nextWait`（`game.js:694-696`），而房主说了不打 → `wantNext=false` → 他在**结算页**不在就位态；`#btn-add-bot` 又只存在于 `#screen-room` 的 `.room-actions` 里（`index.html:447`）。于是"最该按补 AI 的那个人"按不到。这是断点 ① 的**另一半**，也是同一类的第 5 例。
- **新发现 B：`ALL_OUT_NEXT` 在结算页上是一片空白（对非房主）。** `settleView.js:945-963`：`holdNow` 为空、`joined === 0` → `waitTxt = ''` → 非房主拿到空字符串，`#settle-wait` 是一行空的 `<p>`；房主反而拿到 `'还有朋友要来？点「等人」先别开牌'`（`:996-998`）—— 在一个人都没上场的时候建议他"等人"，是错的方向。**这一条可以直接当断言用**：`ALL_OUT_NEXT && joined === 0` 时 `#settle-wait.textContent` 必须非空。

### 三态文案（`canStartNext` 的四个否决条件 → 一个枚举）

判定顺序即优先级，**视图分支必须与枚举等值**（tech-architect 建议的那条守卫测试）：

| code | 成立条件 | 一句话本质 |
|---|---|---|
| `HOLD` | `holdNextOf(room)` 为真 | 房主说了先别开 |
| `NEED_PLAYERS` | `joined < MIN_PLAYERS` 且 `pending > 0` | 人不够，但还有人没表态 |
| `WAITING_OTHERS` | `joined >= MIN_PLAYERS` 且 `pending > 0` | 人够，在等某个人表态 |
| `ALL_OUT_NEXT` | `joined < MIN_PLAYERS` 且 `pending === 0` | **没人会再表态了，这一把就是凑不成** |
| `READY` | 其余 | 全员就位 |

**关键实现提示（能省掉一半分支）**：`joined === 0` 时**没有任何人在就位态** —— 就位态的唯一入口是 `me.wantNext`（`game.js:480`），`joined === 0` 时无人满足。所以 `NEED_PLAYERS` 与 `ALL_OUT_NEXT` 的 `joined === 0` 情形**只需要结算页那一句话**，`#room-hint` 不用为它们写。

#### `ALL_OUT_NEXT`

**先收窄一个事实：`ALL_OUT_NEXT` 下 `joined` 只可能是 0 或 1**（`MIN_PLAYERS = 2`，且 `pending === 0`）。两种情形下一步动作完全不同，所以这一格内容也完全不同：

| 情形 | 结算页 `#settle-wait` | 就位态 `#room-hint` | 这一格（`#btn-hold`） |
|---|---|---|---|
| `joined === 0`（所有人都说了不打） | `这一把没人上场 · 想打就点「开始下一局」`（所有人同一句，不分房主） | 不出现（`joined === 0` ⇒ 无人在就位态） | **藏起来** |
| `joined === 1`，房主本人就是那个等的人 | `这一把开不了：只有 1 人 · 你补个 AI 就能开` | `这一把凑不成局 · 点「补 AI」就能开` | 「补 AI」 |
| `joined === 1`，房主请假（不在场等） | `这一把开不了：只有 1 人 · 补个 AI 陪他打` | 在场那位的 `#room-hint`：`这一把凑不成局 · 等房主补 AI，或拉个人进来` | 「补 AI」 |
| `joined === 1`，非房主 | `这一把开不了：只有 1 人 · 等房主补 AI` | 同上 | 藏（他没有这颗） |

- **`joined === 0` 时这一格必须藏掉，且不许提供补 AI。** 理由不是"按钮没地方放"：`joined === 0` ⇒ **房里每一个真人都已说了不打**（`pending === 0` + `MIN_PLAYERS = 2`），此时补 AI 要补 2 只，结果是「0 个真人 + 2 只 AI 在打，全部真人旁听」—— 一局空转，没人想看。而房主想要那一把的方法就在旁边：按「开始下一局」（`joined` 变 1），于是这一格立刻变成「补 AI」，再补 1 只刚好够 —— **两步都可以解释，没有一步是"点了没反应"**。这条同时消灭了 tech-architect 那个待实测项（`joined === 0` + 补 2 只 AI），路径根本不存在了。
- **不要写"等"字**：`pending` 为空，这里没有任何人在被等。写"等某人"就是把责任推给一个已经表态的人（现状 `game.js:680` 正是这么错的）。
- **文案里的按钮名必须和借用后的按钮一致**：借用后这颗写「补 AI」（不是「补 AI 队友」——那是房间页那颗的名字，120 设计 px 放不下四个字）。所以提示语里也一律写「补 AI」，别让玩家去找一颗不存在的「补 AI 队友」。
- **视觉**：`#room-hint` / `#settle-wait` 各加一个 `is-block` 类（warn 色文字，不加图标、不新增高度）。**不要**套 `hint.classList.add('ready')` 的绿色（`game.js:688`）—— 绿色在这套界面里的含义是"马上开始"，这里恰好相反。
- **不许做**：① 不给这个状态加"卡住 N 分钟自动开"（人数不够，等到天亮也开不了，只是把死状态换成定时器）；② 不自动复位 `outNext`（那是替人做决定，与 v121 的立场相反）。

#### 借位交互规格（`#btn-hold` 借用成「补 AI」）

**只有一种情况借用**：`code === ALL_OUT_NEXT && joined === 1`。其余一切情况 `renderHoldBtn` 原样走 v122 逻辑（`等人` / `开牌`）。判据只有 `code` + `joined` 两个服务端事实，**不引入任何本地状态** —— 不用"刚点过"、不用"补过一次"这类记忆，那正是 v121 缺陷 2 的形态（界面说一套、服务端认另一套）。

| 问题 | 结论 |
|---|---|
| 1. 请求在途的中间态 | `pressBusy` 会把 `textContent` 覆盖成 label，**复用房间页那颗已有的 label `添加中…`**。理由：同一个动作在全站只有一个名字；宽度已由同一颗按钮上的「挂起中…」证明放得下（v123 就是在这个宽度上定的字号） |
| 2. 补满之后这颗棋子 | **不需要"消失"规则**，需要的是"归还"：补 1 只 AI → `joined` 变 2 → 离开 `ALL_OUT_NEXT` → 这一格自动回到 v122 原语义（`等人`/`开牌`）；而 `joined ≥ 2` + `pending === 0` ⇒ `READY` ⇒ 服务端当场开牌（`hub.joinRoom` 末尾的 `_maybeAutoStart`，v122 补的），这一屏直接消失，玩家看到的是发牌。**不要**用 `canAddBot` 的 `activePlayers < cap` 去决定显隐 —— 容量够不代表"缺的人数够"，那正是断点 ① 的原始病根 |
| 3. 优先级（请假房主） | **一律「补 AI」，不做"等人优先"分支。** 因为在 `ALL_OUT_NEXT` 下「等人」是一个**点了没有可观察结果**的动作（gate 第 ② 条本就不成立，挂起只是多一道空门闩），而这一格的原则是"只放此刻真能推进事情的动作"（断点 ③ 的结论）。请假房主想让人进来这件事，由文案承接（`补个 AI 陪他打`），不靠一颗无效按钮 |
| 4. 非房主看到的是什么 | **纯文本，落在原有节点上，不新增槽位**：结算页 `#settle-wait`（`index.html:506`）、就位态 `#room-hint`（`#screen-room` 那行，`game.js:664`）。它和「新发现 B 的修复」是**同一处**，不是两句抢一个节点 —— 一个 code 决定这个节点写哪一句，B 的修法就是把这个节点在 `joined === 0` 时不再留空 |

**必须一并做掉的两条硬约束（tech-architect 提的，我都背书）**：
- `onAddBot(el)` 接元素、默认回退 `$('#btn-add-bot')` —— `pressBusy`（`game.js:3083`）按元素去重，写死元素会让 busy 守卫落在看不见的那颗上，而 `hub.addBot`（`hub.js:907-912`）不幂等 → 连点两只 AI。
- `data-hold-next` 与 `data-add-bot` 必须互斥（借用时 `removeAttribute('data-hold-next')`）。否则一次点击命中两个委托，而这个状态下点「开牌」无副作用 → **不会报错，只表现为"补完 AI 之后按钮行为随机"**，比原 bug 更难查。
- 补充断言建议：`code === ALL_OUT_NEXT && joined === 1` 时，`#btn-hold.textContent === '补 AI'` 且 `#btn-hold` 上没有 `data-hold-next` 属性；`joined === 0` 时 `#btn-hold` 是 `hidden`。

#### `NEED_PLAYERS`

`joined > 0` 这一支**直接复用 `WAITING_OTHERS` 文案**（现有「已经有 {joined} 人进入下一把 · 还在等 X」在 `joined >= 1` 时是准确的，别动）。只有 `joined === 0` 需要新句子：

| 位置 | 文案 | 说明 |
|---|---|---|
| 结算页 `#settle-wait` | `还没人报名 · 点「开始下一局」，2 人都点才发牌` | 现状这里对非房主是**空行**，对房主是「还有朋友要来？点「等人」」（`settleView.js:996-998`）—— 两个人互相等对方点，就是因为两边都没有这句话 |

#### `WAITING_OTHERS`

**一个字都不改。** 现有文案（`game.js:677` 的「等 X 点「开始下一局」…」、`settleView.js:960-961` 的「还在等你 / 还在等 X」）」已经做对了两件事：说清在等谁、且把责任放在该动的那个人身上。

### 规则决策：`ALL_OUT_NEXT` 要不要把「补 AI」放开给非房主 —— **不放开**

三条理由，按权重：

1. **补 AI 不是"改我自己的状态"，是"给整桌发一手牌"**：它会进 `handHadBot`（`stateMachine.js:1488`）、影响这一把所有人的输赢与成就口径。这属于桌上规则，需要一个人负责 —— 与 v122「等人」只给房主是同一条先例（`stateMachine.js:1236`：只有房主能决定等不等）。
2. **技术上没有"没人能按"的风险**：`ensureLiveOwner` 在 `leaveRoom`（`stateMachine.js:500`）与 `startNextRound`（`:1495`）都会转移所有权，房主永远在场，所以不存在"只能靠开放权限来救"的情形。
3. **非房主的痛点不是"我不能按"，是"我不知道球在谁手上"**。第 3 条用**文案**解决（上面「等房主补 AI」），不用改权限解决。一人开发的项目，权限一旦多点开花，后面每个动作都要重新回答一遍"谁能按"。

**但必须修的是"房主按不到"（新发现 A）**。位置从哪来 —— 不新增任何高度：`ALL_OUT_NEXT` 状态下「等人」这个动作**毫无意义**（本就开不了牌，等谁都没用），所以把那颗棋子**借用**成「补 AI」：`renderHoldBtn`（`settleView.js:1004`）在 `ALL_OUT_NEXT` 分支里画成「补 AI」+ `data-add-bot`，委托回到 `onAddBot`。这是唯一一处"不加行、不挤主按钮"的可用位置，也和 v122/v123 反复撞到的那堵墙（结算页 390×844 垂直预算已满）一致。
