## 0. 结论摘要

| 维度 | 结论 | 最严重的问题 |
|---|---|---|
| 1 功能逻辑 | 骨架与主流规则一致，**有 2 处会改变输赢的缺陷** | 飘三叶顺子/同花顺平局按「入房顺序」判赢 |
| 2 UI/交互 | 完成度高（14 个弹窗、无障碍、断网提示齐备），**2 处体验断点** | 结算期重进房间把分数重置成 20，结算页显示错账 |
| 3 PWA | manifest / SW / 离线兜底都在，**3 处短板** | `/sw.js` 走 1 小时 HTTP 缓存，更新可能延迟 |
| 4 前端代码 | 分层清楚，**但单文件 4990 行** | `bindEvents` 422 行、`resize` 258 行；47 处空 catch |
| 5 存储与账号 | scrypt + HMAC 令牌 + 版本号吊销，做得比同规模项目好 | 无找回、昵称不唯一、改密码接口不限流 |
| 6 兼容 | iOS/安卓现代浏览器没问题，**旧内核有系统性风险** | flex `gap` 用了 104 处（Chromium<84 / Safari<14.1 全部失效） |
| 7 性能 | 首屏 ~208KB(gzip) / 13 请求，牌面已缓存、节点已复用 | 无 preload，首字节线上冷启动 3.2s |

### 必须改（P0）

1. **飘三叶「顺子 / 同花顺」同点数时没有比花色**，`comparePiaoSanYeResolved` 直接返回 0，
   而 `settleGroup` 只按 `> 0` 换赢家 → **先按下「准备」/先进房的人白赢一分**。
   实测：`4♦5♦6♦` vs `4♠5♠6♠` → `compare = 0`，`settleGroup` winner = 先入房者。
2. **结算期重新进房把分数重置成 20**。`StateMachine.joinRoom()` 对「已 joined 且 left」的人也执行
   `p.score = INITIAL_SCORE`。实测：中途离开时 7 分 → 结算期点进来变 20 分，
   结算页显示 20，而档案里记的是 `7-20 = -13`。玩家看到的账和排行榜的账对不上。

### 应该改（P1）

3. **AI 不受「能不爆就不许爆」约束**：20000 手随机样本里，AI 有 300 手把十点半排成爆点，
   其中 **202 手（1.0%）本可不爆**。人被弹窗挡住、AI 照样送 → AI 白输一组，且规则双标。
4. **`/sw.js` 命中通用静态缓存头 `public, max-age=3600`** → Safari 会把 SW 脚本一起缓存，
   发版后最多 1 小时才拿到新 SW（Chrome 对主脚本默认忽略 HTTP 缓存，Safari 不一定）。
5. **没有任何安装引导**：没有 `beforeinstallprompt` 处理，iOS 也没有「添加到主屏幕」提示 ——
   用户根本不知道这东西能装成 App。
6. **改密码接口没有失败限流**：`/api/auth/password` 直接 `profiles.login()` 验旧密码，
   但没走 `loginBlocked/noteLoginFail`（删号那条已经在走）。拿到令牌就能无限猜旧密码。
7. **昵称不唯一**：`createAccount` 只保证账号名唯一。两个人可以用同一个昵称上排行榜，
   而榜单只显示昵称 → 可冒充。
8. **没有找回密码**：只有管理员 `/api/admin/password` 能重置。注册页没写这一句，
   玩家忘密码会以为号废了。

## 1. 功能逻辑

### 1.1 【P0】飘三叶顺子/同花顺：同点数不平花色，按入房顺序判赢

**现状**
```js
// engine.js comparePiaoSanYeResolved
case PSY_TYPE.STRAIGHT_FLUSH:
case PSY_TYPE.STRAIGHT:
  return ta.high < tb.high ? -1 : (ta.high > tb.high ? 1 : 0);   // ← 同 high 直接 0
```
而 `settleGroup` 里：
```js
var winner = candidates[0];
for (...) if (comp(candidates[i].hand, winner.hand) > 0) winner = candidates[i];
```
`candidates` 的顺序 = `room.players` 的顺序 = 入房顺序。于是 **`0` 等于「先来的赢」**。

**影响**：`4♦5♦6♦` 输给 `4♠5♠6♠` 的场景里，赢家反而是方片那手。同花顺、混花顺子都会中招；
一局 8 个人里出现两手同点顺子的概率不高但绝不罕见，而且**输的人完全无从理解**（牌面看起来一样大）。
另外 `同花`/`散牌`/`对子` 都做了完整比较，只有这两种牌型漏了 —— 属于「改规则时漏了一处」的典型。

**建议**
1. `comparePiaoSanYeResolved`：`high` 相同时回落 `compareHighCards(a, b)`（会按花色逐张比），
   保持与同花/散牌一致的口径；`straightInfo` 里 A23 的 high=3 保持不变。
2. 顺手在 `settleGroup` 里对 `comp === 0` 的**真平局**做一次显式处理（平分或按花色），
   而不是让「数组顺序」当裁判 —— 现在这条隐式规则没有任何一行代码或文档在说它。
3. 补测试：`engine.test.js` 加一组「同花顺同点不同花」「顺子同点不同花」，
   并在 `settle()` 断言赢家是花色大的那手。

### 1.2 【P0】结算期重新进入，分数被重置为 20

**现状**（`stateMachine.js` `joinRoom`）
```js
var p = existing || player;      // existing 可能是 left 的人
...
p.score = CONFIG.INITIAL_SCORE;  // ← 无条件重置
```
**影响**：中途离开（`left=true`）的人，在处理结算页时点回房间，分数变 20。
`_persistSettlement` 早已按冻结分数落库，所以**档案是对的、界面是错的**；
玩家看到「我明明输了 13 分，结算页写 20」，第一反应是「算错了」。

**建议**
```js
var rejoiningSettled = settling && !!existing;    // 结算期认回旧座位
if (!rejoiningSettled) p.score = CONFIG.INITIAL_SCORE;
else p.joinedLate = true;                          // 不打上一局的弹窗，但分数保留
```
并给这条加断言（`server/test/resume.test.js` 或 `pwa/test` 里都行）。

### 1.3 【P1】AI 与人类规则不一致：AI 会排出「本可不爆」的十点半

**现状**：人类点「提交分组」会被 `tenHalfAdvice(kind:'bust')` 拦住（第 35 章），
AI 走的是 `AI.decideRound1` 的纯期望值枚举，`tenHalfEV` 给爆点 0 分，但**只要另外两组收益更高就会选爆**。

**实测**（20000 手随机牌）：
```
AI 排成爆点十点半 300 手，其中 202 手整手存在不爆的十点半组合（1.01%）
```

**影响**：AI 白送一组 + 玩家看到「AI 能爆我不能爆」，规则感被破坏。

**建议**：`decideRound1` 的枚举里加一级约束 —— 先筛出 `tenHalfPair(tenhalf).bust === false`
的组合，只有全部组合都爆时才回到现在的打分逻辑。只改 3 行，且与 `tenHalfAdvice` 同一口径：
```js
// 收集阶段分成两组：candidates（不爆）与 fallback（爆）
// 先在不爆里取最优，没有才用 fallback
```

### 1.4 【P2】结算相关的数据卫生

- `douNiuInfoResolved` 的「五花牛」判定**不校验张数 = 5**：任一手牌全是 J/Q/K 就返回 `type:10`。
  正常流程进不来（`submitGroups` 校验 5 张），但这是一条「靠上游保证」的隐式契约。
  建议加 `if (hand.length === 5 && allCourt)`。
- `submitGroups` 只校验**本轮参与**的组（第 2 轮只看 `single/douniu`），
  却把 `tenhalf/piaosanye` 也原样写进 `p.groups`。多带的牌既不在校验范围、也不会被结算读取 ——
  不构成作弊，但会让档案里出现「手里没有的牌」。建议第 2 轮把这两组强制置空。
- 幂等键 `roomId#handSeq` 在**内存里**且只留 40 条。房间号 6 位、会回收，
  **同一房间号 + 同一场次号**在 40 条窗口内撞上就会把整场战绩静默丢掉（代码注释里已承认这点）。
  建议键里带上 `endedAt`（`roomId#handSeq#endedAt`），成本为零。

### 1.5 已核对无误的部分（不必再动）

- 6 张两轮：`1+2+3` / `1+5`，`ROUND_GROUPS` 与 `GROUP_COUNT` 一致；
  `submitGroups` 校验「每组张数、总数 6、无重复、必须来自手牌」四项齐全。
- 大王万能：十点半枚举 52 张取最优（含当 10）；飘三叶枚举 52 张取最大牌型；
  斗牛正确处理「三张真牌自成十 → 王补两张 = 牛牛」与「王去凑十」两条路，且**王不参与比大小**。
- 计分：单张 1/人；十点半 10.5 收 2、否则 1；飘三叶 `1 + 场上豹子数`；斗牛 4/3/2/1 + 没牛额外 5。
  每组严格零和，`anyScoreChange` 只在真动分时置真，`voided` 判据正确。
- 弃权/弃局：弃权者留在房间、照付赢家；弃局者分数冻结并按冻结值落库（防「输定了就退房」）。
- 十点半「双爆比谁爆得少」与解析口径一致（`tenHalfResolvedBetter` / `compareTenHalf` 已对齐）。

## 2. UI / 交互

### 2.1 现状：做得比预期好

- 14 个弹窗统一走 `showModalEl/hideModalEl` + `pushModalState`，Esc 可关，`modal-open` 时锁滚动，
  `modal-a11y.test.js` 有 113 条断言盯着（层级、焦点、aria）。
- 所有异步按钮都过 `pressBusy()`（防连点 + 按钮变「提交中…」），`blockedOffline()` 统一拦断网操作。
- 断网有顶部横幅 + 重连提示 + 「掉线时间过长已退出本局」三级文案；错误上报有节流。
- 横竖屏两套版式，安全区、灵动岛、底部色带都做过实测修正。

### 2.2 【P1】首屏对未登录用户会「闪一下首页再跳登录」

**现状**：`<section id="screen-home" class="screen">` 没有 `hidden`，`screen-auth` 反而带 `hidden`。
`showScreen('screen-auth')` 要等 12 个 `defer` 脚本下载执行完（弱网 1-2s）才发生。
**影响**：新玩家先看到「创建房间 / 加入房间」，再被弹到登录页，像被踢了一次。
**建议**：把 `screen-auth` 设为初始可见（`screen-home` 加 `hidden`），
由 `init()` 决定去留；或在 `#stage` 上放一个纯 CSS 的启动占位，JS 就绪后再撤。

### 2.3 【P2】键盘弹出会把整页「压扁」

**现状**：`#viewport` 是 `fixed; inset:0`，安卓键盘弹出时布局视口变小 → `ResizeObserver` 触发 `resize()` →
`stageH = vh / scale` 掉到 1500 设计像素以下 → `stage.classList.toggle('compact-v', stageH < 1500)` 生效。
**影响**：在登录页/改名弹窗里输入时，字号与间距整体缩一档，收起键盘又弹回来。
**建议**：`resize()` 里加一句「有输入框聚焦时不切换 `compact-v`」，或键盘态直接跳过 `stageH` 相关的类切换。

### 2.4 【P2】其他

- `stageCoords()` 里 `new DOMMatrix()` **没有 try**（同文件的 `stageScale()` 有）。
  极老 WebView 上点牌会抛异常，表现是「点了没反应」。建议包一层，失败时退化成无动画落牌。
- 空 catch 共 47 处（`game.js` 23 / `roomStore.js` 24）。多数是「存储不可用不影响主流程」这类合理忽略，
  但排障时完全无声。建议统一改成 `catch (e) { debugLog('xxx', e); }`，只在 `?diag=1` 时打印。
- 战绩页/排行榜已有 loading 与失败重试入口，这块不用动。

## 3. PWA

### 3.1 现状

- manifest：`name/short_name/start_url/scope/display:standalone/theme_color/background_color` 齐全，
  三种图标（192 / 512 / maskable / apple-touch 180×180）都在。
- SW：导航 network-first + 3s 超时兜底、JS/CSS network-first + 2s、图标/图片/音频 cache-first、
  `/ws` 与 `/api` 不拦截；`PRECACHE` 27 条，失败会留下 `__precacheReport`；
  `skipWaiting + clients.claim`；403 有专门的「链接已失效 + 自愈」页。
- 版本一致性：`index.html` 里的 `checkVersionConsistency()` 拉 `no-store` 的 `/index.html` 比版本，
  不一致就 `reloadWhenIdle()`（正在分牌时延后，避免丢草稿）。

### 3.2 【P1】`/sw.js` 用了普通静态缓存头

**现状**：`sendFile()` 对所有非 HTML 统一 `Cache-Control: public, max-age=3600`，`/sw.js` 没有特判。
**影响**：Safari 会按 HTTP 缓存取 SW 脚本 → 发版后最多 1 小时才装上新的 SW，
期间离线兜底用的还是旧 `PRECACHE`。Chrome 对主 SW 脚本默认忽略 HTTP 缓存，所以这个坑只在 iOS 上出现。
**建议**：
```js
if (filePath.endsWith('/sw.js')) headers['Cache-Control'] = 'no-cache, no-store, must-revalidate';
```

### 3.3 【P1】没有任何安装引导

**现状**：全仓搜不到 `beforeinstallprompt`，也没有 iOS 的「分享 → 添加到主屏幕」提示。
**影响**：安卓只有浏览器菜单里那个不起眼的入口；iOS 更是完全没有提示。PWA 的核心价值（图标 + 全屏）
大部分玩家根本没享受到，而 `--pt-h` 那一整套 standalone 修正也就白做了。
**建议**
- Android：`window.addEventListener('beforeinstallprompt', e => { e.preventDefault(); installEvt = e; })`，
  在首页右上角放一个「装到桌面」按钮，点了 `installEvt.prompt()`；已安装（`display-mode: standalone`）时隐藏。
- iOS：UA 判断 `iPhone && !navigator.standalone`，首访显示一次性提示条「分享 → 添加到主屏幕」，`localStorage` 记住已读。

### 3.4 【P2】图标与 manifest 细节

- `purpose: "maskable"` 复用了 `icon-512.png`。这张图**带 5% 的金色圆角边框**，
  被 Android 裁成圆形后四个角的描边会被切掉（主体内容在安全区内，不会丢信息，但观感毛边）。
  建议单独出一张「满底 + 主体占 80% 内切圆」的 maskable 图。
- manifest 缺 `id`（Android 用 `start_url` 当 id，分享码变化时理论上可能被当成两个应用）、
  缺 `screenshots`（影响安卓安装弹窗的富展示）。
- SW 的 cache-first 分支用 `caches.match(req)` **没带 `ignoreSearch`**，
  而 `PRECACHE` 里的条目是带 `?sharecode=` 存进去的：分享码一换，同一资源就会在缓存里存第二份。
  建议这一支也统一 `{ ignoreSearch: true }`。

### 3.5 离线能力边界（要说清）

断网可以打开页面、看首页/战绩页，但**联机对局必须在线**（`/ws` 不拦截），这是合理设计；
`blockedOffline()` 会拦掉操作并提示，不会出现「点了没反应」。

## 4. 前端代码

### 4.1 【P1】`game.js` 4990 行 / 234KB（gzip 86KB），是最大的维护风险

**现状**：一个 IIFE 里塞了渲染、手势、弹窗、战绩、排行、分享图、音频、视口、认证 UI 全部逻辑；
`bindEvents()` 单函数 **422 行**，`resize()` **258 行**，`renderRoom()` 149 行。
**影响**：改一处要在 5000 行里找上下文；`bindEvents` 这种巨型注册函数最容易出「重复绑定 / 漏绑」。
**建议**（不必一次做完，按收益排序）：
1. 先把 `bindEvents` 按屏拆成 `bindAuth/bindHome/bindRoom/bindGame/bindRecords/bindRank`，
   每个 ≤ 80 行，主函数只做调用。
2. 把「分享图绘制」(`drawShareCard` 97 行)、「视口/缩放」(`resize` + 相关 400 行) 抽成
   `shareCard.js` / `viewport.js` —— 这两块与业务状态耦合最低，抽出来风险最小。
3. 拆分时保持「无构建工具、全局变量挂载」的现状，别为了模块化引入 bundler（会破坏 SW 的
   network-first 策略和现有探针）。

### 4.2 【P2】双份统计实现

服务端 `profile.js`（权威）与本机 `records.js`（离线兜底）各实现了一套
`场次/胜/负/平/胜率/连胜/最长连胜/最佳单场`。两边现在口径一致（有测试对齐），
但这是**同一个业务规则的两个实现**，改规则必须改两处。建议在 `records.js` 顶部写死一条注释
指向 `profile.js` 的对应函数，并在 `pwa/test/records-ai.test.js` 里加一条「与 server 同口径」的对照断言。

### 4.3 命名与结构（小）

- 大量 `var` + ES5 写法是**有意为之**（兼容老 WebView），不是遗漏，别建议改成 `const/let`。
- `state` 这个全局对象字段偏多（`resultSeqShown/absorbSig/settleCelebrated/recordKey/justDealt/reviseRound/activeGroup/...`），
  建议按「本次打开 / 当前房间 / 当前分牌」分组成三个子对象，减少跨屏污染。
- `el()` / `esc()` / `colorFor()` / `short()` 这些工具在 `game.js` 和 `records.js` 各有一份，
  可以合并，但收益不大。

### 4.4 潜在崩溃点（都是 P2）

| 位置 | 场景 | 后果 |
|---|---|---|
| `stageCoords` 的 `new DOMMatrix` | 老 WebView | 抛异常 → 点牌无反应 |
| `esc(g.winnerNickname)` 传 `undefined` | 异常结果对象 | 界面出现字面量 `undefined` |
| `p.nickname + ...`（结算行） | 昵称为 null | 显示 `null` |
| `state.myId.slice(-4)` | myId 为空串 | 退化成「玩家」，不崩 |
| `$('#rp-ai-note-text').textContent` | 已在 `if (aiNote)` 内 | 安全 |

## 5. 存储与账号

### 5.1 做得对的地方（先说清楚，避免误改）

- 密码：`scrypt(N=16384, r=8, p=1)` + 16B 随机 salt，**异步**跑在 libuv 线程池（不再冻结事件循环），
  比较走 `timingSafeEqual`。
- 令牌：HMAC-SHA256 自签（`base64url(json).base64url(sig)`），90 天 + 半程滑动续期；
  payload 带 `tv`（令牌版本），改密码/停用 → `tv+1` → 旧令牌当场失效；HTTP 与 WS 两条链路都查 `tv`。
- 密钥：`AUTH_SECRET` 落在**数据目录**（项目外）`0600`，发布换代码不踢人。
- 登录：账号不存在与密码错**返回同一句**；失败同时按「账号+IP」和「纯 IP」两层计数（6 次 / 30 次 / 10 分钟）。
- 删号要输密码，且复用登录失败计数（不能当爆破通道）。
- 备份密钥 `server/backup-key.txt` 已 `git rm --cached` 并进 `.gitignore`；`?full=1` 与 `/api/admin/*` 都要密钥。
- 战绩容量有预算：`recent` 20 条、`_seen` 40 条、本机 200 条、`sessionLog` 400KB 字节预算。

### 5.2 【P1】改密码接口不限流

**现状**：`/api/auth/password` 用 `profiles.login(acct.name, body.oldPassword)` 验旧密码，
但没有 `loginBlocked` / `noteLoginFail`（`/api/auth/delete` 有）。
**影响**：手机被借走/令牌被抓到时，可以无限次猜旧密码再改掉。
**建议**：把删号那 4 行（检查 + 记失败 + 成功清零）搬到改密码分支，抽成一个小函数复用。

### 5.3 【P2】登录存在时间侧信道

**现状**：账号不存在时**立刻**返回（不跑 scrypt），存在时要跑 ~60ms。
**影响**：`time_total` 的差异（1ms vs 60ms）足以区分账号是否存在，前面防枚举的文案就白防了。
**建议**：账号不存在时也 `await auth.verifyPassword(password, DUMMY_SALT, DUMMY_HASH)` 一次。

### 5.4 【P2】无手机号注册的取舍

**现状**：账号 = 账号名 + 密码，没有任何找回路径；昵称不唯一；令牌在 `localStorage` 存 90 天。

| 风险 | 评价 | 建议 |
|---|---|---|
| 忘密码 = 永久丢号 | **真实痛点**，熟人局里一定会发生 | 注册页写明「忘记密码找管理员重置」；管理端已有 `/api/admin/password` |
| 昵称不唯一 → 榜单可冒充 | 中 | 榜单行尾加 `#id 后 4 位`，或注册时提示「该昵称已被使用」 |
| 令牌存 localStorage（90 天） | 低-中（共用设备/理论 XSS） | 设置页加「退出全部设备」（= `tv+1`，服务端已有能力，缺一个入口） |
| 无手机号 = 无实名/无短信成本 | 这是**优点**，不要为了「更安全」去加手机号 | 保持 |

另外：`server/data/profiles.json`（种子）是入库的，里面有全部玩家的 scrypt salt/hash。
私有仓库可接受，但要意识到「仓库泄露 = 离线字典攻击的起点」；密码下限 6 位在这种前提下偏软，
可考虑提到 8 位（新增成本几乎为零）。

## 6. 兼容性

### 6.1 【P1】flex `gap` 用了 104 处

**现状**：`style.css` + `records.css` 里 104 处 `gap:`，绝大多数在 `display:flex` 的容器上。
**影响**：flex `gap` 需要 **Chromium ≥ 84 / Safari ≥ 14.1**。
- iOS 12 / 13 / 14.0 的 Safari（iPhone 6/7/8 一批机器卡在 iOS 12-15 之间）→ 间距全部塌成 0，元素贴在一起；
- 安卓微信 X5 / 老系统 WebView（Chromium 66-77）→ 同样失效。

**建议**（二选一，推荐前者）：
1. 明确写出支持矩阵（`iOS ≥ 14.5 / Android Chrome ≥ 84`），在 README 和引导页里说清，别让老机器用户一头雾水；
2. 或者给关键容器补 `margin` 兜底（`@supports not (gap: 1px)` 里加边距），成本高但兼容到底。

### 6.2 【P1】微信内置浏览器

| 项 | 现状 | 影响 / 建议 |
|---|---|---|
| Service Worker | iOS 微信 WKWebView **不支持 SW** | 无离线、无预缓存；`sw.js` 会被静默忽略，不报错。可在微信环境跳过注册，省一个失败请求 |
| 添加到桌面 | 微信里没有该入口 | 用户看不到「安装」；引导文案要写「用系统浏览器打开后再添加」 |
| 音频 | 首次手势解锁 + Web Audio 回退 | 微信 iOS 上 `Audio.play()` 有时仍被拒 → 已有合成音兜底，OK |
| 分享 | `navigator.share` 在微信不可用 | 已有「长按图片保存」兜底，OK |
| 顶栏遮挡 | `100vh` 与地址栏 | 已有 `--pt-h` + `screen.height` 校正，OK |

### 6.3 其余

- iOS Safari 13+ / 安卓 Chrome / Edge：核心路径没问题（`pointer events`、`ResizeObserver`、
  `visualViewport`、`DOMMatrix` 都有兜底或降级）。
- 微信小程序 / QQ 浏览器未测，无数据。
- 建议补一份 `docs/compat.md`：支持矩阵 + 已知降级点（flex gap、DOMMatrix、SW），
  这样以后「某个安卓机显示不对」时不用从头猜。

| **合计** | **≈ 208 KB / 13 请求** | — |

**结论**：体量可接受（4G 约 1-2s 首屏），但有两个可优化点。

### 7.2 【P2】没有 preload / 资源提示

12 个 `defer` 脚本并行下载、顺序执行，`index.html` 解析完才知道要拉 `game.js`。
**建议**：`<link rel="preload" as="script" href="./js/game.js?v=...">` 与 `style.css`（首屏 CSS 已在 head，可省），
至少给 `game.js` 加一条 —— 它是首屏最大的资源，提前一个 RTT。

### 7.3 【P2】`index.html` 冷启动 3.18s

线上第一次请求 HTML 要 3 秒（进程冷启动 / 容器唤醒），之后 0.4-0.6s。
这是部署环境特性，不是代码问题；但 SW 的 `NAV_TIMEOUT_MS = 3000` 刚好卡在这个量级上，
**冷启动时会出现「先给缓存、再刷新」的闪烁**。建议把导航超时提到 4000-4500ms，
或首次安装后（有完整 PRECACHE）才启用抢跑。

### 7.4 已经做好的（不必再动）

- 牌面：`getCardImg` 按 `suit-rank@wxh` 缓存 dataURL，53 张 × 少量尺寸，内存几 MB 上限；
  不再每次重绘都重画 canvas。
- 手牌：`renderHand` **复用 DOM 节点**，只改 `left/transform`，不重建 `<img>`（低端机点击延迟的主因已解决）。
- 组槽：字符串拼 HTML + `lastSlotsHtml` 短路，内容没变就不重写。
- 服务端：静态资源 gzip（≥1KB、level 6）+ 1 小时缓存；JSON 响应也走同一套压缩协商（带 `Vary`）。
- 服务端限流：注册 12/10min、登录 6/10min、JOIN 10/10s、单连接消息级限流、WS 缓冲区摊还扩容。
