## 二、① 离开房间的撤销

### 2.1 裁定：走「延迟执行」，不走「先执行后撤销」

确认框回调里的三步 —— `RoomStore.leaveRoom(state.roomId, state.myId)` → `cleanupRoom()` → `showScreen('screen-home')` —— **整体搬入** `undoBar.show({...}).onCommit`，确认后 5 秒才执行。窗口内服务端状态真的没变，撤销只是「什么都不做」。

**理由（直面「云端无逆操作」）**：
1. `leaveRoom` 是**服务端动作**：`hub.js` 移除成员；对局中（`stateMachine.js` L412–449）另置 `p.left=true`、冻结分数、判「人数不足 → 本局结束」并**给全桌广播**。
2. 这些后果没有逆操作：既无「重新入座并恢复分数 / 撤消弃局」的接口，也无「撤回全桌已收到的本局结束」的办法。它比清除战绩更不可逆 —— 清除战绩只影响本人数据，离开会**改写别人的这一局**。
3. 故「先执行后撤销」只能做出本机假装回去的假撤销：界面说「已取消离开」，服务端已标记离场、其他人那局已结束。这正是 `undoBar.js` L10–18 拒绝的「假撤销比不给更坏」。
4. 延迟执行不需要快照与回滚，窗口期数据真的还在，不存在「回滚失败」；5 秒后不可恢复是天然的。
5. 全部改动在客户端搬动既有三步，**不新增服务端接口、不改协议字段、不给 `leaveRoom` 加参数或改返回值语义**。

**相对契约改判了什么**：`undoBar.js` 契约本身**不改**。本批只把「离开」接成它的**第二个调用方**，并新增一条离开专属的状态变更守卫（§2.3）与一个 reason 取值（§2.3 末）。这是新增，不是改判契约。

### 2.2 交互模型：导航一并延后

- 确认后玩家**仍留在原屏**、仍是服务端房间成员，撤销条覆盖显示；三项动作一起延后，不出现「界面已到首页、服务端还在房间里」的分裂。
- 沿用 `undoBar` 既有交互（清除战绩时列表 5 秒后才清空、界面不跳走），不另造「确认即导航」。
- `onLeave` 的 `mid` 代价文案（`game.js` L3727–3743）**原样保留**：「对局中离开算弃局 · 本场按当前分数记入战绩 · 其他人这局也会就此结束」不重写、不新增第二套、不复述。

> **「导航中被结账」的准确根因**不是导航，而是「延迟窗口内服务端尚未移除该玩家」：即使界面跳到首页，服务端仍把他算作成员，窗口内结算照样落到他头上。**不靠改变导航时机规避**，靠 §2.3 的守卫。见异议 D-1。

### 2.3 状态变更守卫 —— 判据（不许含糊）

**挂载点唯一**：`attachRoom` 的 `RoomStore.subscribe(roomId, cb)` 回调（`game.js` L3317）。不另开轮询、不另挂监听、不在 `render()` 里判。该回调的 `r === null` 分支本身就会 `cleanupRoom()` + `showScreen('screen-home')`（L3318–3330），这**正是**「窗口内被结账」的真实代码路径，必须纳入判据。

**单一判据** `leaveMustCommitNow(confirmSnap, r)`：`confirmSnap` = 确认框弹出前 `fetchRoomSnapshot()` 所得快照（`game.js` L3715，已有）；`r` = 窗口内广播。命中 **P1–P4 任一**即返回真：

| | 判据 | 依据 |
|---|---|---|
| P1 | `r === null`（房间不存在 / 已回收 / 已开下一局且没带上我） | `game.js` L3318–3330 |
| P2 | `r.phase !== confirmSnap.phase`（阶段推进，含进入 `SETTLED` / 本局结算） | `stateMachine.js` L50–56 |
| P3 | `r` 标记房间已解散（`dissolve` 已生效），或 `r.players` 中已无 `myId` | `stateMachine.js` L412 |
| P4 | 收到本局结算事件（与 P2 的 `SETTLED` 取并集，防未来结算不走 phase 变更） | 结算广播 |

**命中 → 立即提交**（`undoBar.flush('room-changed')`）。**不是作废、不是照常执行、不是等满 5 秒**：
- 「作废 / 自动撤销」会把玩家硬塞回一个已结算或已解散的房间，而服务端已把他记为参与者或已清席位 —— 比执行离开更坏，且条子说「你还在房间里」是假的。
- 「照常执行」会在剩余窗口里继续显示「可撤销」，而事实已不可撤销 —— 撒谎，即用户点名的「可撤销」与「已发生的结算」互相否定。
- 「立即提交」把条子切成「已不可撤销」，让客户端状态与「玩家点名要离开」的意图一致。提交时 `leaveRoom` 在已结算房间里退化为「退出已结束房间」，**不再触发弃局**（由服务端按当时 `phase` 判定，客户端不改服务端）。

**明确排除，不进判据**：`ownerId` 变化（房主转移）、其他成员进出、`score` 变化、`ready` / `wantNext` 变化、`holdNext` 挂起开关、未生效的 `dissolve` 投票过程。这些广播**一律不提交、不作废、照常走满 5 秒，撤销仍成立**。房主转移为何排除：它不改变「我是否还是房间成员」这一唯一与「撤销离开」相关的事实。

**`room-changed` 为新增 reason 取值**：`undoBar.flush(reason)`（L141）已接受任意 reason 字符串，实现不改；仅在该文件注释的取值列表补一行。它是客户端内部字符串，**不是协议字段**。

**提交幂等**：`onCommit` 内三步须可重复调用不抛错。窗口内若订阅回调已走过 `cleanupRoom()` + `showScreen('screen-home')`，提交时再走一遍不得重复弹提示或重复导航；`RoomStore.leaveRoom` 沿用「尽力而为、失败也报成功、断线宽限与回收兜底」（`roomStore.js` L734–746），不得改成报错弹窗。

### 2.4 5 秒窗口竞态出口（逐条：撤销成不成立 / 不成立时怎么办）

| # | 出口 | 撤销还成不成立 | 不成立时怎么办 |
|---|---|---|---|
| 1 | 玩家已导航到别的屏（主动切屏） | **成立**。确认后本就不导航，主动切屏不剥夺反悔权。 | 撤销条随 `#undo-bar` 常驻（锚点约束见 §2.6 / D-2）；撤销后**不做** `cleanupRoom`、**不** `showScreen`，`state.roomId` 与 `state.room` 原样保留，玩家回到原房间屏。 |
| 2 | 房间在窗口内已结算或已解散 | **不成立**（P1–P4）。 | 立即提交 + 「已不可撤销」文案（§2.5）；`leaveRoom` 退化为退出已结束房间，不二次弃局。 |
| 3 | 房主转移 | **成立**（不进判据）。 | 不触发提交。若我是原房主：延迟窗口内我**仍是房主**，「开牌 / 等人」责任仍在我身上，撤销条不得覆盖该入口；撤销后按新 `ownerId` 以普通成员身份留下。 |
| 4 | 页面转后台 / 关闭 | **不成立**（契约规矩 2，已由 `visibilitychange` + `pagehide` 实现 `flush('hidden')`）。 | 立即提交，走同一 `onCommit` 真离开；不新增第二套后台监听。 |
| 5 | 连点 | **成立**（对第一个待办）。 | **入口短路**：`undoBar.isPending()` 为真时忽略新的「离开」请求并提示「正在离开…」，**不许**让第二次 `show()` 把第一次顶成 `superseded`。理由：`superseded` 对清除战绩安全（清两次＝清一次），对离开不安全 —— 第一次会真把人踢出房间，第二次再开窗口就失去对象。若有**别的**待撤销动作（如清除战绩）进来，仍按规矩 1 立刻提交离开，不例外。连点「撤销」沿用 `undo()` L121 的空操作保护。 |
| 6 | 断网 | **成立但需兜底**：窗口按本地计时照常走满 5 秒。 | 到点仍调 `leaveRoom`，沿用「断网也算退出、不弹离开失败、不把玩家卡回房间」（`roomStore.js` L743–745）；不因断网改判定。若窗口内连接恢复并推来 `r === null` → 转 #2。 |
| 7 | 撤销条 DOM 缺失 | **不成立**（契约规矩 3，`no-dom`）。 | `show()` 返回 false 并直接 `onCommit('no-dom')` → **立刻真离开**；绝不静默丢弃，绝不改成「因为没有条子所以不走了」。 |

**reason 全值域**（沿用 §一引用索引的接线范例 L1881–1888）：`timeout` / `hidden` / `navigate` / `superseded` / `no-dom` / **`room-changed`**（新增）六者**都**真离开；唯一不离开的路径是 `undo`，它根本不进 `onCommit`。

### 2.5 文案（三句，不新增载体）

| 场景 | 终值 | 载体 |
|---|---|---|
| 等待期 · 对局中 | `正在离开（5 秒内可撤销）· 对局中离开算弃局，其他人这局也会结束` | `#undo-msg` |
| 等待期 · 非对局中 | `正在离开房间（5 秒内可撤销）` | `#undo-msg` |
| 撤销成功 | `已取消，你还在房间里` | `flash()`，对齐 `recordsView.js` L1878 口径 |
| 已不可撤销 | `房间状态已变化，已按最新状态离开，本次无法撤销` | 撤销条切换文本后收起 |

- 等待期**只复述「弃局 + 其他人这局结束」这一个代价**（`onLeave` 已写，不另造一套），**不复述轮次 / 分数**：那属于确认框，且会随窗口漂移过时。确认框的代价结论在提交时由服务端按当时 `phase` 判定，客户端**不锁死**。
- 「已不可撤销」要讲清「为什么不能撤」，且**不许**出现「撤销成功」「已取消」字样。
- 三条都**不新增弹窗、不复用 `askConfirm`、不用第三个提示载体**（撤销条与 `flash` 是既有两个）。

**窗口时长**：沿用 `undoBar.js` 的 `DEFAULT_MS = 5000`，**本批不调**。若日后需要调，可调区间 **4000–6000ms**；依据：低于 4 秒读不完代价文案，高于 6 秒会让同桌在「这人到底走没走」上等待过久。

### 2.6 负向约束与验收点

**负向约束（不许做什么）**
1. 不许新增服务端接口、不许改协议字段、不许给 `leaveRoom` 加参数或改返回值语义。
2. 不许「先执行后回滚」或本机假装恢复；不许窗口内提前调 `leaveRoom`。
3. 不许新建第二个撤销条 DOM（`#undo-bar` 唯一）、不许为离开新增一套后台监听 / 计时器 / 独立状态机。
4. 不许重写 `onLeave` 的 `mid` 代价文案、不许在等待期复述轮次或分数。
5. 不许把 `ownerId` 变化、他人进出、分数变化当提交判据。
6. 不许让 `superseded` 制造「房间已退出却还开着一个离开窗口」。

**验收点（可机检，不写测试代码）**
- **A1**：确认后 5 秒内 `leaveRoom` / `cleanupRoom` / `showScreen` 调用数均为 0；到点后各为 1；撤销后各为 0。
- **A2**：六种 reason 逐一触发，`onCommit` 均恰好执行一次真离开；`undo` 路径上 `onCommit` 为 0 次。
- **A3**：窗口内注入 P1–P4 四类广播，`flush('room-changed')` 均被调用、条子切「已不可撤销」、撤销入口失效；注入 `ownerId` 变化 / 他人进出 / 分数变化则 `isPending()` 仍为真、可撤销。
- **A4**：确认后 `state.roomId` 非空且订阅未取消；撤销后屏与 `state.room` 不变；连点路径下 `leaveRoom` 调用数 ≤ 1。

## 四、③ 首局后的策略引导

### 4.1 裁定与边界

| 问题 | 裁定 | 理由 |
|---|---|---|
| 出现时机 | **首次进入结算页**（不选「首局结算后」） | 「首局结算后」要额外判「这是不是第 1 局」+「我是否参与了该局」；结算页可能是回看上一局（`openPrevResult`）、旁观或第 N 局，判据会分叉。「首次进入结算页」只需一个事件；且策略讲的是「下次分牌怎么分」，在任何一局的结算页给都成立。 |
| 触发条件 | **按设备只出现一次**；显示那一刻即写键 | 不在关闭时写（本行无关闭动作）；显示即写可避免刷新后重复。隐私模式写不进 → 降级为每次进入结算页都显示，因它不挡任何控件、不强制交互，可接受；**不新增第二个去重源**。 |
| 不挡住什么 | 不许压住 `#btn-next`（开始下一局）、`#btn-hold`（等人 / 开牌）、结算数字；不许增加第二个弹窗；**不许新增行高** | 结算页 390×844 无多余一行（`settleView.js` L1015–1022 实测：三种加行方案都造成重叠）。唯一载体 = 结算页单行文本，复用既有行高。 |
| 怎么关掉 | **不需要手动关**：按设备只此一次，离开结算页随屏收起；不设关闭按钮、不设自动消失计时器 | 它是一行文本不是弹窗；加关闭按钮就等于承认它会反复出现，与「一次性」自相矛盾。 |

## 七、设计异议（允许反对制作人假设，逐条给替代方案与理由）

**D-1 · 反对把 ① 的风险表述为「导航中被结账」并据此调整导航时机。**
替代：导航与三步动作一并延后（§2.2）+ 状态变更守卫立即提交（§2.3）。理由：根因是「延迟窗口内服务端未移除该成员」，改导航时机挡不住服务端把他算进结算，只会让「界面说走了、广播说还在」的状态分裂更隐蔽。且 `subscribe` 的 `r === null` 分支本就会把玩家送回首页 —— 该路径必须进判据，而不是靠锁屏规避。

**D-2 · 反对「复用 `#undo-bar` 就算接完了」。**
替代：复用**同一个** `#undo-bar` 节点，给离开态加屏级修饰（如 `data-undo-origin="leave"`）由 CSS 换锚点。理由：`.undo-bar` 是 `position:absolute; bottom:300px; z-index:82`（`pwa/css/style.css` L3467–3488），按战绩页调的；离开发生在房间 / 对局 / 结算三屏，原锚点可能压住结算数字或 `#btn-next`。新建第二个条子会同时违反契约规矩 1 与「同一事实只有一个载体」。

**D-3 · 反对把 ② 继续列为本批待办。**
替代：判 A 销项，只做结算页 HOLD 文案口径对齐（一行字）。理由：实测两屏均已可见「房主在等人 + 还剩多久」；硬做就是加一个和文字说同一件事的按钮，并会撞 `hold-next.test.js` 守住的「非房主不可操作」分界。范围控制优先于补齐一个不存在的缺口。

**D-4 · 反对 ③ 采用「首局结算后」作为触发时机。**
替代：「首次进入结算页」，按设备一次性（§4.1 / §4.2）。理由：「首局」依赖服务端判断局次与「我是否参与」，中途加入、旁观、回看上一局都会让判据分叉；「首次进入结算页」只需一个可机检事件，且策略是「下次分牌怎么分」，在哪一局的结算页给都成立。

**异议条数：4。**

## 十、v1.1 增补（2026-11-09 清验证债时的两处改判）

> 本节只写**改了什么 + 为什么 + 证据**，不复述 §2、§4 的正文。与正文冲突时**以本节为准**。

### 10.1 「屏级修饰换锚点」改为「结算屏由 JS 现算」

- **原文**：D-2 / §2.6 要求「给离开态加屏级修饰（如 `data-undo-origin="leave"`）由 CSS 换锚点」，验收写「三屏均不压主控件与结算数字」。
- **改判**：房间屏与对局屏仍用 CSS 那条统一锚点；**结算屏改由 `game.js` 的 `anchorLeaveBarOnSettle()` 现算**（取「等待行顶 / 动作区顶」更靠上者，再上留 8 CSS px，按舞台缩放换算）。
- **为什么**：结算页的等待行高度**随文案与宽度变**（策略引导 390 / 320 都是两行，HOLD 态一行），固定值只能对一档正确。实测：写死 `481px` 时，390 从「压 `#btn-next` 8031px²」变成「压 `#settle-wait` 2332px²」，320 压住「改把数」那排。
- **证据**：`probe-undo` [10]，390 / 320 两档，条子与「底部动作区 + 等待行 + 结算数字」交集面积均为 0。

### 10.2 「短竖屏不给策略行」改为「允许换行、整句照给」

- **原文**：§4.1「不许新增行高」+ R11（施工裁定）「短竖屏不显示、也不烧掉已看额度」。
- **改判**：320 档照常显示，**允许换行**（实测 2 行），显式 `white-space: normal` + `text-overflow: clip`；行数上限 3 行，由 `probe-undo` 断言。
- **为什么**：R11 的初衷是「不给半句」。但「整档不显示」与「省略号截断」是同一个问题的两面 —— 玩家都读不到那句策略。既有行高确实排不下一行，那就用两行；多占的这一行由结算列表让位（列表可滚），比「这一档没有引导」更接近 §4.1 的目的。
- **证据**：`probe-undo` [10] 打印 `策略行`：390 / 320 均 2 行、`scroll <= client`、与 `#btn-next` 间隙 17 / 14 CSS px、左右不越出 `#stage`。

### 10.3 新增的一处「已知代价」（如实记账，不当作达标）

| 屏 | 条子遮住什么 | 390×844 | 320×568 | 为什么接受 |
|---|---|---:|---:|---|
| 对局 | 手牌上沿 + 分组标签下沿 | 21029px² | 12667px² | 该屏从上到下没有 62px 空档（牌位到 545、标签 562–609、手牌 626–748、动作条 761–807）；条子容器 `pointer-events:none`，点牌照样落到牌上 |
| 结算 | 正文（320 档含「改把数」那排） | 0px² | 3266px² | 同上；且玩家此刻要么撤销、要么离开，正文不是当前动作 |

**验收口径随之明确**：三屏的硬判据是「不压**底部动作区按钮**、**等待行**、**结算数字**、**牌位里的牌**」；手牌 / 分组标签 / 结算正文属已量化的已知代价，超出上述数值需重新裁定。
