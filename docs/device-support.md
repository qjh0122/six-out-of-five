# 机型支持矩阵（实测 · v105 · 三族范围）

> 口径：**「支持」不是「能打开」**，是下面四条同时成立。全部来自真浏览器实测
> （`scripts/probe-devices.js`，Edge headless + CDP，每个视口**重新加载**后进 5 人牌桌量）。
> 代码基线：`20261031v` / sw `weile-liuxuanwu-v106`。判据本身在 `pwa/js/ringGate.js`（纯函数 + 单测）。
> **范围裁定（用户）**：必须支持的是 **iPhone / 安卓 / 电脑** 三族；平板与折叠屏「可以不支持」，
> 只记录不判定，也不为它们花工。
>
> 复跑：`node scripts/probe-devices.js --assert`（不达标则退出码非 0）；全流程见 §6。

## 0. 一页结论

| 族 | 结论 | 说明 |
|---|---|---|
| **iPhone** | ✅ 竖屏 375×667 起、横屏 **844×390 起** | SE（667×375）横屏**不支持**，理由见 §4 |
| **安卓** | ✅ 竖屏 360×640 起、横屏 **800×360 起** | 800×360 是 v105 新放开的档（以前被 scale ≥ 0.5 挡住） |
| **电脑窗口** | ✅ 宽 ≥ 640 / 高 ≥ 300 的任何窗口，**含左右分屏的窄高窗口** | 16:9 全屏停在「窄横屏」档，桌面四区档几何上到不了，见 §5；窄高窗口见 §2.5 |
| **平板** | ⚪ 横屏可玩、竖屏不上桌 | **裁定不做**。竖屏（4:3）设计高只有 1000 < 闸门 1200，见 §4 |
| **折叠屏** | ⚪ 外屏竖 / 内屏横可玩，内屏竖不上桌 | **裁定不做**。内屏竖的组槽溢出在 v105 已归零，但没有桌子（scale 0.414 < 0.44） |

一句话：**三族要的都拿到了** —— iPhone 竖横、安卓竖横、电脑窗口（含分屏窄高）。
平板与折叠屏按裁定不追，不支持的都是「几何上装不下」，不是漏判 —— 每一档都在 §4 给了数字。

## 1. 「支持」的定义（四条，写在跑之前）

一台设备算「支持」，必须同时满足：

| # | 硬指标 | 阈值 | 为什么是这个数 |
|---|---|---|---|
| 1 | 组槽不溢出 | `scrollHeight − clientHeight ≤ 0` | 这套皮肤没有可见滚动条，溢出的组会像「消失」 |
| 2 | 牌面宽度 | ≥ **39 CSS px** | 39.4 是 16:9 竖屏紧凑档的实测值；它替换掉的 v86 版式是 29.8 CSS |
| 3 | 表情入口 | ≥ **44 CSS px** | 对局里唯一的表情入口，手指够得着的下限 |
| 4 | 座位昵称 | ≥ **10.4 CSS px** | 桌面昵称是主要识别信息；10.4 是 iPhone 横屏（scale 0.52）现状 |

这四条只对**闸门放行**的档位生效，另外单独断言「iPhone / 安卓 / 电脑三族各自必须有档位进桌」——
否则「把桌子关掉」就能让前四条全绿，那是最坏的一种绿。

## 2. v105 改了什么判据

### 2.1 触摸尺度闸门（scale ≥ 0.5）撤销

原来横屏有一道 `scale ≥ 0.5` 的闸门，注释里写清了它的**唯一**理由：
「表情入口 88 设计px × scale ≥ 44 CSS」。而 `.gt-emo` 现在接上了 `--tap-min`
（= `max(88, ceil(44/scale))`），热区由构造保证 ≥44 —— **这条阈值的理由消失了**。

代价是安卓横屏最常见的那一档（800×360，scale 0.48）以前根本没桌子。

### 2.2 下限改为 0.44

新的理由从「点得到」换成「这张桌子还像不像一张桌子」：

| scale | 牌面（设计px → CSS） | 头像 CSS | 判断 |
|---|---|---|---|
| 0.48（800×360 横） | 102×143 → 49×69 | 32.6 | ✅ 进 |
| 0.459（Z Fold 外屏横） | 101×141 → 46×65 | 31.2 | ✅ 进 |
| 0.44（下限） | 104×146 → 46×64 | 30 | ✅ 极限 |
| 0.411（SE 横 667×375） | 137×192 → 57×79 | 15.6 | ❌ 不进 |
| 0.394（640×360 横） | 137×192 → 54×76 | 15 | ❌ 不进 |

`0.44` 正好卡在「800×360 之上、667×375 之下」。SE 横屏不是被新规则踢掉的，
它以前也进不来 —— 区别是现在**理由是可量的**（不是「差 2 个像素点不准」，
而是座位块只有 46 CSS px 宽，名字必被截断）。

> 注：表里 ❌ 那两行的「牌面」是无圆桌版式的牌面（v86 版式给得更大），
> 所以「不支持」在牌面这一项上并不吃亏，吃亏的是没有桌子。

### 2.3 字号与热区按 scale 反算，而不是写死

写死设计字号等于假设缩放是 1。圆桌上最小的字是座位昵称（原 20 设计px），
在 0.48 上只有 9.6 CSS px。现在四个字号由 `resize()` 按 CSS 目标反算：

| 变量 | 基准 | 保证 | 0.52 | 0.48 | 0.44 |
|---|---|---|---|---|---|
| `--seat-name` | 20 | ≥10.4 CSS | 20（不变） | 22 | 24 |
| `--seat-score` | 22/24 | ≥12 CSS | 24（不变） | 25 | 28 |
| `--seat-label` | 15 | ≥7.8 CSS | 15（不变） | 17 | 18 |
| `--seat-me` | 30/34 | ≥14 CSS | 34（不变） | 34 | 34 |

**主力机型（scale ≥ 0.52）一个像素都不动** —— 抬的只有被压小的档。
门槛是从「现状值」反推的（10.4 = 20×0.52），不是先定 10.5 再让 iPhone 横屏跟着变。

同一套思路下，表情按钮直径 = `max(88|92, --tap-min)`，居中半径由 `--emo-half` 给，
不再写死 44 —— 否则按钮长到 97 时中心会偏 4.5 设计px。

### 2.4 就位态（准备中）在矮横屏上的重叠

顺带修的一个**既有** bug：横屏就位态右栏「信息卡 + 动作条」两行，
750~780 的设计高装不下 779（房间号 + 6 行卡 + 提示 + 胶囊 + 三颗按钮），
多出来的部分压到动作条底下 —— 实测 728×348 下提示行 top 226、动作条 top 230，
「等待其他人准备」被「准备」按钮压掉一大半。

修法是去掉唯一一行不影响决策的内容（提示说的「等待其他人准备 / 全部准备好」，
中央牌的「已准备 4/5」和卡片抬头的「等大家准备 5 人」都写着），
其余 96 设计px 靠收间距出，**不缩字号**（字号已贴着 11 CSS px 下限）。

### 2.5 电脑窄高窗口（左右分屏）改走横向版式

这是「电脑兼容」里唯一真正的缺口。桌面把浏览器拉成**竖长**（Windows 的 `Win+←`、
macOS 的分屏）时，`宽 < 高` 被判成竖屏，走手机竖版 —— 而竖版的设计高是**算出来的**：

```
竖版设计高 = 视口高 ÷ (视口宽 ÷ 750) = 750 × 高宽比
```

竖版首页与牌桌要 ≥1000 设计px 才装得下，也就是要求 **高宽比 ≥ 1000/750 = 1.333**。
手机竖屏全是 1.6~2.6，装得下；桌面分屏只有 1.0~1.3，**必然溢出**：

| 窗口 | 高宽比 | 竖版设计高 | 结果 |
|---|---:|---:|---|
| 960×1040（1920 屏左右各半） | 1.083 | 813 | **组槽溢出 195 设计px、牌面 60×84（全场最小）** |
| 960×940（笔记本左右各半） | 0.979 | — | `宽>高`，本来就走横版，正常 |
| 720×780 | 1.083 | 813 | 同样溢出 |

改法是把判据从「宽 ≥ 高」换成「宽 ≥ 高 **或** 高宽比 < 1.333」（`RingGate.isLandscape`）。
960×1040 改判横版后：scale 0.591、设计高 1759、**组槽溢出 0、牌面 144×202**。

**为什么这条改不动手机与平板**（不是"测过没坏"，是数学上碰不到）：

| 设备 | 高宽比 | 与 1.333 的距离 |
|---|---:|---|
| iPhone SE 竖 320×568 | 1.775 | +0.44 |
| iPhone 15PM 竖 430×932 | 2.167 | +0.83 |
| 安卓 360×640 竖 | 1.778 | +0.44 |
| Pixel 7 竖 412×915 | 2.221 | +0.89 |
| Z Fold 外屏 竖 344×882 | 2.564 | +1.23 |
| iPad 竖 768×1024 | **1.333**（恰好卡在等号，`<` 不成立） | 0 |
| iPad Pro 竖 1024×1366 | 1.334 | +0.001 |

`ring-gate.test.js` 把这张表连同 20 个视口的朝向期望一起钉住了：改判任何一行都会红。
iPad 竖屏那条最脆（差 0.001 就会被改判），单独有一条注释说明。

> 已知外观代价：窄高窗口改走横版后，画布设计高是 1759（设计稿只有 750），
> 右栏三组会拉开较大间距、首页上下留白偏多。内容不溢出不重叠，属于「空」而不是「坏」。
> 要不要收这个空，见 BACKLOG N21。

## 5. 电脑端：为什么 16:9 拿不到「桌面四区」档

横屏的舞台设计高是**算出来的**（宽受限时）：

```
设计高 = 视口高 / (视口宽 / 1624) = 1624 ÷ 窗口宽高比
```

| 宽高比 | 设计高 | 档位 |
|---|---:|---|
| 4:3（1.33，iPad 横） | 1218 | desktop ✅ |
| 16:10（1.6） | 1015 | desktop ✅ |
| **16:9（1.78）** | **913** | narrow |
| 2.09 | 776 | narrow |
| 2.37 | 686 → 750（高受限） | narrow |

桌面四区的门槛是 `stageH ≥ 1000`（左栏要装 620 的桌 + 88 标签条 + 88 操作条），
而 16:9 恒给 913：**1024×768 的 iPad 横屏进得了桌面四区，2560×1440 的显示器进不了。**

这不是 bug —— 16:9 的纵向预算确实不够那套几何。真要让 27 寸更像「大桌」，
得给 16:9 单独做一档（把左栏按比例放宽、桌子跟着长），工作量与风险都不小
（要动 `seatRing.MODES` 与四区网格），**本版不做**，记在 `docs/BACKLOG.md`。
> 口径澄清：「电脑兼容」= 四条硬指标全过 + 能正常打完一局，**不是**「必须有桌面四区」。
> 16:9 的牌面已经封顶 144×202，缺桌面四区只影响桌子周围那圈留白。

电脑端现在的实际观感（1920×947）：桌子 650 CSS 高、牌面 144×202 CSS、
所有控件 ≥44 CSS px。是「支持」，只是没吃到那 13% 的桌子放大。

## 6. 全流程 UI 巡检（v105 新增）

前面 §1 的四条硬指标量的是**牌桌**（一个屏幕 × 30 个视口）。但用户实际会走完一条路：
引导 → 登录 → 首页 → 建房 → 准备中 → 对局 → 结算 → 战绩 → 排行 → 规则 → 账号。
牌桌没问题不等于这条路每一步都没问题。所以补了一个**正交**的探针：
`scripts/probe-ui-flow.js`（一个视口 × 13 屏；v106 加了「对局·交换」一屏）。

| 脚本 | 铺开方式 | 回答的问题 |
|---|---|---|
| `probe-devices.js` | 一个屏幕 × 30 视口 | 这个机型**支不支持** |
| `probe-ui-flow.js` | 一个视口 × 13 屏 | 这条流程**有没有坏** |

### 6.1 五类硬问题（写在跑之前，事后不许放宽）

| # | 类 | 判据 |
|---|---|---|
| 1 | **出界** | 可见元素矩形超出舞台 > 2 CSS px（被裁掉 = 看不见） |
| 2 | **溢出** | 可见元素自身内容超框（`scrollHeight − clientHeight > 1`）= 「显示不全」的根 |
| 3 | **遮挡** | 两个「可点/可读块」矩形相交 > 4px²，且互不包含，且压掉小者 ≥ 35% |
| 4 | **截断** | `overflow:hidden` 的纯文本元素 `scrollWidth > clientWidth` |
| 5 | **热区** | 可见按钮宽或高 < 30 CSS px（真正的点不到） |

### 6.1b 「对局·交换」这一屏是功能断言，不是版式审计（v106）

第 13 屏和另外 12 屏的性质不一样：它不看的版式，它验证
**「手指拖一张牌到另一张牌上，两张真的会互换」**。

为什么必须单独验：`pwa/test/swap.test.js` 能证明 `StateMachine.swapCards` 这个纯函数对，
但证明不了界面接得对 —— 中间还隔着 `elementFromPoint` 的落点判定（**必须先判牌、再判组**，
否则「落到某张牌上」永远被解析成「落到这个组」）、以及「交换分支必须排在
`if (!d.slotKey) return` 之前」（顺序错了就静默失效，拖过去没反应）。

所以这一屏真的派发一次 `pointerdown / pointermove ×2 / pointerup`，然后比对
「原来在 single 的那张是否到了 tenhalf、原来在 tenhalf 的是否到了 single」。
**验完立刻再拖一次换回来** —— 不换回来的话十点半那一组的构成变了、点数可能爆，
下一步「对局·已提交」会当场撞上 `#bust-modal`（探针自己制造的噪声，不是产品缺陷）。

失败时它进 `bad` 而不是软问题清单：拖不动是功能坏了，不能算「版式 OK」。

**登记项**（只记录不判死，但每次都要看）：

| 项 | 判据 | 为什么不判死 |
|---|---|---|
| 留空 | 内容包围盒到舞台四边的百分比 | 没有普适阈值，硬给一个数就是自欺 |
| **半行硬切** | 滚动容器里露出 ≥80% 的元素（「差一点点」） | 滚一下能看到，但「差一点点」和「差一大截」是两种体验 —— 差一点点应该改布局让它一次装下，而不是靠玩家发现能滚 |
| 热区 30~44 | 常见于 `.btn-mini` / `.gchip` | 桌面没问题、触屏偏小，记账 |

第 6 类「其他更严重问题」没有统一判据，所以**靠截图逐张人看**（`--shots` 落 12 张/视口），
不伪装成自动检测。**这一条不是免责声明** —— 本轮 9 处缺陷里有 3 处（结算第 5 行、排行页脚歪、
toast 压按钮）就是靠看图才发现的，其中 2 处至今没有硬判据能自动抓住。

### 6.2 审计规则本身先去噪，才敢用它的结论

第一版跑全矩阵报了 54 项失败，**全部是审计自身的误报**。修完这七处才敢信数据：

| 误报源 | 表现 | 修法 |
|---|---|---|
| `inScroller()` 从父级起跳、漏掉根节点 | 横屏登录页 `#screen-auth` 自己就是滚动容器，却报内部元素越界 7px | 从父级一路走到 `body`，**每一层都查（含根）** |
| computed padding 是**设计 px**、rect 是 **CSS px** | 每个弹窗都报「超出 13~15px」，恰好 = `padding × (1 − scale)` | 乘缩放比 `box.width / el.offsetWidth` |
| `scrollHeight` 被绝对定位伪元素撑高 | `.rp-sum` 的光斑让 scrollHeight 虚高 64/90px → 假「内容超高」 | 改用**子元素矩形**判越界，且只对 `overflow:hidden/clip` 容器 |
| sr-only 标题被当「文字被截」 | `#guide-title` 是 `1px×1px + clip-path:inset(50%)`（给读屏用） | `visible()` 排除 ≤2px 与 `inset(50%` |
| 弹窗打开时把底层屏算成「被遮挡」 | 一百多条 `input#room-input × div.modal-box` | 弹窗存在时**只审弹窗**；多层时按 z-index 只留最上层 |
| **「有可见子元素」被当成「不是内容」漏算** | `<p class="rp-note"><svg/>文字</p>` 整块跳过，连文字也没算进留空 → 排行空态虚报 B51（看着像下半屏全空） | 只要有**直接文本节点**就是内容，用它自己的矩形 |
| **可滚动容器里的「差一点点」两不管** | 既不是 `out`（能滚到）也不是 `clip`（overflow 是 auto）→ 结算第 5 行硬切半行从缝里溜过 | 新增「半行硬切」登记项，只认露出 ≥80% 的 |

另有三条「本来就不是问题」的：扇形叠牌相邻 `.card` 的重叠是设计；`overflow:auto` 祖先内的
越界能滚到（不算被裁）；引导卡自动弹窗污染流程（改为静态摘 `.hidden` 单独审一屏）。

**这一节的教训不是「工具会错」，是「工具的错和它的对看起来一样」。** 第一版 54 项全红的时候，
最省事的做法是把阈值调松让它变绿 —— 那等于把门关掉还说门在。正确顺序是先把每一类误报
单独定位到根因、写成一条注释，再去跑道真数据。

### 6.3 巡检第一次量到、已修的 9 处真实缺陷

全部是**既有问题**，不是本轮引入的。

| # | 屏 | 现象 | 修法 |
|---|---|---|---|
| 1 | 结算 | 列表底部**硬切半行**（844×390 实测） | `.settle-body` 挂 `scroll-fade`；`bindScrollFadeOnce()` 幂等绑定 + `rAF`/`setTimeout(80)` 延后再量（紧跟 `innerHTML` 时 `clientHeight` 可能是 0，渐隐永不挂） |
| 2 | 结算 | 第 5 行**只露出 92%**（800×360 实测） | 第 1 条只是遮丑，真因是 `max-height: 470` 装不下「5 行 530 + 尾注 40 + AI 说明 30」。先改 540 救回第 5 行，结果轮到 AI 说明被切 —— **一次算总量给到 580** 才对 |
| 3 | 排行 | 空态**贴顶 + 下方 70% 空白**（390×844 实测） | `is-empty` 同时挂 `#rank-scroll` 与 `#rank-body`，由 `#rank-scroll`（flex 项，高度确定）做 `column`，`#rank-body` 用 `flex:1` 撑满居中 |
| 4 | 排行 | 横屏页脚说明**靠左而标题居中**，看着歪（1280×720 实测） | 横屏页脚是「说明在左 + 清除按钮在右」的成对设计，但排行页**没有清除按钮**（全站排行，没人能清），左对齐失去配对对象。`#screen-rank` 单独居中，战绩页保持左对齐 |
| 5 | 首页 | toast **吞点击**且压住「玩法规则」（1920×947 实测） | `.toast` 补 `pointer-events: none`。手牌容器、座位卡都写过这条并注明理由，唯独 toast 漏了 —— **通知不该吃掉交互** |
| 6 | 登录 | `.auth-link` 热区 54×16 | `padding: 20px 8px; margin: -20px -4px`（热区撑大、版面不动） |
| 7 | 引导 | `.guide-skip` 热区 32×26 | `padding: 24px …; margin: -24px …` |
| 8 | 战绩 | `.rp-replay` 29.3 CSS（差 0.7 够不到 30） | `padding: 24px 10px; margin: -24px -10px`（过 30） |
| 9 | 全局 | `.audio-toggle--sm` / `.install-x` 64 设计px | → 76（728×348 上从 28.7 变 34 CSS） |

第 6~9 条都是同一个模式：**`padding` 撑热区 + 等量负 `margin` 抵消版面位移**。
inline 元素上 `min-height` 无效，改成 `inline-block` 会改变行盒高度、挤动周围，这是唯一不改版面的做法。

### 6.4 记录不修

| 类 | 数量 | 为什么不动 |
|---|---|---|
| 热区 30~44 CSS px | 208 条 | 集中在 `.btn-mini` / `.gchip` / `auth-tab`，桌面端完全够用，触屏偏小。全提到 44 会把工具栏挤爆，收益不值 |
| 半行硬切 | 2 条（**人眼复核均非缺陷**） | 一条是 360×640 结果卡 `div.result-group` 露出 95% —— 切掉的是容器底部留白，里面 5 行全完整；一条是 1280×720 规则正文 `dd` 露出 93% —— 长文档滚动中途，本来就该继续滚。**判据以「元素矩形」为单位，分不清「矩形内的空白」和「矩形内的内容」，所以它只能是线索不是判决** |
| N21 窄高窗口画布偏高 | 1 | 见 `docs/BACKLOG.md` N21：`.rt-desktop` 与 iPad 共用，为「可不支持」的族动三族共用布局，方向是反的 |
| toast 视觉上盖住首页按钮 | 1 | 加了 `pointer-events: none` 后**操作不受影响**（点击穿透），只剩 1.8 秒的视觉遮挡。真要消掉得把首页底部布局让开，收益极低。**这叫「通知本身就该压在内容上」，不是缺陷** |

> 「半行硬切」这项判据本轮救了结算页第 5 行（真实缺陷），也留了 2 条误报。

## 7. 怎么复跑

```bash
node scripts/probe-devices.js --assert      # 支持协议：四条硬指标 + 三族必须有档位进桌
node scripts/probe-devices.js --csv         # 全表机器可读输出
node scripts/probe-devices.js --ready       # 停在「准备中」那一屏（量就位态）
ONLY="360×800 横" node scripts/probe-devices.js --shots   # 单档截图到 tmp-shots/devices/
node scripts/probe-devices.js --home        # 停在首页（版式改判最容易把首页拉散）
node pwa/test/ring-gate.test.js             # 判据本身（纯函数，71 项；含朝向表 20 个视口）

# 全流程巡检（一个视口 × 12 屏）
node scripts/probe-ui-flow.js               # 全矩阵 12 视口 × 13 屏，约 22 分钟
ONLY="1920×947" node scripts/probe-ui-flow.js            # 单档
ONLY="360×800" node scripts/probe-ui-flow.js --shots     # 单档 + 落 12 张截图到 tmp-shots/flow/
```

`--assert` 的四条阈值写在跑之前，事后不许改；改阈值必须同时解释「为什么这个数」。
`probe-ui-flow.js` 同理：五类硬问题的阈值（2px / 1px / 4px² / 35% / 30 CSS px）也是跑之前定的。
