## 0. 结论摘要

1. **能做，但这不是"加一个圆形组件"，而是重新分配三块区域的比例。**
   现状：玩家信息占 9%，牌占 76%。圆桌方案把这两者调到约 30% / 50%。
2. **代价集中在牌面尺寸**，而且几乎全部压在「斗牛 5 张组」一个地方：
   3 张及以下的组，牌面 144×202 → 约 120×168（−17%）；
   5 张组 约 120×168 → 约 86×120（−28%）。这是唯一"明显变小"的地方。
3. **不建议引入任何现成的 poker-table 组件库**（它们全是 React + Tailwind，
   而本项目是零构建、离线优先的原生 JS）。真正值得抄的只有 30 行椭圆参数化数学。
4. **不建议用 Canvas 重画圆桌**。牌桌环是静态几何，DOM + 椭圆公式即可；
   Canvas 会把拖拽、命中、中文字号、无障碍、现有 46 处源码级断言全部推倒重来。
5. **竖屏是唯一必须妥协的一档**，横屏和桌面反而更宽松（桌面比横屏多 265 设计 px 的高）。
6. **顶栏删除和头像放大是同一件事的两半**（2026-10-30 拍板）：删顶栏腾出的 56 设计 px
   不拿去留白，全部给头像。头像上限实测是竖屏 8 人 76 设计 px，再大就贴死。
7. **表情按真广播设计**，且必须体现"谁给谁"：飞行 → 落点气泡 → 中央播报，三层缺一不可。
   这是本项目第一条"客户端可以主动广播给全房间"的消息，需要白名单 + 限流。

## 1. 现状空间账本（竖屏 390×844 → 设计空间 750×1623）

从 `style.css` + `game.js` 的常量和内边距反算，逐块列出（`#screen-game` 的 `padding` 是
上 44 / 下 72 / 左右 40）：

| 区块 | 设计 px | 占画布 | 说明 |
|---|---:|---:|---|
| 上下留白（安全区 + 屏内边距） | 116 | 7.1% | `padding: 44 … 72` |
| 顶栏 `.game-top` | 149 | 9.2% | 轮次/倒计时 + 对手横条 `.gt-opps` |
| 组托盘 `.slots` | **958** | **59.0%** | 3 条满宽「桌带」，`flex:1` 吃掉剩余 |
| 手牌扇 `.hand` | **268** | **16.5%** | 固定高，牌 168×236 |
| 组件间隙 | 40 | 2.5% | `gap: 12` × 2 + 边距 |
| 底部操作 `.game-actions` | 92 | 5.7% | 提交 / 结束 / 离开 |

**把「人」和「牌」分开看：**

- 与人相关的只有顶栏 **149 px（9.2%）**；
- 与牌相关的是组托盘 + 手牌 = **1226 px（75.5%）**。

（若按下文常引用的「内容高度」（去掉 116 的留白）算，这两个数是 9.9% 与 81.4%。两个口径都在用，
看对比对象是谁 —— 引言里用画布口径，讨论「纵向还剩多少」时用内容口径。）

这就是"没有空间维护圆桌"的量化解释，也是用户观感的来源：不是设计得不好，
而是这 9% 里已经塞了 8 个座位、分数、状态、倒计时四类信息，只能压成一条可横向滚动的长条。

> 现状的直接副作用：8 人局时对手条必须**左右滑动**才能看全，`can-scroll` 的渐隐遮罩就是这个信号。
> 圆桌的第一个真实收益不是好看，是**取消这个横向滚动**。

## 2. 为什么"圆桌"在六选五里比德州难

德州扑克能轻松圆桌，是因为它有三个前提，六选五**一个都不满足**：

| 维度 | 德州 | 六选五 | 后果 |
|---|---|---|---|
| 手牌张数 | 2 张 | **6 张** | 手牌区高度是德州的 3 倍（268 vs ~90） |
| 中央内容 | 公共牌 5 张 + 底池 | **没有公共牌** | 中央区没有天然内容，必须重新定义 |
| 分组 | 一个牌面，一次摊牌 | **两轮分组**：1+2+3 / 1+5 | 组托盘是"可拖放的目标区"，必须常驻、必须大 |

第三条最致命：**组托盘不是展示区，是拖拽目标区**。
它一旦缩小，拖牌的落点精度和"看得到自己在放哪"的信心会一起下降。
这一点决定了圆桌改造的边界 —— 环可以做，但托盘不能被压到"看不清点数"。

## 3. 开源方案调研

| 仓库 / 包 | 技术栈 | 座位 | 几何做法 | 能否直接用 |
|---|---|---|---|---|
| `N0seP1ker/PokerTable` | React + Node + Socket.IO 全栈 | 10 | 椭圆绿毡 + SVG 牌 | ✗ 整套后端，与本项目服务端无关 |
| `sfrankiel/poker-table` | React + Tailwind（MIT） | 9 / 10 | 极坐标 `x% / y%`，`useTablePositions(seats, xRadius, yRadius)` | ✗（依赖）／✓（思路） |
| `@stargazeryan/poker-ui` | React + Tailwind v4 | 2–10 | **参数化椭圆**：`ellipsePoint / ringPoints / seatAngle`，`scale-to-fit`，座位是"空框 + 插槽" | ✗（依赖）／✓✓（**几何最值得抄**） |
| `Tehes/poker` | 原生 JS + Service Worker | 2–9 | 响应式 + `dvh`，QR 分发私牌 | ✓（同技术栈，可参考响应式写法） |

**结论：抄几何，不抄依赖。**

原因很直接：本项目 `package.json` 里 `dependencies` 是空的，`pwa/` 是直接被
Service Worker 预缓存的静态文件。引入 React + Tailwind 等于给一个 5500 行的原生 JS
应用套一层构建链路 —— 收益是 30 行数学，成本是打包、版本、离线缓存、测试口径全部重做。

值得抄的就是这一段（`@stargazeryan/poker-ui` 的公开 API 语义）：

```
x(θ) = cx + rx·cosθ
y(θ) = cy + ry·sinθ
θᵢ = startAngle + i·(360/n)
```

配合本项目已有的「上弧铺开」策略（见 §5.1），把 `n` 换成「对手数」，
`span` 按人数查表，就是全部算法。

## 4. 技术路线：DOM + 椭圆定位，不用 Canvas

用户提到"纯 canvas 渲染圆桌"。这一条我**不建议采纳**，理由按重要性排序：

1. **牌面本来就是 Canvas，但只画牌面。** 现状 `Card.drawCardDataURL()` 用 Canvas 画好一张牌
   再转 `<img>`，这样牌是 DOM 节点，能拖、能被无障碍读到、能被测试断言。
   如果整桌搬到 Canvas，等于把已经分层的做法又糊回去。
2. **中文字号与换行。** 昵称是中文（"玩家A"），Canvas 要自己做测量、截断、省略号，
   还要跟着 750 设计空间的 `transform: scale()` 反算字号。DOM 一行 `text-overflow: ellipsis` 解决。
3. **命中测试。** Canvas 里点一个头像要自己做圆形/矩形命中判定 + 长按计时 + 与拖拽手势互斥。
   DOM 里是 `closest('.seat')`。
4. **测试口径。** `pwa/test/` 有 46 处 `readFileSync('js/game.js')` 的源码级断言，
   加上 `journey.js` 的 114 项端到端。Canvas 版这些断言全部失效，只能靠截图比对。
5. **性能不是瓶颈。** 一屏最多 8 个头像 + 6 张牌 + 16 个槽位，DOM 的合成开销远低于重写成本。

**推荐：DOM 定位 + `transform: translate(-50%,-50%)`，坐标用「设计 px 百分比」，
不用 JS 写像素死值。** 这一条与 v81 修底部色带的教训完全一致：
`#stage` 写死高度会在 resize 时不更新，座位坐标写死像素同理。

Canvas 保留在它该在的地方：牌面绘制、毡面纹理（可选）。

## 5. 三端适配方案

三种屏幕共用一套参数化椭圆，差别只在「可用宽高」和「托盘摆哪」。

### 5.1 座位角度算法（核心）

只用**上弧**，下弧留给「我」和牌盘 —— 这是竖屏唯一的出路。

```
span(n):  n=1 → 0°   n=2 → 132°   n=3 → 176°
          n=4 → 214° n=5 → 214°   n≥6 → 224°
```

**关键：在 [270°−span/2, 270°+span/2] 区间内按弧长均分，不是按角度均分。**

按角度均分（最初的写法 `θᵢ = 270° + (i−(n−1)/2)·span/(n−1)`）看起来天经地义，
但椭圆长轴端每度走过的长度是短轴端的 rx/ry ≈ 1.6 倍：

| 位置 | 8 人局相邻座位间距 |
|---|---|
| 顶部（θ≈270°） | 180 设计 px |
| 侧面（θ≈200°/340°） | **103 设计 px** |

而一个带昵称的座位块要 110 宽 —— **侧面必然互相压住**。这就是"头像一大就糊成一团"
的数学原因，靠调 span 是治不好的。

实现：沿区间采 512 个点算累积弧长，再按等弧长二分反解角度（原型里是 `oppAngles()`）。
均分后 8 人局各处间距统一到 ≈143 设计 px，头像才放得大。

两个附带结论：
- `span` 不是纯审美参数，它决定**最外侧座位离画布边还有多远**：4 个对手时 202° 会让
  最外侧座位中心落在 x≈58，8 字长昵称（块宽 132）左边框被裁 8px —— 所以定到 214°。
- 昵称框宽度要按座位离边的距离自适应（`--nmw`），否则长昵称在侧边必然出血。

### 5.2 三端几何

| | 竖屏 390×844 | 横屏 844×390 | 桌面 1280×800 |
|---|---|---|---|
| 画布 | 750×1623 | 1624×750 | 1624×1015 |
| 圆桌（含座位） | 494（30%） | 654（87%） | 704（69%） |
| 组托盘 | 592（36%） | 464（62%） | 641（63%） |
| 手牌 | 220（14%） | 166 | 206 |
| 托盘位置 | 桌下，满宽 | **右栏**（左桌右盘） | 右栏 |
| 牌面（3 张组） | ~120×168 | ~104×146 | ~128×180 |
| 牌面（斗牛 5 张） | ~86×120 | ~78×110 | ~96×135 |

**判断：**

- **桌面最宽松。** 比横屏多 265 设计 px 的高，圆环可以接近正圆，牌面反而比手机大。
- **横屏次之。** 高度只有 750，但宽度 1624 够分成"左桌 + 右盘"两栏，和现状的
  「左槽右手牌」是同一套分栏逻辑，改动面最小。
- **竖屏最紧。** 必须把顶栏 149 px 让给圆环，并把组托盘从 958 压到 592。

> 一个反直觉的结论：**横屏不需要为了圆桌改版式，只需要改"座位在哪"**。
> 现状左栏已经是整块牌区，把座位环画在这块区域的边缘、把手牌移到右栏即可。

### 5.3 中央公共区（替代德州的公共牌位）

六选五没有公共牌，中央改为**公共状态牌**：

```
    第 1 轮 · 房号 4821   ← 原顶栏的两个 pill，删顶栏后收到这里
        分牌中            ← 阶段（原 .gt-phase）
      剩 42s             ← 倒计时（原 .gt-timer，最后 15 秒转暖红）
   已提交 5/8  ●●●●●○○○  ← 提交进度（现状完全没有，只在结算页才知道谁交了）
```

这条是**净增能力**，不是搬迁：现在想知道"还有谁没提交"只能等，或者去房间里猜。

D2 拍板"顶栏彻底消失"之后，这里成了**唯一的公共信息位**，所以顺序按"玩家最常找的排前面"：
房号（要念给朋友听）→ 阶段 → 倒计时 → 进度。

2 人局另加一条对战条（见 §8.3），并且中央块整体下移 34 设计 px 避开正上方对手的昵称。

## 6. 交互规格

### 6.1 点头像 = 一个面板，三档内容（定稿）

早期是「点头像查战绩 + 长按开表情轮盘」，两个组件、两个位置、两套文案。实测下来这套
在圆桌上不成立，2026-10-30 重做成**一个统一的浮层面板**：

| 入口 | 面板落点 | 默认档 |
|---|---|---|
| 点别人头像 | 贴着**那个人的头像** | 表情（可切 短语 / 个人信息） |
| 点自己头像 | 贴着**自己** | 个人信息 |
| 操作栏对话气泡 | 贴着自己 | 表情 |

- **长按已取消**。上一版长按发表情、点击查战绩，两件事抢同一块热区，8 人局几乎必然误触；
  现在点击只有一个语义，面板里的那列竖排 tab（表情 / 短语 / 个人信息）负责二次分流。
- **落点规则**（`panelPos`）：右 → 左 → 下 → 上，取第一个整块放得下的方向；
  左右放不下时（竖屏 750 宽、面板 560，座位环几乎占满）改为**正上/正下**，
  并且把面板往被点那一侧对齐（`a.x > W/2` 右对齐，否则左对齐），而不是机械居中。
  四个方向都放不下才夹回画布。面板开着时被点的那颗头像会补一圈金边。
- **尺寸**：竖屏 560、横屏/桌面 620；高度按内容收（表情档 = 4 列格子的整数倍，
  战绩档渲染后实测内容高再定高，见 `fitPanel`）。横屏/桌面战绩走「KPI 与雷达并排」的宽版。
- **同一张卡**：同一个圆角、同一条绿色标题条、同一列 tab。标题只有三个字
  （表情 / 短语 / 个人信息），跟着 tab 变；副标题只放昵称。
  **不再写**「会出现在你自己的头像旁」「从你的头像飞到他头像旁」这类解释句 ——
  位置本身就是解释。
- **个人信息里不再有「发表情」按钮**：右侧那列 tab 已经能切回表情，卡里再放一个就是重复。

### 6.2 表情 / 短语：两段反馈，不跳

- **只有两层**：飞行 + 落点旁浮出。第三层「中央小字播报 · 谁给谁」按用户要求删掉了
  （一局要发好几次，多一层播报会一直抢中央区）。
- **几何是唯一真相**：`bubBox()` 算出气泡矩形，气泡自己、飞行终点都读它。
  上一版飞行终点是「头像中心」、气泡却在头像右侧，飞到地方再跳一下，非常突兀。
- **给自己发不走飞行**：起点终点是同一个人，飞一下只会像闪了一下，直接就地出现。
- **给别人发走直线**：起点 = 自己头像中心，终点 = 那枚气泡的矩形，外壳只做位移
  （`transform` 插值），缩放 .42 → 1，落定 470ms 后换成真气泡，两者同位置同尺寸，看不出切换。
- 每条消息带自增序号隔离定时器，否则连发两条时后一条会被前一条提前清掉。
- **表情 / 短语素材是位图**，不是矢量自绘：13 个表情由 `scripts/crop-emoji.py` 从参考图裁出
  （泛洪抠底 + 逐个包围盒 + 96×96 带 alpha），逐字照抄的 8 条短语在 `PHRASES` 里。
  理由很直接：自绘怎么画都和参考图有差距，用户要的是「一模一样」。

### 6.3 座位状态（把状态从文字变成图形）

| 状态 | 表现 | 触发 |
|---|---|---|
| 已提交 | 头像右下角绿勾 | 该玩家本轮已提交 |
| 等待中 | 头像右下角金色「…」 | 未提交且未超时 |
| 超时弃权 | 头像降饱和 + 红「弃」 | `endReason` 为超时 |
| 离线 | 头像灰度 | WS 断开 |

现状这些信息是挤在顶栏的一条药丸文字里，8 人时基本读不出来。

### 7.1 落地状态（2026-10-31 补）

**这张表曾经害过事**：进度表 `docs/release-progress.md` 里也有一个「P0」，指的是

## 8. 四个问题的结论（2026-10-30 拍板）

| 编号 | 问题 | 结论 | 落地情况 |
|---|---|---|---|
| **D1** | 斗牛 5 张组缩到 86 宽是否接受 | 未表态 | 原型暂按 a（86），待定 |
| **D2** | 顶栏要不要彻底消失 | **要** | 已改：顶栏整块删除，轮次/房号/倒计时/提交进度全搬进毡面 |
| **D3** | 表情是本地氛围还是真广播 | **真广播，并且要体现「谁给谁」** | 已改：三段反馈 + 服务端协议草案（见 §8.2） |
| **D4** | 2 人局对面坐还是左右坐 | **对面坐** | 零改动，见下 |

### 8.1 D2 的三条连带影响（都不显然）

顶栏不是"删掉就完了"，它原来承载四件事，每一件都要有下家：

1. **房号** → 进中央 `pl-meta`（「第 1 轮 · 房号 4821」）。放在中央其实比放顶栏更好找 ——
   玩家念房号给朋友听的时候眼睛正盯着桌子。
2. **菜单（☰ / ⋯）** → 不需要了。点自己的座位卡弹战绩卡，卡里带「发表情 / 改头像」，
   底部的操作栏保留「离开」。**顶栏唯一的价值是给这些按钮一个家，而座位卡本身就是更好的家。**
3. **空出来的 56 设计 px** → 不拿去留白，**全部换成更大的头像**。
   这是 D2 和「头像放大」两件事拼在一起的真正价值：删顶栏不是为了好看，是为了把空间给头像。

反过来说，如果当初 D2 选"保留顶栏"，头像就只能在 56~62 设计 px 上打转 —— 竖屏没有第二处能匀出 30px。

### 8.2 D3 服务端协议草案

真广播意味着「表情」从装饰变成了**一条需要鉴权、限流、校验的消息**。这是本轮唯一新增的服务端写操作。

```text
C→S   { type:'emoji', to:<playerId>|null, id:'<白名单里的 1 个>' }
S→C   { type:'emoji', from:<playerId>, to:<playerId>|null, id, at:<ts> }   // 只发给同房间
```

四条硬约束（缺一条就会被刷屏或被打穿）：

1. **白名单**：`id` 必须是服务端源码里写死的 8 个之一，**绝不接受任意字符串**。
   前端有 `esc()` 不代表可以放过 —— 一旦允许透传，聊天/广告/注入会立刻从这个口子进来。
2. **限流**：每人 2 秒 1 条、整房 1 秒最多 3 条；超出静默丢弃（不回报错，报错本身也会被刷）。
3. **不落盘**：不进 `profiles.json`、不进回放、不进战绩。表情是瞬时事件，
   一旦持久化就会带来"删号要不要删表情"这类没必要的连锁问题。
4. **`to` 用 playerId 不用座位号**：座位号会随人数/重排变化，`playerId` 才是稳定身份。

前端三段反馈（缺一层都会让人分不清是谁发的）：

| 层 | 时长 | 作用 |
|---|---|---|
| **飞行**：表情从自己座位飞向对方座位 | 480ms | 给发送者和旁观者「谁发给谁」的空间线索 |
| **落点气泡**：对方头像旁冒出白气泡 | 2.6s | 接收者最容易错过飞行那 0.5 秒，必须有落点 |
| **中央播报**：「你 → 玩家A 👍」 | 2.6s | 空间线索对第三个人不够，必须留一条可读记录 |

实测踩到的时序坑：三条反馈各有生命周期，**必须按「每条消息一个序号」管理**。
第一版用无序号定时器，两个人连着发表情时，后一条会被前一条的 2600ms 定时器提前清掉 ——
8 人局里两三个人同时点表情是常态，这个 bug 一定会出现。

### 8.3 D4 是个免费答案，但带一个副作用

现有几何里 1 个对手就落在 θ=270°（正上方），「我」在正下方 —— **本来就是对坐**，
选"对面坐"等于零改动，不需要额外分支。

副作用是：2 人局的桌子会变成一个**大空盘**（两个人撑一个 2:1 的椭圆）。
这是对面坐的必然结果，不是 bug。补法是中央加一条**对战条**：

```
你 +4   分差 2   +6 玩家A
```

分差是单挑时唯一真正重要的一条信息（谁领先多少），现在界面上根本看不到。
加了它之后中央区才有理由占住那块地方，而不是靠字号硬撑。

代价：2 人局中央块变高，**「第 1 轮 · 房号」会和正上方对手的昵称重叠**，
需要把中央区整体下移 34 设计 px、「我」的座位下移 16 设计 px。两个数都是量出来的最小值。

## 9. 头像系统（预设库 + 允许上传照片）

### 9.1 现状：根本没有"头像"这个东西

现在桌面上那个圆圈是**昵称首字 + 按 playerId 哈希出来的底色**（`colorFor(pid)`），
`server/data/profiles.json` 里没有 `avatar` 字段，服务端也从未下发过头像。

所以"加个换头像功能"实际是**打通一条新链路**，不是加个弹窗：

```
profiles.json 加 2 个字段   →  入座时带上（3 处 joinRoom/newRoom）  →  _view 自动透传
    avatar / avatarVer                 ↑ 已经是 Object.assign({}, p)，不用改
                                                        ↓
                                              前端渲染 + 选择面板
```

好消息：`hub._view()` 是 `Object.assign({}, p)` 整对象拷贝，**座位对象加了字段就自动透传**，
不用改序列化白名单。这是这次唯一省下来的地方。

坏消息：入座有 3 个入口（建房 / 加入 / 补 AI），加上重连路径 `_bind()`，
每个都要带上头像；漏一个就会出现"有的人有头像、有的人没有"。

### 9.2 预设库：8 底纹 × 6 色板 = 48 款

- **为什么不用 emoji**：跨机型/跨系统 emoji 长相不一致（Android 与 iOS 差别很大），
  8 人局里还容易撞脸撞色。预设必须是**我们自己画的东西**。
- **为什么用纯 CSS 而不是图片**：零素材、零请求、离线可用；
  而且和现有「首字 + 哈希色」老数据天然兼容 —— `pat` 缺省 = `p0` = 现在线上看到的模样，
  **不迁移任何存量数据**。
- 第一版做的是"细纹理"（细斜纹、小圆点），在 66px 的格子里几乎分辨不出来，
  一整屏缩略图看起来像同一个东西重复了 48 次。改成**双色构成**（对半 / 内圆 / 斜带 / 2×2）
  之后，小到 40px 也能一眼分出来。

### 9.3 上传照片：技术链路清楚，成本在合规

你选了「预设库 + 允许上传照片」。技术侧我有把握，先把链路写清楚：

| 环节 | 做法 |
|---|---|
| 客户端 | 选图 → `canvas` 裁成正方形 → 缩到 256×256 → JPEG q0.8（约 20–30KB）→ 上传 |
| 存储 | `~/.lxw-appdata/avatars/<playerId>.jpg`，**独立文件，绝不 base64 进 profiles.json** |
| 下发 | `GET /api/avatar/<playerId>?v=<avatarVer>`，`avatarVer` 自增用于破缓存 |
| 房间广播 | 座位对象只带 `avatarVer`（4 字节），**不带图片本身** |
| 删号 | 删文件（`/api/auth/delete` 已有清理钩子） |
| 离线 | SW 预缓存当前用户的头像；别人的头像走运行时缓存，断网时退化成预设底纹 |

> **为什么不能塞进 profiles.json**：那个文件每次房间广播都会整份参与序列化（`_view` 是整对象拷贝）。
> 8 个人各带一张 30KB 的 base64 = 240KB，每秒广播一次 —— 移动网络直接崩。
> 这条如果走错，后面全是性能事故。

**合规成本高于技术成本，这点必须写在最前面：**

这是本项目**第一次有用户生成内容进入可见区**。真人照片会带来四类风险，
而且都不是"写好代码就没事"的：

1. **内容风险** —— 色情、血腥、暴恐，8 人局里只要有一个人放上去，全桌都看得见；
2. **侵权 / 冒用** —— 上传明星/他人照片，我们没有能力审核，也没有处置流程；
3. **举报链路** —— 一旦能做到"看得见别人的照片"，就必须能做到"举报他"，
   否则出事时你没有出口；
4. **存储与隐私** —— 照片是个人身份信息，涉及留存期限、删除义务。

**我的建议：分两步放**

- **第一步（1 天）**：只上预设库，`avatar` 字段先落地。这一步零合规风险，先让"换头像"这个功能成立。
- **第二步（2–3 天 + 长期运营）**：上传作为 feature flag 默认关闭，开启前必须补齐：
  默认头像兜底、举报入口、管理员一键清除、大小与格式双重校验、只存头像不存原图、
  注销时删文件。**没有举报入口就不要开上传** —— 这是唯一一条我建议不要妥协的。

如果只想要"头像看起来有个人味"，预设库 48 款已经够了；上传带来的是真实感，也是真实风险。

### 9.4 头像放大到什么程度（实测，不是感觉）

「稍微大点」需要一个数。我做了 56 / 76 / 92 三档，在 2/3/5/8 人 × 三端下逐个量座位块间隙：

| 端 | 2 人 | 3 人 | 5 人 | 8 人 |
|---|---|---|---|---|
| 竖屏 · 小 56 | 312 | 194 | 117 | 39 |
| 竖屏 · 中 76 | 292 | 186 | 97 | **19** |
| 竖屏 · 大 92 | 276 | 183 | 80 | **2.6 ✗** |

（单位：设计 px，座位块外接矩形的最小间隙；>0 即不重叠，<16 就已经视觉贴死）

结论：**竖屏 8 人局的天花板是 76**。所以代码里加了按人数收敛的上限
（`n≥8` 时 92 自动降到 76），而不是让用户选出一个挤坏的版式。
横屏和桌面更宽松（8 人 92 还有 69~74 的余量），桌面单独给了一档 86。

## 10. 本轮实测修正（都是量出来的）

原型第一版跑通之后，逐项量测发现五个真问题。记在这里，因为它们大多会被直接带进实现：

| # | 问题 | 量到的事实 | 修法 |
|---|---|---|---|
| 1 | **座位按角度均分是错的** | 椭圆长轴端每度的弧长是短轴端的 rx/ry≈1.6 倍 → 8 人局顶部相邻间距 180、侧面只有 103，而座位块要 110 宽 | 改成**按弧长均分**（数值积分 + 二分反解角度）。8 人局各处间距统一到 ≈143 —— 这是头像能放大的数学前提 |
| 2 | **5 人局（4 个对手）最外侧座位出血** | span 202° 时最外侧座位中心 x≈58，8 字长昵称的块宽 132（半宽 66）→ 左边框被裁 8px | span 202° → 214°；同时昵称框宽度按「离画布边的距离」自适应收窄（`--nmw`） |
| 3 | **2 人局中央区和对手昵称重叠** | 对手在正上方，昵称/分数正好压在「第 1 轮 · 房号」上 | 中央区下移 34、「我」下移 16（都是最小可行值） |
| 4 | **表情轮盘把目标头像整个盖住** | 实心圆盘 280px 覆盖了它自己挂靠的那个座位 | 改成**镂空环形**（`radial-gradient` 中心透明），头像原样透出；「发给谁」是圆桌化之后唯一要紧的信息 |
| 5 | **连发两条表情，后一条被前一条清掉** | 无序号定时器，2600ms 清理会误伤新消息 | 每条消息一个自增 `seq`，只清自己那条 |

另外两条不算 bug、但要在实现时记得的：

- **昵称 8 字上限 + 侧边座位 = 必然截断。** 8 字在 21 设计 px 下约 176 宽，画布边距不够。
  现在最左侧座位显示成「爱吃肉的棒…」。要根治只能限制昵称长度（产品决定），

## 11. 验收标准

- **不重叠**：任意 2–8 人、任意档头像，座位块外接矩形两两间隙 ≥ 16 设计 px；
- **不出界**：任意座位块到画布边缘 ≥ 8 设计 px（含昵称，昵称框按距离自适应）；
- **环在桌内**：座位中心到椭圆的距离 ≤ 2 px；
- **托盘不缩水**：3 张及以下的组，牌面 ≥ 110×154；5 张组 ≥ 82×115；
- **触控**：座位命中区 ≥ 44 CSS px（沿用 `--tap-min`）；
- **表情**：三条反馈都在；连发 3 条不互相干扰；白名单之外的消息被服务端丢弃；
- **无回归**：`npm test` 与 `journey` 全绿，新增座位环纯函数单测（对齐 `slotLayout.js` 的先例）；
- **三端**：`probe-viewport-fit` 5 档仍全绿（圆桌不能再把高度算成死值 —— 见 v81 那条教训）。

## 12. 风险

1. **拖牌落点变远。** 组托盘压缩后手牌到托盘距离变短（好事），但托盘变窄后 5 张组槽位更小，
   拖拽精度下降。需要真机试一次，真接不上就得回到 D1 的选项 b。

3. **上传头像的合规成本被低估。** 见 §9.3。技术 2–3 天，运营是长期的。
4. **测试改动量被低估。** 46 处源码级断言里有多少依赖 `.gt-opps` 结构和 `.gt-me` 的 DOM 形状，

5. **服务端新增写入口。** 表情是第一条"客户端可以主动广播给全房间"的消息，
   现有 WS 有鉴权但没有按消息类型的限流，需要一起补。

## 13. 逐组结算、牌型特效、战绩页（2026-10-30 增补）

### 13.1 为什么改成「每比完一组就结算」

原规则是一轮三组比完再统一算账。问题很直接：**比大小已经把某人打到 0 分（见底），
后面两组再赢回来，整轮算完他反而是正分** —— 见底这件事在体验上等于没发生。

改成逐组结算后，一局要结算 **3 次**（第一轮 1+2+3）或 **5 次**（两轮），
每比完一组立刻出分、见底者当场出局。原型里就是 `buildScenes()` 生成的场景序列：

```
分牌 → ①揭晓 → ①结算 → ②揭晓 → ②结算 → ③揭晓 → ③结算 → [轮次交替] → 分牌 → ①揭晓 → ①结算 → ②揭晓 → ②结算 → 局终
```

- 场景 A（①就见底）4 幕，场景 B（无人见底）14 幕，两种都要在原型里能看到；
- `TIMING = { divide:1500, reveal:1400, settle:3200, break:2800 }`：揭晓 1.4s 够看清牌型，
  结算 3.2s 够看完 5 家 +/−，交替 2.8s 只放一次（要报本轮各家净得）；
- **见底政策两档**（`seg-policy`）：`立即局终` / `出局者退出、其余继续`。
  第二档的「其余继续」必须能一局里出现 2 人以上出局，否则等于第一档。

### 13.2 「进入下一次比牌」和「进入下一轮」

- **下一组**：结算条右下角固定写「下一组 3s 后」，倒计时结束自动切下一幕；
  不设「确认」按钮 —— 一局 5 次结算，5 次确认会打断节奏。
- **下一轮**：中间插一张**轮次交替卡**（`.brk`），内容是「本轮各家净得」+
  「下一轮的组顺序预告」+「分数延续 · 3s 后发第二轮牌」。
  预告那一行是这一版补的：原来只说「3s 后发牌」，玩家不知道第二轮先比什么。
  卡上不出手牌、不出组托盘，避免和「手里已经 6 张新牌」自相矛盾。

### 13.3 四种牌型特效（只有赢家放）

| 牌型 | 触发 | 表现 |
|---|---|---|
| 王十点半（`jh`） | 十点半组，赢家手上有王凑成 10.5 | 金色光环 + 冲击波 + 粒子 + 大字 `10.5` |
| 豹子（`bz`） | 飘三叶组，赢家三张同点 | 红金光环 + 毡面轻震 + 大字 `豹子` |
| 牛牛（`nn`） | 斗牛组，赢家三张凑 10 且余两张也成 10 | 紫色系，另外用金色徽章圈出「凑 10 的三张」 |
| 五花牛（`wh`） | 斗牛组，赢家五张全是 JQK | 紫金混色 + 更强震屏 + 大字 `五花牛` |

两条硬规则（都是用户当场提的）：

1. **只给赢家放**。同一组里可能出现两个五花牛、或者豹子 + 十点半，
   特写是「赢的那一手」的奖励，不是「这组有特殊牌」的通知；
   一局 5 次结算，每次放两三个就没法看了。`specialOf(mode, win)` 只接赢家，
   结算条里的橙色特殊标签也**只贴赢家那一行**（`spec = i === 0 && ...`），
   否则会出现「动画没放却有红标」。
2. **不写解释文本**。原来牌型大字下面还有一行「全手 JQK · 每家收 4 分」，
   牌型名本身已经足够，1.4 秒里读两遍同一件事纯属浪费，删掉。
   牌型尺寸 104 / 94 / 84（1 张 / 3 张 / 5 张），特效层只铺毡面矩形，不压顶部座位。

### 13.4 战绩页：6 项 + 五维牌风

参照微乐麻将的个人信息卡，在原有「总局数 / 胜率 / 总得分」之外补三项：

| 指标 | 口径 |
|---|---|
| 总局数 | 累计完成的局数 |
| 总胜局 | 单局净得分为正算一胜 |
| 总胜率 | 总胜局 ÷ 总局数 |
| 最高连胜 | 连续净得分为正的最长段 |
| 单局最高 | 单局净得分的历史最大值 |
| 总得分 | 所有单局净得分之和 |

右侧「牌风」雷达五维：**速度 / 防守 / 互动 / 策略 / 获胜**（和微乐同一套词）。
原型里这五个值是按玩家 key 哈希出来的假数据，只为把版式撑起来，接真数据时换掉即可。
底部「最近五场 · 净胜」是给「这把该不该跟」用的近期状态，不是长期统计。

### 13.6 组牌阶段的牌型反馈（2026-10-31 增补，v92）

§13.3 那四种特写全部发生在**结算弹窗**里。但一局里玩家在组牌上花的时间是结算的 4 倍（60 秒 vs 15 秒），
而组牌阶段的界面一个字都没说 —— 玩家把五张牌放进斗牛组，只看到进度从 `4/5` 变成 `5/5`，
想知道自己是牛几得自己在脑子里凑十。

这是审计里最实质的一条缺口（详见 `docs/pattern-fx-audit.md`）。补法是**放满即报**：

| 组 | 满几张 | 显示什么 | 为什么不是别的 |
|---|---|---|---|
| 比大小 | 1 | 不给 | 一张牌，牌面就是答案；再贴胶囊是重复 |
| 十点半 | 2 | `slot-point` 实时点数（金色 / 10.5 绿 / 爆牌红） | 这一组的牌型**就是**点数，早就有了 |
| 飘三叶 | 3 | 牌型胶囊：豹子 / 同花顺 / 同花 / 顺子 / 对子 / 散牌 | |
| 斗牛 | 5 | 牌型胶囊：五花牛 / 牛牛 / 牛9~牛1 / 没牛 | |

三条实现上的硬约束：

1. **判定只能走 `Engine`。** 前端此前一次牌型判定都没有（`game.js` 里 `Engine` 出现 0 次）。
   自己复算一次，大王万能的解析择优就会和结算对不上 —— 原型用 `r.t === 9` 裸数字，
   牛 9 被当成牛牛（随机 800 组里 18.5%）。
2. **胶囊顶掉 `n/n`，不并排。** 满组的进度条没有信息量，而窄横屏两列档
   `.slot-meta-main` 是 `nowrap` —— 并排会直接顶出格子。
3. **普通牌型不用组色。** 第一版用 `--slot-color`，结果飘三叶的「对子」变成一颗红胶囊，
   和旁边十点半的「爆 20」撞在一起，把「红 = 这组废了」的语义稀释了。
   现在普通牌型统一中性深底，只有 `BIG_FX` 里那 5 个大牌型才上牌型色 + 成手脉冲。

成手脉冲只放一次，靠 `slotTypeSeen` 记忆「上一次真正写进 DOM 的牌型」。
**提交时机是这段代码唯一的坑**：必须放在 `html !== lastSlotsHtml` 的写入分支里。
提前更新的话，「内容没变 → 跳过重写」那一帧会把状态吃掉，下一帧就判不出「刚成手」，
脉冲永远不放 —— 而这个 bug 在静态代码里完全看不出来。


## 14. 准备态就长在牌桌上（2026-10-30 增补）

### 14.1 人数收敛到 2–5

6 / 8 人档取消，只剩 **2 / 3 / 4 / 5**（默认 5）。连带清掉的两处是为 8 人做的补丁：
`curAv()` 里 `S.n >= 8` 的头像上限、座位块间隙的极端收敛。去掉之后 5 人是密度上限，
`span` 表里 `6 → 224°` 那一档就成了死数据（留着不碍事，但别再照着它调）。

### 14.2 不再有「房间页」：房间 = 这张桌子的无牌状态

参考微乐：进房间看到的就是牌桌。所以这一版把准备界面做成 **同一个 `geo()` 下的另一种
`phase`**，而不是另一个页面。

| 区域 | 对局中（`phase:'play'`） | 准备中（`phase:'ready'`） |
|---|---|---|
| 座位环 | 头像 + 昵称 + 分数 | 头像 + 昵称 + 「已准备 / 等待」 |
| 毡面中央 | 第几轮 · 房号 · 本组牌型 · 状态 | 房号 · 玩法 · 就绪计数 · 就绪点阵 · 上局净得 |
| 托盘区 | 组带（3 组）/ 结算条 | **本房间规则卡**（两轮顺序 / 见底政策 / 起始分 / 我的战绩） |
| 手牌区 | 6 张牌 | 无 |
| 操作栏 | 表情 · 主按钮（提交 / 下一组 / 再来一局）· 退出 | 表情 · **准备 / 取消准备 / 开始游戏** · 退出房间 |

**为什么准备态要占住托盘区**：托盘区 + 手牌区一共 870 设计px。只把桌子往中间一挪，
开局发牌时整圈座位会跟着跳一下；占住同一块矩形，牌就是从规则卡的位置长出来的，
一次位移都没有。规则卡的内容全部从 `GROUPS` / `SCORE_A|B` / `S.policy` 读，
不是写死的文案 —— 换规则它自己会变。

### 14.3 三个老功能在新界面上的位置（底层逻辑一行没动）

用户提的硬约束：退出、局终再开一局这些已经做好的功能不能因为换 UI 就没了。

| 功能 | 原来在哪 | 现在在哪 | 行为 |
|---|---|---|---|
| 退出 | 操作栏右侧「离开」 | 同一位置，文案随 phase 变（对局中「退出」/ 房里「退出房间」） | 弹确认 → 本局作废 → 回准备态 |
| 局终再开一局 | 局终卡「看结算」 | 同一位置的主按钮「再来一局」 | 回准备态，**不直接发牌**，等全员准备 |
| 表情 / 短语 | 操作栏左侧气泡 | 不变，两种 phase 共用 `emoBtnHTML()` | — |

- 阶段只有两个入口能改：`toReady(delta, msg)` 与 `startGame()`。别处一律调它们，
  否则 `rdy / countdown / timers` 这三个状态迟早会互相打架。
- 退出确认是**全项目唯一的模态**。理由只有一个：退出不可撤销（本局分数清零），
  别的（面板、tab、准备）都能就地切换，不该拦手。
- 局终回准备时会把「上局净得 ±N」带到房间牌上 —— 微乐也是这么做的，
  玩家刚被扣分，回到房间第一眼想知道的就是「刚才那把我输了多少」。

### 14.4 就绪与开局节奏

```
点「准备」→ 其他玩家按 650 + i×700ms 陆续就绪（原型模拟）
          → 全员就绪 → 3 秒倒计时（房主可点「开始游戏」提前）
          → 发牌，phase 切到 play，停在第 1 幕
```

- `S.cdOn` 是防重入的：每个对手的定时器都会走到 `startCountdown()`，只认第一个。
- 取消准备会把 `countdown` 与所有定时器一起清掉，再点准备会重新排一遍 ——
  否则会出现「点了取消，3 秒后照样开局」。
- 原型里「其他玩家」是假的（定时器模拟）。真接后端时把 `simulateReady()` 换成
  服务端推送，`startCountdown()` 换成「房主开始」事件即可，其余不用动。

### 14.5 这一轮踩的两个渲染坑

1. **`@keyframes` 收尾把居中位移抹掉**：`.ask` 最初用 `pop`，它结尾是
   `transform:scale(1)`，`translate(-50%,-50%)` 被覆盖，卡片直接偏到右下角（越界 95px）。
   `.brk` 上踩过一次，这是第二次 —— 结论：任何带 `translate(-50%,-50%)` 的元素，
   自己的 keyframes 必须把位移写进每一帧。
2. **opacity 动画在无 GPU 合成下被截成半透明**：确认框原本淡入（opacity 0→1），
   截图里整个卡片是透的，底下的规则卡文字直接压到按钮上。改成只动 `scale`、
   透明度全程 1 之后正常。这个项目的截图链路（headless + `clip` + `scale:2`）
   对「提升为合成层的透明度动画」不可靠，之前 `backdrop-filter` 的镜像问题也是同一类。

### 14.6 验收脚本

`scripts/proto-flow.js` 用真浏览器点真按钮，跑 25 条断言：

- 打开即准备态；点准备 → 全员就绪 → 倒计时 → 自动发牌（含倒计时中「提前开始」）；
- 局终 →「再来一局」→ 回准备态且记录上局净得；
- 准备态与对局中的「退出」都先弹确认，取消不生效、确认才回准备；
- 侧栏「播放整局 / 回到准备界面」来回切不串味；
- 2/3/4/5 四档准备态：座位数正确、无任何元素越界。

`scripts/shot-prototype.js` 仍负责出图 + 断言（现在 55 组），本轮新增的检查项：
`.room / .ask / .toast` 纳入越界检查；`anch.cover` 量「面板是否盖住被点的那颗头像」
（横屏个人信息从 100% 降到 0，靠的是把兜底落位从「居中」改成「靠最远一侧」）。

## 15. 规则层：原型直接引用引擎（2026-10-30 收口）

**一句话**：原型不判牌，只画牌。判定全部调 `pwa/js/engine.js`。

```html
<script src="../../pwa/js/engine.js"></script>   <!-- UMD，执行后就是全局 Engine -->
```

```js
// 名次：用引擎的比较器排序
entries.sort(function(a, b){ return Engine[CMP[mode]](b.eh, a.eh); });
// 胜负与分数：一整组交给引擎
var st = Engine.settleGroup(mode, entries.map(e => ({ id: e.k, hand: e.eh })));
```

### 为什么必须这样

原型曾经自己实现过一份 154 行的精简判定（`evSingle / evTenHalf / evPiao / evDouniu`），
与引擎构成**两份真相**。那份手抄版压掉了两样东西：

1. **大王万能**的全部分支 —— 十点半王能当 10 且比真 10 大、斗牛王能去凑三张、飘三叶王万能、有大王不算五花牛；
2. **`compareHighCards` 那层「逐张交错比 (点数, 花色)」的兜底** —— 一旦压成一维 key 数组，
   就会写错维度顺序。「先比完所有点数再比花色」和「逐张交错」在 96% 的牌面上结果相同。

代价是可量化的：飘三叶 4.4%、十点半 0.8%、含大王时斗牛 25.5% 的组**判赢判反**。
而固定演示牌组恰好绕开这些边界，画面一直是对的；25 + 54 条断言又只验布局不验分数，
所以错的东西一直是绿的。

### 原型自己只保留两样东西

| 保留 | 理由 |
|---|---|
| **牌型文案**（`handLabel`） | 显示层，属于这次要改的 UI。格式保持原样：「牛 9」「爆牌 18.0」「十点半」「五花牛」 |
| **三张凑十高亮**（`niuTrio`） | 纯视觉，引擎不导出这个分组。找错了也只是高亮错三张，不影响赢家和分数 |

### 护栏

`scripts/review-rule-parity.js` 现在检查的是「适配层有没有把引擎用错」：
赢家一致、每人得分一致、每家收分一致、名次排序严格单调、特效只挂赢家、牌型文案非空。
外加三条历史回归（牛9 不误播、全桌没牛不多扣、含王斗牛）。四种牌型 × 含王/不含王 ×
5 人/2 人 × 800 组全部 100% 吻合。

### 一个副作用

原型不再能「单独拷走一个 html 就打开」——它需要同仓库的 `pwa/js/engine.js`。
真的缺了会显示一句明确提示而不是白屏。**这是有意的取舍：宁可多依赖一个文件，
也不要规则出现第二份。**
