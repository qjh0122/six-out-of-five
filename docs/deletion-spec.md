## 0. 一句话结论

**你要的"删 A 的对局数据 + 删他和别人产生的关联数据"，现在无对象可删 ——
因为服务端从来没有存过"一场牌有哪几个人打"。**

`profiles.json` 是 `playerId → 一个人自己的统计` 的扁平表，每场结算各写各的，
A 的档案里没有 B，B 的档案里也没有 A。目前的"关联"只存在于两个地方：

1. **别人手机上的回放**（`lxw_sessions_v1`），里面有 A 的 `playerId` 和昵称 —— 显式；
2. **别人战绩里那一行的净胜分**，语义上对应"和 A 打的那场"，但字段里没有任何身份 —— 隐式。

所以要真正做到"级联删除"，第一步不是写删除逻辑，**是先建立"对局账本"**，
把原本不存在的关联关系补出来，然后才有东西可删。这是一次数据模型变更，
不是一次 bug 修复。

## 1. 需求原文与拆解

你的原话：

> 如果 a 删了号，那么他所有对局数据也会删掉，对应的和别人产生的关联数据也会被删掉，
> 不然就有问题。

这句话里其实裹着**三个层次不同、代价差一个数量级**的诉求，必须先拆开：

| 编号 | 诉求 | 现在做到哪 | 难度 | 会改别人的数字吗 |
|---|---|---|---|---|
| **R1** | A 自己的对局数据消失 | 服务端档案已删；**本机两份副本没清**（BACKLOG N3） | 低 | 否 |
| **R2** | A 在**别人设备上**的身份痕迹消失 | 完全未做，且技术上无法远程触达 | 中 | 否 |
| **R3** | A 参与过的场次从**别人的战绩**里消失 | 完全未做，**且现在没有可以删除的数据结构** | 高 | **会，而且是不可逆的** |

R1 是 bug（漏清），R2 是隐私（被遗忘权），R3 是数据模型变更。

你说话时想的大概是 R3（"关联数据也被删掉"）。但 R3 有个你可能没预料到的后果 ——
**它会把别人的战绩改掉**，见 §3。

## 2. 现状调研（全部实测，不是推断）

### 2.1 服务端只有一张扁平表

`server/data/profiles.json` 当前 8 个人，一条档案长这样：

```json
{
  "pb99796cf5f4474f9": {
    "playerId": "pb99796cf5f4474f9",
    "nickname": "玩家A",
    "games": 27, "wins": 9, "losses": 14, "draws": 4,
    "totalNet": 55, "currentStreak": -2, "longestStreak": 4,
    "longestLoseStreak": 3, "bestNet": 31,
    "recent": [
      { "endedAt": 1793345307090, "net": -6, "roomId": "393283",
        "playerCount": 4, "endReason": "scoreZero" }
    ],
    "aiGames": 14,
    "aiRecent": [ ... ],
    "account": { "name": "...", "salt": "...", "hash": "...", "createdAt": 0, "tv": 0 }
  }
}
```

关键点：**`recent[]` 里没有"对手是谁"这个字段**，一个都没有。
只有 `endedAt / net / roomId / playerCount / endReason`。

所以 A 删号时，B 的档案里**没有任何东西指向 A**，天然不需要"级联"。

### 2.2 "对局"这个实体从未存在过

`server/profile.js:1114` 自己写着：

```
服务端从来没有存过「这一局有哪几个人」——房间是内存对象，结算完就回收了。
```

`server/hub.js` 的 `_persistSettlement()` 结算时做的是：

```js
room.players.forEach((p) => {
  if (p.isBot) return;
  if (!this.profiles.accountOf(p.id)) return;   // 已删号的人不再落库
  const net = (Number(p.score) || 0) - CONFIG.INITIAL_SCORE;
  this.profiles.record(p.id, p.nickname, net, endedAt, room.roomId, room.handSeq, meta);
});
```

每个真人**各写各的一行**，写进各自的档案。`room` 结算完就被回收，
参与名单随之消失。这就是"没有对局实体"的代码证据。

### 2.3 客户端有两份副本

| 存储键 | 内容 | 含 A 的什么 |
|---|---|---|
| `lxw_records_v1` | 本机最近 200 局，每局带 `playerId` / `roomId` / `myNet` / `replay` | A 自己的账 + **回放副本里的对手** |
| `lxw_sessions_v1` | 最近 4 场整场回放（`SESSIONS_MAX`） | **所有对手的 `playerId` + 昵称 + 出的牌** |
| `lxw_session_v1` | 登录令牌 | 无 |

回放里存人的结构（`game.js:1907` `slimRound`）：

```js
rows: (g.entries || []).map(function (e) {
  return {
    i: e.id || '',        // ← 对手的 playerId
    n: e.nickname || '',  // ← 对手的昵称
    c: (e.hand || []).map(cardText),
    d: (g.deltas && g.deltas[e.id]) || 0
  };
})
```

**`i` 和 `n` 就是"关联数据"的实体形态。** 全系统只有这一处真正存了"A 和谁打过"。

### 2.4 一个必须知道的事实：历史数据已经不完整了

`RECENT_MAX = 20`，但有人场次早超过 20：

| 玩家 | games | recent 条数 | 已丢失 |
|---|---|---|---|
| 玩家A | 27 | 20 | **7 场** |
| 玩家D | 25 | 20 | **5 场** |
| 玩家B | 20 | 20 | 0 |
| 玩家C | 19 | 19 | 0 |

那 12 场的原始流水**已经不存在了**（`markAiGames` 的"残值"机制就是为绕开这件事设计的：
窗口外的那截只能用「汇总 − 窗口内汇总」估出来，估不出是哪一场）。

**结论：即使只对现有数据做级联删除，这 12 场也无法精确处理。**
任何声称"删干净"的方案，都必须先建立完整账本，并且只能对**账本上线之后**的场次保证精确。

## 3. 核心冲突：删 A 的数据，会改 B 的数字

这是整个需求里唯一需要你拍板的地方，其他都是工程问题。

假设 A 和 B 打过 8 场，B 在其中净胜 +40。现在 A 删号，如果按"关联数据也删掉"执行：

```
B.games     25  →  17     ← 少了 8 场
B.totalNet  +99 →  +59    ← 少了 40 分
B.wins      12  →  7
B.currentStreak 3 → 0（连胜被打断，因为中间那几场没了）
B.longestStreak 4 → 2
```

然后排行榜按 `totalNet` 重排，**第一名可能易主**。

由此产生三个副作用：

1. **B 什么都没做，战绩被改了，而且没有任何通知渠道**（没有站内信、没有消息）；
2. **不可逆**：A 无法恢复，B 的原始数字也找不回来（那 8 场的 `net` 只在账本里，
   账本删了就是删了）；
3. **如果 B 的战绩全由和 A 的对局构成**，`games` 会变成 0 → **B 从排行榜上消失**。

还有一个更微妙的：B 的"连胜"是跨对局的连续属性。删掉中间任一场，
**连胜的记录就不再是一个真实发生过的序列**。这不是"数字变小"，是数据变成了假的。

### 3.1 换个角度：你要抹的到底是"身份"还是"分数"？

这两个目标经常被混为一谈，但代价差 10 倍：

| 目标 | 做法 | B 的数字 | 是否符合"被遗忘权" |
|---|---|---|---|
| 抹掉**身份** | 回放里 A 显示成"已注销玩家"，昵称和 id 清空 | 不变 | ✅ 满足（识别不出是谁） |
| 抹掉**分数** | 从 B 的统计里减掉那几场并重算 | 变 | ✅ 满足，但**伤及 B** |

通用的隐私实践（GDPR 第 17 条那一类）采用的是**前者**：
删的是"能识别到 A 的数据"，不是"B 与 A 之间发生过的事"。
B 的胜负记录属于 B 自己的数据，A 的删除权不应回溯修改它。

**但对这个 8 人局的场景，我不打算用"合规实践"来说服你** —— 你的顾虑是合理的：
"我删了号，别人还能看到我出的牌、我的名字"，这确实让人不舒服。
只是那个问题的解法是**抹身份**，不是**改分数**。

这个判断需要你来做，见 §10 的 Q1。

## 4. 三个方案

### 方案 1：副本清除（不含级联）

**只做 R1 + 部分 R2，不动任何人的分数。**

改动点：

| 位置 | 改什么 |
|---|---|
| `pwa/js/game.js` `leaveAccountState()` | 加 `Records.clear(pid)` + `SessionLog.clear()` |
| `server/index.js` `/api/auth/delete` | 删号后（a）重写种子文件（见 §6.1 的复活窗口）；（b）调一次 `hub.kickPlayer(pid, '账号已删除')`（见 §6.2） |
| 新增 `/api/players/alive` | 批量查 playerId 是否还存在，供对方设备清理回放用（方案 3 的基础，方案 1 可先不做） |

**一个必须知道的副作用**：`SessionLog`（`lxw_sessions_v1`）**没有账号归属字段**
（`absorb()` 只认 `roomId + startedAt`），所以 `clear()` 只能全清。
同一台手机上如果先后登过两个号，A 删号会把 B 的回放一起清掉。
轻微、可接受，但要写进改动说明 —— 别让人以为是新 bug。
要做到"只清 A 的"，得先给 SessionLog 加 `owner` 字段（约 +0.5 天）。

工作量：**约半天**。
优点：零风险，不改任何人的数字，可立即上线。
缺点：**R3 完全没做** —— B 的战绩里那几场还在，A 参与过的事实还在。

### 方案 2：对局账本 + 级联删除 + 全量重算

**这是你字面要求的方案。**

#### 2.1 新增数据文件 `games.json`

```json
{
  "g:393283#7#1793345307090": {
    "roomId": "393283",
    "handSeq": 7,
    "endedAt": 1793345307090,
    "hasBot": false,
    "voided": false,
    "seats": [
      { "p": "pb99796cf5f4474f9", "n": -6 },
      { "p": "p0838d6b34b2ae4ca", "n": 31 },
      { "p": "pc1a2b3c4d5e6f708", "n": -25 }
    ]
  }
}
```

- 键 = `g:` + `roomId` + `handSeq` + `endedAt`（与现有 `record()` 的幂等键同构，天然去重）；
- `seats` 只有 `playerId` 和净胜分，**不存昵称**（昵称会变，存了就得同步）；
- 一场一条，删除时整条删掉 —— 这就是"删掉这一局"的物理动作。

#### 2.2 账本上线后的三重影响

好处（顺手解决的）：

- `suggestAiGames()` 不再需要靠 `playerCount` 差值去猜谁缺席 —— 账本里直接有名单；
- 可以精确回答"我和谁打得最多"（未来可做）；
- `record()` 的幂等键可以简化（账本本身就能判重）。

代价：

- 存储翻倍（当前 8 人 × 25 场 ≈ 200 条，可忽略；50 人 × 500 场 ≈ 25000 场 × 4 座 = 10 万条 ≈ 6MB，需上限）；
- 每场结算多一次写盘（账本与 profiles 需保证同一次 flush 落盘，否则会出现"账本记了、档案没记"）。

#### 2.3 删号流程（新）

```
POST /api/auth/delete  { password }
  ↓ 校验密码（已有逻辑，含限流）
  ↓ 1. 从账本找出所有含 A 的 gameKey        → keys[]
  ↓ 2. 从账本删掉这些条目                    → 有了这一步，"这一局"才真的不存在
  ↓ 3. 收集 seats 里的其他参与者             → others[]
  ↓ 4. 对 others 里每个人：从账本重算统计     → 精确，不依赖 recent 窗口
  ↓ 5. 删除 A 的档案
  ↓ 6. 写墓碑 deleted[sha1(A.pid)] = { at }  → 供客户端清回放
  ↓ 7. 踢掉 A 的所有连接（tv+1 + close）
  ↓ 8. 同步写种子文件
  ↓ 9. 返回 { removed, cascadedGames, affectedPlayers: N }
```

第 4 步的"从账本重算"是关键：因为账本里有每一场的 `net`，
所以可以完全绕开 `recent` 的 20 条窗口，得到精确值。这比 `_residual()` 那套
"汇总减窗口内"的近似算法干净得多 —— 后者本质是在猜窗口外发生了什么。

#### 2.4 历史数据怎么办

**账本上线前的场次没有账本。** 三个选择：

| 做法 | 结果 |
|---|---|
| 只处理账本内的 | 历史场次删不掉，但所有人的数字不被动过。**推荐** |
| 用 `recent` 尽力补 | 只能覆盖窗口内的，且 12 场已丢失的补不回来 → **删一半留一半，比不删更糟** |
| 全量重置 | 所有人战绩归零重新开始（`resetStats()`），激进但干净 |

#### 2.5 工作量与风险

- 服务端：约 **2 天**（账本、迁移、级联、重算、接口、日志）
- 前端：约 **1 天**（删号确认文案、受影响玩家提示、回放清理）
- 测试：约 **1.5 天**（§8 列的用例，含并发、幂等、崩溃恢复）
- 总计 **4–5 天**，且是本项目第一次**主动删除他人数据**，属于高危变更

**风险点（必须有人签字的那种）**：
- 删号是幂等的吗？重复调用会不会二次级联 → 把别人的战绩又减一遍？
- 删号过程中进程崩溃，账本删了、档案没删 → 重启后 A 的档案回来但账本没了，
  这时 A 的 `games` 是旧的、但账本查不到那几场 → **数据永久不一致**
- 两个玩家同时删号，互为主角 → 交叉级联，需要串行化

### 方案 3：墓碑 + 身份匿名化

**不动任何人的分数，但抹掉 A 的一切身份痕迹。**

#### 3.1 新增墓碑表

```json
// server/data/tombstones.json
{
  "a3f5c8...": { "at": 1793345307090, "nickHash": "9b2c..." }
}
```

键是 `sha1(playerId)`，不存明文 id。

#### 3.2 客户端行为

1. **A 自己**：`Records.clear(pid)` + `SessionLog.clear()` —— 同方案 1；
2. **B 打开回放时**：
   - 前端把回放里出现过的所有 `playerId` 批量发给 `/api/players/alive`
   - 服务端比对墓碑表，返回"已注销"集合
   - 前端**本地删掉**这些人在回放里的行（或整场删掉）
   - 若整场只剩自己，把整场回放一起删
3. **B 的战绩列表**：不受影响（数字不变）。

#### 3.3 效果

- A 的 id 和昵称从**所有能触达的设备上**消失（B 下次打开回放时就清）；
- B 的场次、胜率、连胜、排行榜名次**一分不变**；
- A 参与过的"对局事实"仍在，但识别不出是谁。

工作量：**约 1 天**。

**遗留**：B 如果永远不打开回放，那份副本就永远留在他的 localStorage 里。
这是分布式数据的物理限制 —— 没有任何客户端方案能解决，只能靠"下次打开时清理"。

## 6. 实现设计（无论选哪个方案都要处理的公共部分）

### 6.1 删号后存在一个"种子复活"窗口

`profile.js` 的持久化是两层：主文件（`~/.lxw-appdata/profiles.json`，项目外）
+ 项目内 `server/data/profiles.json` 作为**容器重建时的种子**。

`remove()` 只写主文件，种子文件不动。而种子会在两种时机被重写：

| 时机 | 内容 | A 还在吗 |
|---|---|---|
| `npm run backup`（发布前） | 从线上 `?full=1` 拉 `dump()`，dump 读的是主文件 | **不在**（主文件已删） |
| 容器重建（主文件不存在） | 直接读种子恢复 | **在** |

所以风险窗口是：**A 删号 → 下一次发布之前 → 容器恰好重建**。
这期间一旦重建，A 的档案被种子原样恢复，账号能登录、战绩全在，删号等于没删。
过了下次发布，种子被重写，窗口关闭。

这不是"必然发生"，是"必然会发生一次的东西迟早发生"。修法很简单：
`/api/auth/delete` 里删完后**立即重写种子文件**（复用 backup 脚本的写种子那段），
1 行调用的事。

### 6.2 删号后连接是"懒踢"，不是"不踢"

`server/hub.js` 的 `_pid()` **每次取身份都复查账号**，
并且已经有现成的 `kickPlayer(playerId, reason)` 专为"停用 / 删号"准备。

但 `/api/auth/delete` 现在只做了 `profiles.remove(pid)`，**没有调 `kickPlayer`**。
实际表现是：

- A 的 WebSocket 不会立刻断，但**下一次任何操作**都会被 `_pid()` 踢掉
  （`accountOf` 返回 null → `_kick`）；
- 如果 A 停在结算页一动不动，这条连接会一直挂着、座位一直占着，
  别人看到的是一具不懂不动的幽灵（`_persistSettlement` 有 `accountOf` 守卫，
  所以不会再给他记战绩 —— 数据是安全的，只是观感问题）。

所以这里不是"漏了功能"，是"已在的状态机自己兜住了，只是兜得慢"。
补一行 `hub.kickPlayer(pid, '账号已删除')` 就从懒踢变成立即踢。

### 6.3 回放里的"已注销"展示

如果选方案 3，`openReplay()` 渲染时需要一个降级路径：

```js
// 三态：存活 / 已注销 / 未知（离线，查不到）
name = alive === false ? '已注销玩家' : (row.n || '玩家')
```

离线时必须显示**原昵称**而不是"已注销" —— 否则断网看回放会满屏"已注销"，
比不清理更吓人。

### 6.4 接口约定（新增）

```
GET  /api/players/alive?ids=p1,p2,p3
     → { ok: true, dead: ["p2"], checked: 3 }
     限制：一次最多 50 个 id；不返回存活者的任何信息（防枚举）

GET  /api/privacy/policy
     → { ok: true, text: "..." }   // 隐私说明，说明副本的边界
```

### 6.5 隐私说明必须写清楚的三句话

1. 删号后，你的账号、战绩、排行榜记录立即消失；
2. 你参与过的对局回放会**留在对手的设备上**，直到他们下次打开该回放时被清理；
3. 对手的战绩数字（他们赢了多少分）**不会被修改** —— 那是他们自己的记录。

第 3 句是方案 2 和方案 3 的分野，按最终选择的方案改写。

### 6.6 一个容易漏的点：删除顺序

正确的删除顺序是 **账本 → 档案 → 种子**，任何一步失败都要能回退到"什么都没删"。
`profiles.flush()` 是延迟 500ms 的，删号路径必须像 `resetStats()` 那样
**手动 clearTimeout + 立刻 flush**，否则进程在这 500ms 内重启，
内存删了、文件还在 → 重启后 A 复活。

## 7. 三方 review

### 7.1 产品视角

**支持的**：
- 删号就该删干净，这是信任问题。用户点了"删除"却还能在别人手机上看到自己的牌，是产品缺陷。
- 方案 3 能覆盖 95% 的直觉需求，且不伤及无辜。

**反对方案 2 的三条理由**：
1. **改别人的战损**：B 打开战绩发现少了 8 场、掉了 40 分，第一反应是"我的数据被偷了"。
   产品上没有任何解释成本低于"这是 A 删号导致的"这种说法 —— 而这本身就在泄露 A 的行为。
2. **排行榜会跳**：8 人小圈子，第一名易主是**社交事件**，不是数据变化。
3. **不可逆**：A 手滑删号（虽然有密码确认），B 的战绩永久损失。当前没有任何恢复手段。

**如果一定要做方案 2，产品侧的前置要求**：
- 删号确认框必须写明："你在本系统的 N 场对局将从 M 位玩家的战绩中移除，此操作不可恢复"
- 需要一个"7 天冷静期"（软删除），但当前没有这个机制，属于额外工作量
- 需要给受影响的玩家一个可见提示（下次登录时一次性告知），否则他们无法归因

**产品推荐**：**方案 1 + 方案 3**。理由：解决真实痛点（身份残留），不制造新问题（改别人数字）。

### 7.2 开发视角

**技术债现状**：
- `profiles.json` 单文件全量读写，`_serialize()` 每次都序列化整张表。
  加账本后变成两个文件，**必须保证原子性**（要么都写要么都不写），
  现在是两次独立的 `writeFile + rename`，中间崩溃就分叉。
- `record()` 的幂等键 `roomId#handSeq#endedAt` 与账本键同构，可以复用，但
  `_seen` 只保留最近 40 个 —— 账本是持久的，两者语义不同，不能合并。

**方案 2 的实现难点（按难度排序）**：

1. **重算的精确性**：账本里只有 `net`，没有"这一把是第几轮结束的"。
   而 `currentStreak` 是时序敏感的。从账本重算需要按 `endedAt` 升序排 —— 这个可行。
   但如果两个玩家在同一 `endedAt` 有多场（不可能，房间内 `handSeq` 唯一），可以忽略。
2. **`bestNet` 的语义**：`record()` 里第一场直接做初值（不是从 0 起算）。
   从账本重算时必须复刻这个逻辑，否则"全负的人最佳成绩变 0"。
   `_aggregate()` 已经实现了正确版本，直接复用即可。✅
3. **崩溃一致性**：账本与档案是两份文件。最坏情况是账本删了、档案没删。
   缓解：删号前先把两份都写成 `.tmp`，再依次 rename；或者用一个 `pending-delete.json`
   记录"正在删除中"，启动时检查并完成未竟的删除。**这是 2 天估算里最不确定的一块。**
4. **并发**：两个删号请求同时进来，A 和 B 互为对手。Node 单线程不存在真并行，
   但 `await` 之间会让出。需要一把进程内锁（`this._deleteLock = Promise`）。

**方案 3 的实现难点**：几乎没有。墓碑表只增不改，`/api/players/alive` 是只读查询。

**开发的推荐**：如果做，先做方案 3（1 天，可回滚），观察一版再说。
方案 2 建议拆成两步：先上账本（只写不读，纯埋点），跑两周确认数据正确，再做级联删除。
理由：级联删除一旦写错，**删的是别人的数据**，而且没有回滚。

### 7.3 测试视角

**方案 2 必须覆盖的用例（写得出来才能开工）**：

| # | 场景 | 期望 |
|---|---|---|
| 1 | A 打 3 场后删号 | 账本 3 条消失；同场其他玩家的 `games -3`；`totalNet` 精确 |
| 2 | 重复调用删号接口 | 第二次返回 `{removed: false, cascaded: 0}`，**不改任何数字** |
| 3 | 删号时 A 还在房间里 | A 被踢；该房间结算不写入 A；其他人正常落库 |
| 4 | A 是唯一玩家（单机 AI 局） | `aiGames` 清零，账本无痕迹，不影响任何人 |
| 5 | 两个玩家同时删号且互为对手 | 串行执行，第二次的级联范围不含已删的场次 |
| 6 | 删号过程中 kill -9 进程 | 重启后要么全删要么全留，**不允许出现"账本没了档案还在"** |
| 7 | A 删号后 B 打开回放 | 回放里没有 A 的 id / 昵称 / 牌 |
| 8 | B 断网时打开回放 | 显示原昵称，**不显示"已注销"**（离线不能判存活） |
| 9 | 账号名/昵称被复用 | A 删号后新玩家注册同名，B 的回放**不能把新玩家当成 A** |
| 10 | 历史溢出数据（那 12 场） | 明确不在级联范围，且**不产生错误的重算** |
| 11 | `bestNet` / `currentStreak` 重算 | 与 `_aggregate()` 口径一致，含"全负玩家"边界 |
| 12 | 删号后发布一次 | 种子文件里没有 A，容器重建后 A 不复活 |

**测试视角的关键意见**：

- 用例 2、6、9 是**必须有的**，缺任意一条都不该放行。
  用例 9 尤其容易漏：墓碑表如果按 `playerId` 存，新玩家是新 id，不会误伤；
  但如果实现时图省事按昵称哈希存，就会把同名新玩家一起标成"已注销"。
- 用例 6 无法在当前架构下单测覆盖（要真 kill 进程）。要么加 `pending-delete` 机制，
  要么接受"崩溃后人工修复"并在文档里写明。
  **这是我认为方案 2 真正的风险，不是代码量大，是不可测。**

**测试的推荐**：方案 2 至少要 1.5 天写用例 + 1 轮真实设备验证。
如果开发估 2 天，测试估 1.5 天，那 4–5 天的总估算是乐观的。

## 11. 决策与实施结果（v80 / 20261030v）

### 11.1 你选了什么

| 决策项 | 选择 | 含义 |
|---|---|---|
| Q1 别人战绩里那几场 | **a 留** | 只抹身份，B 的场次/净胜/连胜一分不变 |
| Q2 别人设备上的副本 | **a 清理** | 对方下次打开回放时本地抹掉 |
| Q3 历史数据 | a 不在范围 | 账本没建，也就不存在"历史场次删不掉"的问题 |
| Q4 冷静期 | a 不要 | 删了就是删了 |

实际落地 = **方案 1 + 方案 3**，与预估的 1 天一致。

### 11.2 实现时改掉的两处设计

**（1）不要墓碑表。**
§4 方案 3 里设计了一张 `tombstones.json`，实际没建。
理由：`/api/players/alive` 要回答的问题就是「这个档案还在不在」，
而 `profiles.has(pid)` 直接就是答案。多一张表就多一处「必须和删除保持同步」的地方，
而它带来的唯一额外能力是区分「已注销」和「从没存在过」—— 调用方传上来的 id
全都来自真实回放，不存在后者。少一个状态，少一类 bug。

**（2）抹字段而不是删行。**
§6.3 里写的就是这个，实现时确认了理由：1v1 局删掉对手那一行，回放里只剩一个人，
渲染出来像一副没打完的牌。而回放的价值在「这把牌怎么走的」，不在「对手叫什么」。
所以只清 `i`（playerId）和 `n`（昵称），牌和分数原样留着。

判据是 **`i` 与 `n` 同时为空 = 已注销占位**。
只有 `i` 为空是「老数据没存 id」，那是"不知道名字"，不是"已注销"。
这两者混起来，所有老记录都会凭空变成「已注销玩家」。

### 11.3 端到端探针抓到三个真 bug

这三个都不是设计阶段想到的，是 `scripts/probe-delete-purge.js` 跑出来的。
**它们的共同点是：单测全绿、代码看起来对、界面上没有任何异常表现。**

| # | 症状 | 根因 |
|---|---|---|
| 1 | 删号后本机战绩一条没删，界面却显示"账号已删除" | `AuthStore.deleteAccount()` 成功后立刻 `clearSession()`，等 `leaveAccountState` 再取 pid 只拿到空串；而 `Records.clear('')` 匹配的是「没有归属的老记录」，自己这个号的一条都不动 |
| 2 | 存活查询永远查不到结果（线上会 403/401） | 用了裸 `fetch('/api/players/alive' + apiQuery(...))`，既没拼 sharecode 也没带 `X-Session-Token`。本地服务端不校验网关，所以本地是通的 |
| 3 | 清理跑完了，界面上名字还在 | scrub 改的是磁盘那份，内存里的 `packs` 还是旧的；重画必须重新 `SessionLog.load` / `Records.all()` |

第 2 个和第 41 章 manifest 403 是同一类问题的两面：
**「本地绿」和「线上绿」是两件事**，而这次的教训更具体 ——
裸 `fetch` 在本地能跑通，只因为本地没有网关。

### 11.5 这一次留下什么

**已解决**：
- A 删号后，A 自己的手机（战绩 + 回放）、服务端档案、种子文件三处都清；
- A 在 B 手机上的回放副本，会在 B 下次打开时把名字抹掉；
- B 的分数一个字节没动 —— 这是你选的，也是我认为对的那条。

**明确不解决（写进文档而不是假装不存在）**：
- B 如果永远不打开回放，那份副本就永远留着。没有任何客户端方案能解，
  只能靠"下次打开时清理"。这是分布式数据的物理限制。
- `SessionLog.clear()` 是全清（它没有账号归属字段），同机多账号时 A 删号
  会连带清掉 B 的回放。回放是过程数据不是战绩，可接受。
- 方案 2（账本级联）没做。若将来要改口径，先看 §2.5 和 §7.3：
  它真正的风险不是代码量，是「崩溃后账本与档案分叉」这条**不可测**。
