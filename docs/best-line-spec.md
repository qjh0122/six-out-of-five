# 「理论上最高分 vs 实际得分」需求分析（P1-1 / B1）· ✅ 已实施（v110）

> **一句话**：这把牌，如果分牌的时候你做的是最优选择，你能拿几分；实际上你拿了多少。
>
> **实施结果**：`pwa/js/bestLine.js` + 结算页一行小字，2026-11-01 上线。
> 与本文的差异只有三处，都是实施时才知道的：
>
> | 本文写的 | 实际做的 | 为什么 |
> |---|---|---|
> | 加一个「开关控制，关掉与现状一致」 | **没加开关** | 加开关意味着两条渲染路径要各自维护，而这条功能只是多渲染一小块。真要退回，删 `recheckEl` 一处即可 —— 有 `if (!rec) return null` 兜着，删了页面照常 |
> | 从 `p.groups` 取手牌 | 从 `room.history` 取 | 下一把 `dealAll` 会覆盖 `groups`，而结算页渲染时已经是「这一把打完」。history 是唯一同时带手牌和每组 `deltas` 的地方 |
> | 按 `room.handId` 过滤出「这一把」 | 按 history **末条**的 `hid` 过滤 | **这是个真 bug**：结算页读到 `handId=2` 而 history 的 `hid` 全是 1 → 过滤出 0 条 → 复盘行整块消失且不报错（当时 4589 条单测全绿）。原因见 `bestLine.lastHandRounds` 的注释 |
>
> 实测：整把 66 种分法 / 192 次 `settleGroup`，平均 **6ms**（本文估的是 <100ms，实际更快）。
> 交叉验证「拿实际分法跑一遍 == 实际净胜」已作为固定断言写进 `pwa/test/best-line.test.js`。
>
> 这是 `docs/PLAN.md` 里「决策可见性」那一层的核心，也是评审里唯一能把这游戏从「能玩」
> 推向「优秀」的改动 —— 因为它把系统**早就算得出来的东西**第一次交给玩家看。

## 一、为什么要做（判断，不是功能清单）

六选五的对手牌永远是暗的。这意味着玩家**没有任何反馈通道知道自己的分法好不好**：

- 赢了，可能是分法好，也可能是运气；
- 输了，可能是分法差，也可能是运气。

同类游戏（斗地主、麻将）都有「复盘」这条路，而这游戏的 60 种分法比它们复杂得多，
玩家却只能靠「下次试试另一种」自学。最直觉的打法胜率 41.2%，**低于随机**（见 `REVIEW-2026-11-01`）。

系统其实一直在算这件事：`ai.js` 能在 1 毫秒内给 60 种分法打分，但它只用来决定机器人出牌，
**从没让玩家看过一眼**。这个方案要做的就是把那张表搬出来。

## 二、口径（这一节是全文最重要的部分）

### 2.1 是「事后最优」，不是「事前最优」

| | 事前（打牌前） | 事后（打完之后） |
|---|---|---|
| 已知信息 | 只有自己 6 张 | 所有人的 6 张 |
| 能算什么 | 期望值（EV） | **确定的最优结果** |
| 例子 | 「这个分法中奖面更宽」 | 「这样分你能拿 +6，你实际拿了 +2」 |

**只能做事后。** 事前最优需要预测对手的牌，那不是「理论最高」，那是「猜」。

事后最优的意义也成立：玩家想知道的正是「我这手牌本可以打成什么样」——
这是复盘的标准问法，和棋类复盘的「这步走了臭棋」是同一件事。

### 2.2 只在「已经结束的一把」上算

不能在对局中算，也不能预告。理由有两条：

1. 对局中算需要知道对手手牌，那是作弊；
2. 就算能算，中途告诉玩家「你这次分错了」会打断牌局节奏。

### 2.3 与「残局」无关：整把算完才能算

一把两轮，两轮都打完才有完整信息。第一轮结束时只能算第一轮（60 种分法），
第二轮只能算第二轮（6 种分法）。两轮独立，可以分别算再相加 —— 见 §3.2。

## 三、算法

### 3.1 核心：把「我的手牌所有分法」逐个真结算一遍

```js
// 伪代码
function bestNetOf(myHand, others, round, groupsDone) {
  var best = -Infinity;
  forEachSplit(myHand, round, function (split) {          // 60 种 / 6 种
    var net = 0;
    ROUND_GROUPS[round].forEach(function (mode) {
      var entries = [{ id: 'me', hand: split[mode] }].concat(others);
      var r = Engine.settleGroup(mode, entries);
      net += r.deltas.me;                                  // 我在这一组的净得
    });
    if (net > best) best = net;
  });
  return best;
}
```

**关键点：用 `Engine.settleGroup` 真结算，不自己写一套比较逻辑。**
理由和整个项目一样：算分口径只能有一份，否则「复盘说你能拿 6 分，实际结算给了 5 分」
会比没有这个功能更糟。

### 3.2 两轮分别枚举，不相乘

| 轮次 | 分组形状 | 分法数 | 每组结算次数 |
|---|---|---|---|
| 第一轮 | 1 张 + 2 张 + 3 张 | `6 × C(5,2) = 60` | 60 × 3 = 180 |
| 第二轮 | 1 张 + 5 张 | `6` | 6 × 2 = 12 |

**不能把两轮的分法相乘**（60 × 6 = 360 种组合）：第一轮和第二轮用的是同一副 6 张牌，
但两轮各自独立结算，不存在「第一轮这么分、第二轮必须那样分」的耦合。
分别取最优再相加，就是整把的最优。

代价：192 次 `settleGroup`，每次约 0.1~0.5 毫秒（纯算术 + 少量排序），
**总耗时 < 100 毫秒**，在结算页渲染前算一次可以接受。

### 3.3 边界情况

| 情况 | 处理 |
|---|---|
| **十点半爆点** | 归入「不可能的选项」，不算进最优里 —— 因为爆点本来就被弹窗硬挡住、提交不上去。否则会出现「理论最高分是靠一个你没被允许提交的分法拿到的」 |
| **弃权（手牌为空）** | 不参与枚举。弃权那一组无论怎么分都是 0 分，把它算进最优没有意义 |
| **中途离开 / 掉线** | 用离开那一刻冻结的手牌与分数，与结算口径一致 |
| **平局** | `settleGroup` 已经处理了平局（`tieIds`），不需要额外分支 |
| **含 AI 的局** | 照常算。AI 的牌也是牌，事后复盘一样成立 |
| **别人的最优分要不要显示** | **不显示**。结算页只给自己那一行加，别人的最优分属于「我替你复盘」，越界了 |

## 四、展示

### 4.1 位置：结算页「我」那一行

结算页现在是每人一行（名次 + 昵称 + 净胜）。在「我」那一行下面加一行小字：

```
🥇 我             +2
   └ 理论上最高 +6　（差 4 分）
```

**为什么只给自己加**：这是复盘，不是排行榜。给别人加会让结算页变成「公开处刑」，
而且玩家会去比较「他运气真好」，反而偏离「看自己的决策」这个目的。

### 4.2 文案：三种情况分开写

| 情况 | 文案 |
|---|---|
| 实际 = 最优 | `最优分法，这手牌你已经打满了` |
| 差 1~2 分 | `理论上最高 +6（差 2 分）` |
| 差 ≥3 分 | `理论上最高 +6（差 4 分，分牌可以再想想）` |

**不用「你亏了 4 分」这种说法**：亏不亏取决于运气，而这个数字衡量的是决策质量。
「差 4 分」是事实，「亏 4 分」是评判。

### 4.3 回放里也要有

结算页只显示最近一把。回放（`historyKit` 的 packs）里每一把都能看到同一行，
否则玩家第二天想复盘就找不到了。

**实现上是一次计算两处用**：`packHistory` 打包时顺手把 `bestNet` 算进去存好，
结算页和回放读同一个字段。不要在两个地方各算一次 —— 那会变成两份口径。

## 五、实现位置

| 文件 | 改什么 | 理由 |
|---|---|---|
| **`pwa/js/bestLine.js`（新建）** | 枚举 + 结算 + 返回最优净胜 | 纯逻辑，可单测；不进 `game.js`（那个文件已经够大） |
| `pwa/js/settleView.js` | 结算页「我」那一行下面加一行 | 它已经是结算页的唯一渲染处 |
| `pwa/js/historyKit.js` | `packHistory` 时算 `bestNet` 存进 pack | 回放要读同一份 |
| `pwa/css/style.css` | 一行小字的样式 | — |

**服务端不改**：这个数字是「复盘提示」，不参与战绩、不进排行榜、不落库。
一旦落库就要考虑口径变更时怎么迁移，而它对玩家档案没有任何价值。

## 六、成本与风险

| 项 | 内容 |
|---|---|
| **成本** | 1.5 天（枚举 0.5 + 结算页 0.5 + 回放 0.3 + 测试 0.2） |
| **最大风险** | **口径漂移**：如果 `bestLine` 自己写了一套比较逻辑，某天引擎改规则，它会算出一个和实际结算不一致的「理论最高」——玩家一眼就能看出这游戏在胡说。**必须复用 `Engine.settleGroup`，并且测试里要用同一批手牌交叉验证「实际分 == 用实际分法跑 bestLine 的结果」** |
| **次要风险** | 性能。192 次结算在低端机上可能到 300ms。第一次实测要量，超过 500ms 就在 Web Worker 里跑或者改成「点了才展开」 |

---

## 七、验收判据

1. 用实际的分法跑 `bestLine`，得到的值**必须等于**结算页显示的实际净胜（这条是交叉验证，错了说明口径漂移）
2. 最优值**永远 ≥ 实际值**（数学上必然成立；出现反例说明枚举漏了分法）
3. 十点半爆点的分法不出现在最优结果里
4. 结算页只给「我」加这一行，别人没有
5. 回放里每一把都能看到同一行，且数字与结算页一致
6. 192 次结算总耗时 < 500ms（在 iPhone 上实测）

## 八、明确不做

| 不做 | 理由 |
|---|---|
| **事前最优 / 概率预告** | 需要预测对手牌，那是另一套东西（而且会破坏博弈） |
| **告诉玩家「具体该怎么分」** | 那就不是复盘了，是把答案直接给出去。只给结果不给路径，玩家才会自己想 |
| **给别人算最优** | 越界，且会把结算页变成公开处刑 |
| **落库 / 上排行榜** | 它对档案没有价值，落库只会多一份要维护的口径 |
