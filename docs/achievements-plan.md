## 一、结论先行

**能做，而且成本比预想低。**

关键发现：`Engine.settleGroup` 返回的每一组结果里，`entries[].typeName` **已经带着每个玩家的牌型**
（豹子 / 同花顺 / 牛牛 / 五花牛 / 10.5 …）。也就是说结算那一刻，成就需要的原始数据全部算好了，
只是 `stateMachine` 在组装 history 时把这个字段丢掉了（`stateMachine.js:974`）。

所以**不需要新增牌型判定逻辑**，只需要：把已有的 `typeName` 留下来 + 在落库时按玩家累加计数。

**一件事必须提前说清**：现有 118 场历史战绩里**没有存牌型**，服务端也没有回放数据。
所以服务端的权威计数**从上线那天开始**；本机能回填的只有最近几场（详见 §九，
量级是几十把，不是 118 场）。

## 二、数据可行性

### 2.1 逐项核对

| 要统计的 | 现在有没有 | 缺什么 | 改动量 |
|---|---|---|---|
| 十点半 10.5 次数 | **结算时算出来了**（`typeName`） | 没存进档案；`stateMachine` 组装时丢了 `typeName` | 小：保留字段 + 累加 |
| 同花顺 / 豹子次数 | 同上 | 同上 | 小 |
| 牛牛 / 五花牛次数 | 同上 | 同上 | 小 |
| 大牌型对撞（被吃 / 吃掉） | **牌型都有**，但需要「双方都是大牌型」的判定 | 需要一份「哪些算大牌型」的名单 + 一个比较 | 小：纯函数 |
| 第一轮三组通吃 | 有（每组的 `winnerId`） | 需要按轮聚合判定 | 小：纯函数 |
| 第二轮两组通吃 | 同上 | 同上 | 小 |
| 场次 / 胜负 / 连胜 / 最高净胜 | **已有**（`games` / `wins` / `longestStreak` / `bestNet`） | 无 | 零 |
| 单把净胜 ≥N | 已有（`recent[].net`） | 无 | 零 |
| 建房次数 / 连续登录天数 | 没有 | 需要新字段 | 小 |

### 2.2 改动点（共三处）

| 文件 | 改什么 | 为什么 |
|---|---|---|
| `pwa/js/stateMachine.js:974` | `entries` 里补回 `typeName`（引擎已经给了，这行只是没带上） | 前端回放也能受益：回放里能看到每个人当时是什么牌型，不只是赢家 |
| `server/profile.js` | `_blank()` 增加 `ach` 字段；`_persistSettlement` 后累加 | 档案里存成就计数 |
| `server/hub.js` | 结算落库时把本轮 `groups[].entries[]` 传给累加函数 | 把数据从房间状态送进档案 |

### 2.3 数据结构（建议）

```js
ach: {
  v: 1,                                  // 版本号，以后加字段能迁移
  seen:  { th:0, ld:0, sf:0, nn:0, wh:0 },   // 参与该组的次数（概率分母）
  made:  { th:0, ld:0, sf:0, nn:0, wh:0 },   // 拿到该牌型的次数
  vsWin: { th:0, ld:0, sf:0, nn:0, wh:0 },   // 双方都是大牌型时，我赢
  vsLose:{ th:0, ld:0, sf:0, nn:0, wh:0 },   // 双方都是大牌型时，我输
  sweep1: 0,   // 第一轮三组全赢
  sweep2: 0,   // 第二轮两组全赢
  sweepAll: 0, // 一把五组全赢
  sweepTotal: 0,
  handsPlayed: 0,   // 已计入成就的把数
  from: 1793000000000  // 开始统计的时间戳，页面上要写「从 X 月 X 日起」
}
```

**体积**：约 20 个整数 ≈ 300 字节/人，对现在 8 个档案、`MAX_PROFILES=200000` 的规模都不是问题。

### 2.4 「对撞」的精确定义（按你的原话）

> 分母是「自己拿到大牌型的同时，别人也拿到大牌型」；吃掉普通牌型不算

落到代码上，一组结算时：

1. 算出组内**所有**玩家的牌型（已有 `typeName`）
2. 用一张「大牌型名单」筛出其中的大牌型持有者
3. 如果**我**是大牌型持有者，且**组内至少还有一个别人**也是大牌型持有者 → 记一次 `vs`
4. 其中我赢 → `vsWin`；我输 → `vsLose`

**要注意的边角**：
- **平局**（同牌型同点数同花色）：既不算赢也不算输，但要计入分母吗？建议**计入分母、单列 `vsTie`**，否则「赢+输 ≠ 分母」会对不上账
- **同一个大牌型多个人**（例如三家都是豹子）：只算一次对撞（我 vs 其余），不按人数加权
- **作废的局**（`room.voided`）不计入 —— 与现有战绩口径一致

## 六、风险与明确不做

| 风险 | 说明 | 处理 |
|---|---|---|
| **服务端历史不能回填** | 118 场历史没有牌型数据，服务端也没有回放 | 服务端从上线起算；本机回填最近几场并标注来源（§九）。**不要**把本机回填结果上传服务器——那会引入多设备重复计数 |
| **`ach` 字段会让档案变大** | 每人约 +300 字节 | 可忽略（当前 8 人共 15KB） |
| **老档案没有 `ach`** | 读取时要兜底 | `_blank()` 补默认值，读到缺失就按全 0 处理 |
| **成就会诱导刷** | 例如为了「五子登科」故意找弱对手 | 好友房场景，没有陌生人匹配，刷不出什么；不为它加防刷逻辑 |
| **`stateMachine` 改 `entries` 结构** | 会让回放数据多一个字段 | 只增字段不改结构，老回放读到 undefined 时按「未知牌型」显示，不影响渲染 |

**明确不做**：
- 不做成就点数 / 等级 / 兑换（这是好友房，不是手游）
- 不做全服公告 / 弹窗庆祝（打断打牌）
- 不做「隐藏成就」（玩家没耐心猜）

## 九、历史回填：能回多少、怎么回

> **本方案未采纳（2026-11-01 定）。** 项目所有者选了 **B：只显示服务端值**。
> 下面这段分析保留，是因为它记录了「为什么不回填」这个判断的依据 ——
> 以后再有人问「能不能把老战绩也算进去」，先看这里。
>
> 不采纳的直接理由：回填只在这一台设备有效，于是同一个人在两台手机上看到的数字不同，
> 而且**别人点他头像看到的数字，比他本人看到的少**（因为对手手机里没有他那部分回放）。
> 一个「成就」如果自己看到 7 次、朋友看到 5 次，它就不成立。
> 现在页面统一写「从上线起记录」，所有人看到的数字永远一致。

### 9.1 先说能回多少（这个数字可能和预期不同）

「回填」听起来像能把 118 场历史都补上，但本机数据有两个硬上限：

| 来源 | 上限 | 位置 |
|---|---|---|
| `sessionLog` | **只留最近 4 场**（`SESSIONS_MAX = 4`），每场最多 24 把 | `pwa/js/sessionLog.js:40-41` |
| `records` 里的 replay | 单局内截断：4 轮 / 6 组 / 12 行 | `pwa/js/records.js:152-154` |
| localStorage 配额 | 超出时丢最旧的（由字节预算控制） | `pwa/js/sessionLog.js:23` |

**结论：本机能回填的是「最近几场」，量级在几十把，不是 118 场。**
118 场是服务端的累计战绩数，服务端从来没有存过牌型。

### 9.2 做法：双层数字，不往服务器传

| 层 | 来源 | 覆盖 | 特点 |
|---|---|---|---|
| **A 层（权威）** | 服务端 `ach` 字段 | 从上线那天起 | 准确、跨设备一致、别人也能看到 |
| **B 层（本机回填）** | 扫本机 replay 重算 | 最近几场 | 只在这台设备有效 |

**展示时 A + B 相加，并标注来源**：

```
豹纹加身          已达成
你一共拿过 7 次豹子 · 出现率 4.2%
其中 2 次来自本机历史记录
```

**为什么不把回填结果上传服务器**：

- 一旦上传，就得在服务端做幂等（同一局从两台设备传两次不能算两次），要多存一份去重键
- 更麻烦的是：如果先在一台只玩过 10 局的设备上传，另一台玩过 50 局的设备就被挡住了
- 不上传就没有这些麻烦，代价只是「两处看到的数字可能不同」

**代价说清楚**：

- 你自己的两台设备，成就数字可能不一样（各自的本机历史不同）
- **别人看你的成就，数字会比你看到的少**——因为他看不到你本机的 B 层

### 9.3 实现

| 步 | 做什么 |
|---|---|
| 1 | 新增 `pwa/js/achieveBackfill.js`：扫 `SessionLog` 与 `Records` 的 replay，用 `Engine` 重算每人牌型与组结果 |
| 2 | 结果缓存进 localStorage，key 带数据指纹（场次数 + 最后一把时间戳）——数据没变就不重算 |
| 3 | 首次打开成就页时异步计算，不阻塞渲染；算完再刷新数字 |

**成本 +0.5 天**（在第 4 步 UI 里一并做）。

### 9.4 如果不接受「两处数字不同」

那就退回只显示 A 层，页面上写「从 2026-11-XX 起记录」。
**一句话就能砍掉这 0.5 天和上面那两条代价。** 这个取舍由你定。
